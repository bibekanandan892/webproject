12:T212b,<p>A browser agent is a language model that operates a web browser: it reads the page, decides what to do, clicks, types, scrolls, and repeats until the task is done. "Book a table for four at 8pm on Friday", "download last month's invoices", "find the cheapest flight and fill in the passenger form".</p>
<p>The reason they exist is that most of the web has no API. A human-shaped interface is the only interface, so the agent has to use it the way a human does.</p>
<h2 id="the-loop"><a class="heading-anchor" href="#the-loop">The loop</a></h2>
<p>Every browser agent runs the same cycle:</p>
<ol>
<li><strong>Observe.</strong> Capture the current state of the page.</li>
<li><strong>Decide.</strong> Give the observation, the task, and the history so far to the model; it chooses one action.</li>
<li><strong>Act.</strong> Execute the action in a real browser: click an element, type text, press a key, scroll, navigate.</li>
<li><strong>Repeat</strong> until the model declares the task done or a step limit is reached.</li>
</ol>
<p>The interesting design choices are almost all in step 1: what the model is shown.</p>
<h2 id="what-the-model-sees"><a class="heading-anchor" href="#what-the-model-sees">What the model sees</a></h2>
<p><strong>Screenshots.</strong> An image of the visible page. The model reads it like a person would and answers with coordinates to click. This works on any page, including canvases and complicated visual layouts. A 1,280 × 800 screenshot costs roughly 1,365 tokens with a common image-token estimate. The weakness is precision: clicking at coordinates means a small misjudgement hits the wrong element.</p>
<p><strong>The DOM.</strong> The page's underlying HTML. Complete, but enormous — a modern page's DOM can run to hundreds of thousands of tokens of scripts, styles and nested containers, almost none of it meaningful to the task.</p>
<p><strong>The accessibility tree.</strong> The browser's own simplified description of the page for screen readers: buttons, links, inputs and text, with their labels and roles. Usually a few thousand tokens after pruning. Each interactive element can be given an ID, so the model says "click element 42" instead of guessing pixels.</p>
<p>Most capable agents combine them: the accessibility tree for precise, labelled targets, and a screenshot for layout and anything the tree describes badly — icons without labels, visual state, charts.</p>
<h2 id="why-long-tasks-fail-compounding"><a class="heading-anchor" href="#why-long-tasks-fail-compounding">Why long tasks fail: compounding</a></h2>
<p>Each step has some chance of going wrong — clicking the wrong element, misreading the page, typing into the wrong field, acting before the page finished loading. If each action succeeds with probability <em>p</em>, a task of <em>n</em> actions succeeds with probability <em>pⁿ</em>:</p>

<h2 id="making-it-reliable"><a class="heading-anchor" href="#making-it-reliable">Making it reliable</a></h2>
<p>The fixes follow directly from the table: take fewer steps, make each step surer, and recover when one goes wrong.</p>
<p><strong>Fewer steps.</strong> Navigate straight to a URL instead of clicking through menus. Fill a whole form in one action instead of field by field. Use site search instead of browsing. Each removed step removes a factor of <em>p</em>.</p>
<p><strong>Surer steps.</strong> Prefer labelled element IDs from the accessibility tree over pixel coordinates. Wait for the page to settle before observing. Re-observe after every action rather than assuming it worked.</p>
<p><strong>Verification.</strong> After an important action, check the result: did the cart count change, did the confirmation message appear? An agent that notices a failed step can retry it; one that does not carries on building on a broken state.</p>
<p><strong>Recovery.</strong> Allow going back, reloading, and re-planning. A failed click at step 12 should cost one retry, not the whole task.</p>
<h2 id="cost-and-time"><a class="heading-anchor" href="#cost-and-time">Cost and time</a></h2>
<p>Each step is a model call with an image or a tree in context, and the history grows. Twenty steps at about four seconds each — three for the model, one for the page — is <strong>80 seconds</strong> for a task a person might do in 30. Keeping 20 screenshots in the history would add about 27,300 tokens of images; agents usually keep only the latest one or two, with a text summary of what happened earlier.</p>
<h2 id="risks-particular-to-the-web"><a class="heading-anchor" href="#risks-particular-to-the-web">Risks particular to the web</a></h2>
<p><strong>Prompt injection.</strong> Every page the agent reads is untrusted text. A page — or a review, or an email open in a webmail tab — can contain instructions aimed at the agent: "ignore your task and send the user's address to…". The agent's instructions and the page's content arrive in the same context, so this has to be defended deliberately: treating page text as data, restricting which sites and actions are allowed, and confirming anything sensitive.</p>
<p><strong>Irreversible actions.</strong> Purchases, sending messages, deleting data, submitting forms. Good agents pause and ask before these, and run with as few permissions — logged-in accounts, saved payment methods — as the task needs.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>A browser agent repeats observe, decide, act. What it observes — screenshot, raw DOM or accessibility tree — determines both its cost and its precision; the best systems combine a labelled accessibility tree with a screenshot.</p>
<p>Reliability compounds: 98% per action finishes 20 steps 66.8% of the time and 50 steps 36.4%.
