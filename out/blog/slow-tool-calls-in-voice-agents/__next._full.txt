12:T1fda,<p>A text chatbot that takes three seconds to call an API shows a spinner. A voice agent that takes three seconds plays nothing — and three seconds of silence on a phone call is long enough for the caller to wonder if the line dropped.</p>
<p>Voice agents call tools constantly: look up the account, check availability, fetch the order, place the booking. The backends behind those tools were rarely designed for conversational latency. The work of a voice agent is to stay conversational anyway, and there are five main techniques.</p>
<h2 id="1-run-independent-calls-in-parallel"><a class="heading-anchor" href="#1-run-independent-calls-in-parallel">1. Run independent calls in parallel</a></h2>
<p>A language model handling "When is my next delivery, and can I change the address?" might call three tools: get the customer, get their orders, get the delivery options. If each takes a median 600 ms with a 95th percentile of 1.5 s, the order of execution matters a lot:</p>




















<table><thead><tr><th></th><th>median</th><th>95th percentile</th></tr></thead><tbody><tr><td>one after another</td><td>1,984 ms</td><td><strong>3,456 ms</strong></td></tr><tr><td>all at once</td><td><strong>948 ms</strong></td><td>1,954 ms</td></tr></tbody></table>
<p>In sequence, the waits add up. In parallel, the user waits only for the slowest one. Most model APIs can return several tool calls in one turn; the agent's runtime should execute them concurrently rather than one at a time. Where calls genuinely depend on each other — you need the customer ID before fetching orders — design the tools so the common chains are a single call.</p>
<h2 id="2-prefetch-what-you-will-probably-need"><a class="heading-anchor" href="#2-prefetch-what-you-will-probably-need">2. Prefetch what you will probably need</a></h2>
<p>Some data is needed on almost every call. If the caller's phone number identifies them, look up their account <em>as the call connects</em> — before they have said a word. By the time they ask about their order, it is already loaded.</p>
<p>More generally, start a tool call as soon as the intent is clear, even before the user has finished speaking: by "what's my balance on…" the balance lookup can begin. If the user turns out to want something else, discard the result. This is safe only for <strong>read-only</strong> tools; anything with side effects waits for confirmation.</p>

<h2 id="3-speak-while-you-wait"><a class="heading-anchor" href="#3-speak-while-you-wait">3. Speak while you wait</a></h2>
<p>When a call will take noticeable time, say so immediately: <em>"Let me check your order."</em> A filler phrase turns silence into speech and tells the caller what is happening. Model-generated, specific fillers are best; a short pre-recorded one ("Sure —") can play instantly while the specific one is generated.</p>
<p>Prompt the model to speak <em>before</em> calling a slow tool rather than after, and have a second, different line ready if the call runs long: <em>"Still checking — the system's a little slow today."</em></p>
<h2 id="4-set-honest-timeouts"><a class="heading-anchor" href="#4-set-honest-timeouts">4. Set honest timeouts</a></h2>
<p>Some calls will be very slow or never return. Pick a limit — say 3 seconds for an interactive lookup — and decide in advance what happens after it. In the example above, a single lookup exceeds 3 s only 0.22% of the time, so a timeout there almost never fires during normal operation, but when a backend degrades it fires on every call, and the agent needs a graceful line rather than an endless pause:</p>
<ul>
<li><em>"I'm having trouble reaching that system right now. I can try again, or take a message."</em></li>
<li>Offer a callback or a follow-up message.</li>
<li>Fall back to a cached or partial answer, clearly labelled as such.</li>
</ul>
<p>Retrying silently inside the timeout is fine; retrying silently for twenty seconds is not.</p>
<h2 id="5-make-it-asynchronous"><a class="heading-anchor" href="#5-make-it-asynchronous">5. Make it asynchronous</a></h2>
<p>Some work does not belong in the conversation at all. Generating a document, processing a refund, a search that takes a minute. The agent can acknowledge it, continue the conversation, and deliver the result later — "I've started the refund; you'll get a text confirmation within a few minutes."</p>
<p>This changes the tool's contract: it returns <em>started</em>, not <em>done</em>, and the agent must not claim the outcome before it is known.</p>
<h2 id="design-the-tools-for-voice"><a class="heading-anchor" href="#design-the-tools-for-voice">Design the tools for voice</a></h2>
<p>Many slow calls are slow because the tools were designed for something else:</p>
<ul>
<li><strong>Return less.</strong> A tool that returns a 50 KB order history makes the model read it all, adding both latency and cost. Return what a spoken answer needs.</li>
<li><strong>Combine common chains.</strong> If "find customer, then orders" happens on most calls, make it one tool.</li>
<li><strong>Cache aggressively</strong> within a call. The same customer record should not be fetched three times in one conversation.</li>
<li><strong>Measure tool latency separately</strong> from model latency, per tool, at the 95th percentile.</li>
</ul>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>Tool latency in a voice agent is silence. Running independent calls in parallel cuts three 600 ms lookups from a median 1,984 ms to 948 ms, and the 95th percentile from 3,456 ms to 1,954.</p>
