4:T2d55,<p>A language model on its own reads text and writes text. Ask it something it cannot know and it will guess.</p>
<p>An agent is that same model wrapped in a loop that lets it call tools, see what came back, and decide what to do next. It keeps going until the job is done.</p>
<h2 id="what-actually-changes"><a class="heading-anchor" href="#what-actually-changes">What actually changes</a></h2>
<p>Three things get called AI, and it is worth separating them.</p>
<p>A <strong>plain model call</strong> takes a prompt and returns a completion. One in, one out, nothing else happens.</p>
<p>A <strong>chatbot</strong> is the same thing with the conversation kept and replayed each turn. It remembers, but it still only produces text.</p>
<p>An <strong>agent</strong> can act. It is given a set of tools it may call, and something outside the model actually runs them and hands back the results.</p>
<p>The loop is what makes it an agent. Without it the model could ask for a tool once and never learn what the tool returned.</p>
<h2 id="the-parts"><a class="heading-anchor" href="#the-parts">The parts</a></h2>
<p><strong>The model.</strong> It decides what to do next. Worth being precise: it never runs anything itself. It emits a request — this tool, these arguments — and something else carries it out.</p>
<p><strong>Instructions.</strong> The system prompt: what the job is, which tools exist, what the rules are, and what counts as finished.</p>
<p><strong>Tools.</strong> Each one is a name, a description of when to use it, and a schema for its arguments. The description matters more than it looks — it is the only thing the model has to go on when choosing.</p>
<p><strong>Memory.</strong> Short-term is the running history replayed each turn. Long-term is anything kept outside the conversation and looked up when needed.</p>
<p><strong>The loop.</strong> Ordinary code. It calls the model, executes whatever tool the model asked for, appends the result, and calls the model again.</p>

<p>That is the entire idea. The intelligence is in the model's choices; the loop is plumbing.</p>
<h2 id="watching-one-run"><a class="heading-anchor" href="#watching-one-run">Watching one run</a></h2>
<p>Give an agent three tools — <code>list_orders</code>, <code>get_delivery</code>, <code>calculate</code> — and this goal: <em>which suppliers delivered late last month, and by how many days?</em></p>

<p>Two things in there are worth noticing.</p>
<p>At step 2 it issued five calls together rather than one at a time. Nothing in the loop forbids that, and when calls do not depend on each other it is simply faster.</p>
<p>And at no point did it decide in advance that there would be four steps. It asked for the orders, and what came back determined what it asked for next. That is the part a fixed script cannot do.</p>
<h2 id="when-not-to-use-one"><a class="heading-anchor" href="#when-not-to-use-one">When not to use one</a></h2>
<p>An agent is the right shape when later steps depend on earlier results and the path cannot be known up front.</p>
<p>If the sequence is always the same, write the sequence. A fixed pipeline is faster, cheaper, and does the same thing every time — none of which an agent can promise. Paying a model to rediscover a path you already know is a bad trade, and it will occasionally rediscover a different one.</p>
<p>The same goes for anything a single call answers. Wrapping it in a loop adds latency and failure modes and buys nothing.</p>
<h2 id="what-goes-wrong"><a class="heading-anchor" href="#what-goes-wrong">What goes wrong</a></h2>
<p>The happy path is easy. Nearly all the engineering is in the rest.</p>
<p><strong>It loops.</strong> The same tool, the same arguments, forever — usually because the result never satisfies whatever it is waiting for. A hard step limit is not optional; it is the only guaranteed exit.</p>
<p><strong>It picks the wrong tool.</strong> The model chooses from descriptions alone, so two tools described similarly will be confused with each other. Fixing this is writing better descriptions, not prompting harder.</p>
<p><strong>It invents a tool, or invalid arguments.</strong> Validate arguments before executing and hand the error back as an observation. A well-phrased error is something the model can recover from; a crash is not.</p>
<p><strong>It runs out of context.</strong> Every step appends to the history, so a long run eventually exceeds the window. Older steps have to be summarised while the goal and the recent steps are kept intact.</p>
<p><strong>It stops early.</strong> It reports success on something half done, because nothing told it precisely what finished means. That belongs in the instructions, stated as a checkable condition.</p>
<h2 id="the-short-version"><a class="heading-anchor" href="#the-short-version">The short version</a></h2>
<ul>
<li>An agent is a model, instructions, tools, memory, and a loop.</li>
<li>The loop is what separates it from a chatbot: it can act and then see the result.</li>
<li>The model never executes anything — it requests a tool call and the runtime carries it out.</li>
<li>Independent calls can be issued together; dependent ones force another turn.</li>
<li>The path is decided as it goes, which is the reason to use one and the reason it is unpredictable.</li>
<li>If the steps are always the same, write a script instead.</li>
<li>Step limits, argument validation, context trimming and a clear finish condition are the actual work.</li>
