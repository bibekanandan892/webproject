11:T28b1,<p>Ordinary retrieval-augmented generation is a straight line. Take the question, search for passages that look like it, hand those to the model, get an answer.</p>
<p>It works when one search is enough. Agentic RAG is what you do when it is not: put an agent in charge of the searching, so the number of searches, the queries, and the sources are all decided as it goes.</p>
<h2 id="where-one-search-runs-out"><a class="heading-anchor" href="#where-one-search-runs-out">Where one search runs out</a></h2>
<p><strong>The answer is spread across two documents.</strong> Ask which supplier made the part that failed in a recall, and no single passage contains both the recall and the supplier. Searching for the question retrieves things that look like the question, which is not the same as things that answer it.</p>
<p><strong>The question is vague.</strong> "What changed in the new policy?" matches almost everything and nothing. A fixed pipeline cannot narrow it; it just retrieves badly and proceeds.</p>
<p><strong>The answer is not in the documents.</strong> Some questions want a number from a database, or something only on the web. One vector store is one kind of source.</p>
<p><strong>The retrieval was poor and nothing noticed.</strong> This is the worst of the four. A fixed pipeline hands over whatever ranked highest, including when nothing relevant was found, and the model writes a confident answer on top of it.</p>

<p>The agent decides whether to retrieve at all, which source to use, what query to send, whether what came back is any good, and whether to go again. Standard RAG has none of those decisions in it.</p>
<h2 id="one-running"><a class="heading-anchor" href="#one-running">One running</a></h2>
<p><em>Which supplier made the component that failed in the March recall?</em></p>






























<table><thead><tr><th>step</th><th>what it does</th><th>what comes back</th></tr></thead><tbody><tr><td>1</td><td>recognises two unknowns; starts with the recall — <code>sql_query</code> on the recall records</td><td>batch B-2291, failed part: pressure valve, revision C</td></tr><tr><td>2</td><td><code>vector_search("pressure valve supplier")</code></td><td>chunks about the valve — but revision B</td></tr><tr><td>3</td><td>judges these wrong and re-queries: <code>vector_search("pressure valve revision C supplier")</code></td><td>the revision C entry, supplier named</td></tr><tr><td>4</td><td>enough to answer</td><td>Halvern Industrial</td></tr></tbody></table>
<p>Step 3 is the whole point.</p>
<p>The retrieval at step 2 was not a failure in any way a pipeline could detect. It returned relevant-looking passages about the right component, ranked confidently. A fixed pipeline hands those straight to the model, which writes a fluent answer naming the wrong supplier — and nothing anywhere reports a problem.</p>
<p>What caught it was the agent reading the chunks against a fact it had picked up at step 1: the revision is C, these say B. Then it rewrote the query with the revision pinned.</p>
<p>That is the difference between retrieving and researching.</p>
<h2 id="three-ways-it-usually-shows-up"><a class="heading-anchor" href="#three-ways-it-usually-shows-up">Three ways it usually shows up</a></h2>
<p><strong>Think, act, observe.</strong> The general loop: reason about what is needed, search, read the result, decide whether to go again. This is what the trace above does.</p>
<p><strong>Grading its own retrieval.</strong> Before answering, score the chunks on two questions — are they relevant, and do they actually support the answer being written? Low scores mean searching again or dropping the chunk rather than using it.</p>
<p><strong>Falling back.</strong> When one source comes up empty, try a different kind. Vector search finds nothing, so go to the web; the web is unhelpful, so query the database. Robustness through having more than one place to look.</p>
<p>These overlap in practice. A real system usually does all three.</p>
<h2 id="what-it-costs"><a class="heading-anchor" href="#what-it-costs">What it costs</a></h2>


















































<table><thead><tr><th></th><th>standard</th><th>agentic</th></tr></thead><tbody><tr><td>retrievals</td><td>one</td><td>as many as it decides</td></tr><tr><td>sources</td><td>usually one</td><td>several</td></tr><tr><td>query rewriting</td><td>no</td><td>yes</td></tr><tr><td>checks what it retrieved</td><td>no</td><td>yes</td></tr><tr><td>multi-hop questions</td><td>fails</td><td>handles</td></tr><tr><td>latency</td><td>one round</td><td>several</td></tr><tr><td>cost</td><td>one model call</td><td>one per step</td></tr><tr><td>same question, same path</td><td>yes</td><td>not guaranteed</td></tr></tbody></table>
<p>The last row causes the most trouble in practice. Two runs of the same question can take different routes and produce differently-worded answers, which makes both testing and debugging harder than for a pipeline that always does the same thing.</p>
<p>And the loop needs a way out. Stop when the agent says it has enough, when a confidence threshold is met, or when the step count runs out — but something has to stop it, or a question with no answer in the corpus becomes an expensive infinite search.</p>
<h2 id="when-to-use-which"><a class="heading-anchor" href="#when-to-use-which">When to use which</a></h2>
<p>Use the agent when questions genuinely need more than one lookup, when the answers live in several different kinds of store, when queries arrive vague, or when being right matters more than being fast.</p>
<p>Use the straight pipeline when questions are direct, the data is in one place, and latency and cost matter. Most questions really are one search, and paying an agent to work that out each time is a bad trade.</p>
<h2 id="the-short-version"><a class="heading-anchor" href="#the-short-version">The short version</a></h2>
<ul>
<li>Standard RAG retrieves once and generates; agentic RAG lets an agent decide the retrieval.</li>
<li>One search fails on multi-hop questions, vague queries, several sources, and bad results nothing checks.</li>
<li>The agent chooses the source, writes the query, judges what came back, and decides whether to search again.</li>
<li>Judging the result is the part that matters — plausible wrong chunks are invisible to a fixed pipeline.</li>
<li>Common shapes: the think-act-observe loop, grading retrievals, and falling back to another source.</li>
<li>It costs latency, tokens, and determinism.</li>
<li>Something must stop the loop.</li>
