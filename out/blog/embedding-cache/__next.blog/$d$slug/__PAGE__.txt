5:T1ed5,<p>An embedding model turns text into a fixed vector. It is deterministic: the same text through the same model produces the same numbers, today and next month.</p>
<p>So computing it twice is work you have already done. An embedding cache is the obvious response — store the vector under a key derived from the text, and look it up next time.</p>
<p>The obvious part is not the interesting part. The interesting part is how few entries you need.</p>
<h2 id="traffic-is-not-spread-out"><a class="heading-anchor" href="#traffic-is-not-spread-out">Traffic is not spread out</a></h2>
<p>Suppose a search feature sees 200,000 queries a day across 100,000 distinct phrasings. If those were evenly spread, caching would be nearly pointless — each entry would be used twice.</p>
<p>They are never evenly spread. Real query traffic is heavily skewed: a small number of phrasings account for a large share of requests, and there is a long tail of things asked once and never again.</p>
<p>Under the usual skew:</p>

























<table><thead><tr><th>entries cached</th><th>share of traffic they cover</th></tr></thead><tbody><tr><td>100</td><td>42.9%</td></tr><tr><td>1,000</td><td>61.9%</td></tr><tr><td>5,000</td><td>75.2%</td></tr><tr><td>10,000</td><td>81.0%</td></tr></tbody></table>
<p>One percent of the distinct queries covers 62% of the traffic.</p>
<p>Now price that. A 1,536-dimensional vector at 32-bit precision is 6,144 bytes, so a thousand entries is <strong>6.1 MB</strong> — a rounding error in any process's memory. Those 6 MB take the daily embedding calls from 200,000 to about 76,000.</p>
<p>Ten thousand entries costs 61 MB and covers 81%.</p>
<p>The returns flatten fast, which is the useful thing to know: past a certain point you are spending memory on queries that will be asked once. There is no reason to cache the tail.</p>

<h2 id="the-key-has-to-name-the-model"><a class="heading-anchor" href="#the-key-has-to-name-the-model">The key has to name the model</a></h2>
<p>The cache key is a hash of the text. It must also include the model's identity and version, and this is not a detail.</p>
<p>Two embedding models produce vectors in <em>different spaces</em>. The same sentence embedded by version 2 and version 3 gives two unrelated points; their similarity to each other means nothing. Distances are only meaningful between vectors made by the same model.</p>
<p>If the key is the text alone, then upgrading the model leaves you with a cache full of vectors from the old space, silently mixed with new ones. Nothing errors. Searches simply return worse results, and the cause is invisible because every individual vector looks fine.</p>
<p>Putting the model name and version in the key makes an upgrade behave correctly on its own: the new model's keys miss, get computed and stored, and the old entries age out. No migration step, no flag day.</p>
<p>Normalisation belongs in the key too. If the pipeline lowercases and collapses whitespace before embedding, hash the <em>normalised</em> text — otherwise three spellings of the same query occupy three entries and produce three identical vectors.</p>
<h2 id="getting-rid-of-things"><a class="heading-anchor" href="#getting-rid-of-things">Getting rid of things</a></h2>
<p>Two policies, doing different jobs.</p>
<p><strong>Least-recently-used</strong> answers "the cache is full, what goes?" It suits this workload exactly, because the traffic skew means recently-used entries are overwhelmingly likely to be used again.</p>
<p><strong>Time-to-live</strong> answers "how long may an entry live?" For a pure embedding cache the honest answer is <em>forever</em> — the function is deterministic, so an entry is never stale in the way a database row is. TTL is there for the things around it: bounding memory, letting a changed normalisation step wash through, and expiring keys after a model deprecation.</p>
<p>Do not set an aggressive TTL out of habit. Expiring a correct entry costs a model call and buys nothing.</p>
<h2 id="where-it-pays-besides-queries"><a class="heading-anchor" href="#where-it-pays-besides-queries">Where it pays besides queries</a></h2>
<p>The larger win is often on the ingestion side.</p>
<p>Re-processing a corpus of 50,000 chunks where 2% have changed means 1,000 chunks genuinely need embedding. Without a cache keyed on content, all 50,000 get recomputed, every time, because the pipeline has no way to know which ones changed.</p>
<p>With a content hash as the key, the unchanged 98% are hits. Re-ingestion goes from a scheduled expense to something you can run whenever a document is touched.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>An embedding cache is easy to build and easy to get subtly wrong.</p>
<p>Key it on the text <em>and</em> the model version, normalise before hashing, evict by recency, and size it for the head of the distribution rather than the whole corpus.
