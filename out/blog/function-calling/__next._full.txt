11:T2c82,<p>A language model predicts text. It has no network, no filesystem, no clock. Ask it how many units of a part are left in a warehouse and the best it can do is produce a plausible-looking number, because producing plausible text is the only thing it does.</p>
<p>Function calling closes that gap without changing what the model is.</p>
<h2 id="what-actually-happens"><a class="heading-anchor" href="#what-actually-happens">What actually happens</a></h2>
<p>You send the model a list of functions it may request. Each one is a name, a sentence describing when to use it, and a JSON Schema for its arguments:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="json" data-theme="github-dark-default"><code data-language="json" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#E6EDF3">{</span></span>
<span data-line=""><span style="color:#7EE787">  "name"</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">"check_stock"</span><span style="color:#E6EDF3">,</span></span>
<span data-line=""><span style="color:#7EE787">  "description"</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">"Current on-hand quantity for one part in one warehouse."</span><span style="color:#E6EDF3">,</span></span>
<span data-line=""><span style="color:#7EE787">  "parameters"</span><span style="color:#E6EDF3">: {</span></span>
<span data-line=""><span style="color:#7EE787">    "type"</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">"object"</span><span style="color:#E6EDF3">,</span></span>
<span data-line=""><span style="color:#7EE787">    "properties"</span><span style="color:#E6EDF3">: {</span></span>
<span data-line=""><span style="color:#7EE787">      "sku"</span><span style="color:#E6EDF3">: { </span><span style="color:#7EE787">"type"</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">"string"</span><span style="color:#E6EDF3"> },</span></span>

<span data-line=""><span style="color:#E6EDF3">  }</span></span>

<p>The user asks how many of part <code>BR-4471</code> are left in the southern warehouse. Instead of answering, the model emits:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="json" data-theme="github-dark-default"><code data-language="json" data-theme="github-dark-default" style="display: grid;"><span data-line=""><span style="color:#E6EDF3">{ </span><span style="color:#7EE787">"name"</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">"check_stock"</span><span style="color:#E6EDF3">, </span><span style="color:#7EE787">"arguments"</span><span style="color:#E6EDF3">: { </span><span style="color:#7EE787">"sku"</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">"BR-4471"</span><span style="color:#E6EDF3">, </span><span style="color:#7EE787">"warehouse"</span><span style="color:#E6EDF3">: </span><span style="color:#A5D6FF">"south"</span><span style="color:#E6EDF3"> } }</span></span></code></pre></figure>
<p>and stops.</p>
<p><strong>That is the whole trick.</strong> The model did not check anything. It produced text in a shape your code recognises. Your code runs the real lookup, gets <code>{"quantity": 62}</code>, appends that to the conversation, and asks the model to continue. Now it can answer, because the fact is in its context — the same as any other text you put there.</p>
<h2 id="the-line-this-draws"><a class="heading-anchor" href="#the-line-this-draws">The line this draws</a></h2>
<p>The model proposes; the application disposes. Nothing the model emits reaches the outside world unless code you wrote decides to run it.</p>
<p>This is not a courtesy. It is the only reason function calling is usable in a system that touches real data. The model's output is <em>a request from an untrusted party</em>, and it deserves the treatment any such request gets:</p>
<ul>
<li><strong>Validate the shape.</strong> Does it match the schema? Is <code>warehouse</code> one of the three allowed values?</li>
<li><strong>Authorise separately.</strong> A well-formed <code>issue_refund</code> call is still not permission to issue a refund. The schema proves the request is well-typed, never that it is allowed.</li>
<li><strong>Assume it can be steered.</strong> If the model read a document earlier in the conversation, the text of that document influenced what it proposes now. A tool call is downstream of everything the model has read.</li>
</ul>
<p>The most common mistake is treating a schema-valid call as an approved one. Those are different questions, and only one of them the model can answer.</p>

<h2 id="loops-and-rounds"><a class="heading-anchor" href="#loops-and-rounds">Loops and rounds</a></h2>
<p>Some work needs several calls. Look up an order, then look up the customer on that order, then check their refund history. Each step needs the previous step's answer, so each one is a full round trip: model, tool, model again.</p>
<p>At roughly 1.2 s per model turn and 0.3 s per tool, four dependent calls take about 7.2 seconds.</p>
<p>Other work does not have that dependency. Checking the same part across four warehouses needs four lookups that know nothing about each other. Here the model can emit all four requests in one response, your code runs them together, and all four results come back in one message — about 2.7 seconds, or 2.7× faster.</p>
<p>Being able to tell these apart is most of the performance work in a tool-using system. The question is always: does this call need an earlier call's <em>answer</em>, or just its own arguments?</p>
<h2 id="what-the-tools-cost-you"><a class="heading-anchor" href="#what-the-tools-cost-you">What the tools cost you</a></h2>
<p>The schemas are part of the prompt. Twelve tools at roughly 180 tokens of schema each is a 2,160-token block sitting in front of every request in the conversation — 10,800 tokens across a five-turn loop.</p>
<p>That is the direct cost, and it is the smaller one. The real cost is that choosing correctly gets harder as the list grows. Twelve tools with overlapping descriptions produce wrong choices in a way four crisp ones do not.</p>
<p>Description quality matters more than tool count. <code>Current on-hand quantity for one part in one warehouse</code> tells the model when <em>not</em> to use it. <code>Gets stock info</code> does not.</p>
<h2 id="the-relationship-to-structured-output"><a class="heading-anchor" href="#the-relationship-to-structured-output">The relationship to structured output</a></h2>
<p>Function calling and plain JSON output are the same mechanism used for different purposes.</p>
<p>Both constrain the model to emit text matching a schema. The difference is what happens next: structured output is the answer, and you parse it. A function call is a <em>request</em>, and you act on it and come back.</p>
<p>Which is why the same reliability tricks apply to both — keep schemas small, use enums instead of free strings wherever the set is known, and mark required fields required. Every constraint you express in the schema is one the model cannot violate, rather than one you have to catch afterwards.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>Function calling does not give the model abilities. It gives it a vocabulary for asking.</p>
