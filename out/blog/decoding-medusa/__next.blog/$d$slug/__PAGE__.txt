5:T2449,<p>Generating a token requires one pass over the whole model, and that pass is dominated by moving weights out of memory rather than by arithmetic. The GPU does a small amount of work and waits.</p>
<p>Which means: if you could <em>check</em> several proposed tokens in the same pass, the extra checking would be nearly free. That is the idea behind every method in this family. Medusa's contribution is where the proposals come from.</p>
<h2 id="the-problem-with-a-separate-drafter"><a class="heading-anchor" href="#the-problem-with-a-separate-drafter">The problem with a separate drafter</a></h2>
<p>The established approach uses a small draft model to propose tokens and the large model to verify them. It works, and it costs:</p>

















<table><thead><tr><th></th><th>memory</th></tr></thead><tbody><tr><td>a 1B draft model beside a 7B target</td><td><strong>2.0 GB</strong></td></tr><tr><td>four extra heads on the target itself</td><td>134 MB</td></tr></tbody></table>
<p><strong>15× less</strong> — and memory is the binding constraint on how many requests a serving GPU can hold.</p>
<p>The other costs are not measured in bytes. A separate model has to be chosen, trained, versioned and deployed alongside the target, and it has to stay behaviourally close to it — a drafter that drifts proposes tokens that get rejected, and a rejected proposal is wasted work.</p>
<h2 id="heads-instead"><a class="heading-anchor" href="#heads-instead">Heads instead</a></h2>
<p>Medusa attaches small heads to the frozen base model, reading the same final hidden state.</p>
<p>The original head predicts the next token, as always. Head 1 predicts the token <em>after</em> that. Head 2 predicts the one after that. All of them read the same hidden state produced by the same forward pass, so the proposals cost almost nothing beyond a small matrix multiply each.</p>
<p>Each head is one transform at hidden size — reusing the base model's vocabulary projection, which is why it is 33 MB rather than 262 MB.</p>
<p>Nothing about the base model changes. The heads are trained on top of it, and the tokens they propose still have to be approved by the base model's own distribution, so the output is what the base model would have produced.</p>
<h2 id="the-acceptance-chain-and-why-four-heads"><a class="heading-anchor" href="#the-acceptance-chain-and-why-four-heads">The acceptance chain, and why four heads</a></h2>
<p>Here is the arithmetic that decides how many heads are worth adding.</p>
<p>A proposal is accepted only if every proposal before it was. So the contributions multiply, and each head's realistic accept rate is lower than the last because it is predicting further ahead:</p>





















































<table><thead><tr><th></th><th>accept rate</th><th>chained</th><th>running total</th></tr></thead><tbody><tr><td>base head</td><td>always</td><td>1.000</td><td>1.000</td></tr><tr><td>head 1</td><td>0.72</td><td>0.720</td><td>1.720</td></tr><tr><td>head 2</td><td>0.55</td><td>0.396</td><td>2.116</td></tr><tr><td>head 3</td><td>0.40</td><td>0.158</td><td>2.274</td></tr><tr><td>head 4</td><td>0.28</td><td><strong>0.044</strong></td><td><strong>2.319</strong></td></tr><tr><td>head 5</td><td>0.19</td><td>0.008</td><td>2.327</td></tr><tr><td>head 6</td><td>0.12</td><td><strong>0.001</strong></td><td>2.328</td></tr></tbody></table>
<p>Four heads yield <strong>2.32 tokens per forward pass</strong> — a 2.32× speedup, which matches the published range of roughly 2 to 3×.</p>
<p>And the reason head counts stop around four or five is right there in the column. The fourth head adds 0.044 tokens. The sixth adds 0.001. Each additional head costs memory and training and contributes the <em>product</em> of every accept rate before it, which collapses quickly.</p>

<h2 id="checking-many-guesses-in-one-pass"><a class="heading-anchor" href="#checking-many-guesses-in-one-pass">Checking many guesses in one pass</a></h2>
<p>Each head produces a distribution, not a single token. Taking the top two from each gives 2⁴ = 16 possible four-token continuations.</p>
<p>Verifying those separately would be sixteen forward passes, which defeats the purpose. Instead the candidates are arranged as a <strong>tree</strong> — shared prefixes share nodes — and the whole tree goes through the model in one pass, with an attention mask that lets each node see only its own ancestors.</p>





















<table><thead><tr><th></th><th></th></tr></thead><tbody><tr><td>distinct four-token paths</td><td>16</td></tr><tr><td>positions in the tree</td><td>~30</td></tr><tr><td>forward passes to verify them all</td><td><strong>1</strong></td></tr></tbody></table>
<p>Thirty positions in one pass, against one position per pass in ordinary generation. Since the pass was memory-bound anyway, processing thirty positions instead of one costs very little extra — and one of those sixteen paths is likely to be partly correct.</p>
<p>The mask is what makes this work. Without it, the candidates would attend to each other and the verification would be meaningless.</p>
<h2 id="what-it-left-behind"><a class="heading-anchor" href="#what-it-left-behind">What it left behind</a></h2>
<p>Medusa's specific arrangement was superseded quickly, and the ideas were not.</p>
<p><strong>Proposals should come from the model already running.</strong> A second model is memory and drift; extra heads are neither.</p>
<p><strong>Verification should be a tree, not a line.</strong> Checking one guessed sequence wastes the pass if the first token is wrong; checking a branching set of them does not.</p>
<p><strong>Predicting several tokens ahead is a training objective, not only an inference trick.</strong> Training a model to predict more than one position turns out to help the model itself, not just the decoder attached to it — which is why the idea now shows up during pretraining rather than as an attachment afterwards.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>The speedup is one number: average tokens accepted per forward pass. Everything in the method exists to raise it, and everything about the method's limits comes from the fact that it is a <strong>product</strong> of accept rates rather than a sum.</p>
