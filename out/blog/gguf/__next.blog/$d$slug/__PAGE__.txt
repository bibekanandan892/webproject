4:T2438,<p>GGUF is a file format for a trained model. One file contains the weights, the tokenizer, and the metadata describing how to run the thing — architecture, layer counts, context length, special token ids.</p>
<p>That "one file" is the whole design goal, and the two decisions that follow from it are the interesting part.</p>
<h2 id="what-running-a-model-locally-needs"><a class="heading-anchor" href="#what-running-a-model-locally-needs">What running a model locally needs</a></h2>
<p>A model is a large collection of numbers arranged into named tensors. To run it you also need to know how those tensors connect, how text becomes token ids, and which ids mean <em>stop</em>.</p>
<p>Split that across a weights file, a tokenizer file and a couple of config files and every one of them can drift out of step with the others. A tokenizer from a slightly different revision produces ids the weights were never trained on — and nothing crashes. The model just answers slightly wrong, forever.</p>
<p>GGUF keeps them together because they are not separable in practice. The file starts with the four bytes <code>GGUF</code>, then a table of key–value metadata, then the tensor data. A reader can learn everything about the model from the header before touching a single weight.</p>
<h2 id="why-4-bit-is-really-45-bit"><a class="heading-anchor" href="#why-4-bit-is-really-45-bit">Why 4-bit is really 4.5-bit</a></h2>
<p>Weights are trained at 16 bits each. A 7-billion-weight model is therefore 14 GB, which is more memory than most laptops will give a single process.</p>
<p>Quantization stores each weight in fewer bits. The naive version — pick one scale for the whole tensor, divide, round to the nearest of 16 levels — does not work, and it is worth seeing how badly.</p>
<p>Taking 32,768 weights drawn to look like a real tensor, mostly small with a scattering of large values:</p>

















<table><thead><tr><th></th><th>error, as a share of the weights' own size</th></tr></thead><tbody><tr><td>one scale for the whole tensor</td><td>55.3%</td></tr><tr><td>one scale per block of 32</td><td>9.9%</td></tr></tbody></table>
<p>A single outlier stretches the scale to cover its own magnitude, and every ordinary weight then rounds to the same couple of levels. Almost all the information is gone.</p>
<p>The fix is to quantize in small <strong>blocks</strong>. Thirty-two weights share one scale, so an outlier only ruins its own block. The error drops 5.6×.</p>
<p>That scale has to be stored. A block of 32 costs 16 bytes of 4-bit values plus a 2-byte scale — 18 bytes, or <strong>4.5 bits per weight</strong>:</p>

























<table><thead><tr><th></th><th>bits/weight</th><th>7B model</th></tr></thead><tbody><tr><td>fp16</td><td>16.00</td><td>14.00 GB</td></tr><tr><td>Q8_0</td><td>8.50</td><td>7.44 GB</td></tr><tr><td>Q4_0</td><td>4.50</td><td>3.94 GB</td></tr></tbody></table>
<p>So a "4-bit" model is 3.56× smaller than fp16, not 4×. The missing half-bit is the scale, and it is the reason the format works at all.</p>

<h2 id="reading-the-names"><a class="heading-anchor" href="#reading-the-names">Reading the names</a></h2>
<p>A file marked <code>Q4_K_M</code> decodes as four separate choices:</p>
<ul>
<li><strong>Q</strong> — quantized, as opposed to full precision</li>
<li><strong>4</strong> — the nominal bits per weight</li>
<li><strong>K</strong> — the k-quant family, which stores scales in a smarter two-level arrangement rather than one flat scale per block</li>
<li><strong>M</strong> — the medium variant, meaning some tensors are kept at higher precision than others</li>
</ul>
<p>That last letter matters more than it looks. Not all tensors tolerate quantization equally — attention projections and embeddings are more sensitive than the bulk feed-forward weights. The S/M/L variants are different answers to which tensors get spent on.</p>
<h2 id="why-loading-is-instant"><a class="heading-anchor" href="#why-loading-is-instant">Why loading is instant</a></h2>
<p>A GGUF file stores tensor data in exactly the layout the runtime uses, aligned, with no per-tensor decoding step.</p>
<p>So the runtime does not read the file. It calls <code>mmap</code> and asks the operating system to make the file <em>appear</em> at an address. Nothing is copied. The header is parsed, the tensor pointers are computed as offsets into that mapping, and the model is ready.</p>
<p>The pages arrive from disk when they are first touched, which is why a 4 GB model can start answering before 4 GB has been read. It also means the memory is file-backed and clean: under pressure the OS can drop those pages and re-read them later, rather than swapping. And two processes running the same model share one copy of the pages, because they are mapping the same file.</p>
<p>None of this is possible if the weights need to be decompressed or rearranged on load. The layout <em>is</em> the feature.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>GGUF is unglamorous on purpose. A header, some key–value metadata, and tensor bytes arranged the way the runtime wants them.</p>
<p>What it gets right is that a model is not just weights — and that a "4-bit" model only works because it is not really 4
