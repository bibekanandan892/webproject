4:T2034,<p>A model's context window is a fixed number of tokens. Everything it can see — instructions, the conversation so far, the current message — has to fit inside it.</p>
<p>A conversation only grows. So eventually it does not fit, and something has to go.</p>
<h2 id="the-budget-concretely"><a class="heading-anchor" href="#the-budget-concretely">The budget, concretely</a></h2>
<p>A 200,000-token window is not 200,000 tokens of conversation. Space has to be reserved:</p>

























<table><thead><tr><th></th><th>tokens</th></tr></thead><tbody><tr><td>window</td><td>200,000</td></tr><tr><td>system instructions and tool definitions</td><td>−8,000</td></tr><tr><td>room for the reply</td><td>−24,000</td></tr><tr><td><strong>available for history</strong></td><td><strong>168,000</strong></td></tr></tbody></table>
<p>At roughly 1,400 tokens per exchange, that is about <strong>120 turns</strong>. Plenty for a chat, and not much at all for an agent that reads files and command output, where a single turn can be ten times that.</p>
<h2 id="why-deleting-is-wrong"><a class="heading-anchor" href="#why-deleting-is-wrong">Why deleting is wrong</a></h2>
<p>The simplest response is to drop the oldest messages. It is cheap, it is exact, and it destroys the wrong thing.</p>
<p>What sits in the oldest messages is usually the most important content in the conversation: what the task is, what was decided, what constraint was agreed. What sits in the newest is a partial command output. Dropping by age removes the premises and keeps the working.</p>
<p>Compaction replaces old turns with a <em>summary</em> of them instead.</p>
<h2 id="what-it-buys"><a class="heading-anchor" href="#what-it-buys">What it buys</a></h2>
<p>Triggering at 75% full, keeping the recent portion verbatim and compressing the rest:</p>

























<table><thead><tr><th></th><th>tokens</th></tr></thead><tbody><tr><td>used when compaction triggers</td><td>126,000</td></tr><tr><td>kept verbatim (most recent)</td><td>36,000</td></tr><tr><td>summarised</td><td>90,000 → 8,000</td></tr><tr><td><strong>freed</strong></td><td><strong>82,000</strong></td></tr></tbody></table>
<p>That is 11.3× compression on the old portion, and 82,000 tokens is another 58 turns.</p>
<p>Two things are worth noticing. The compaction is itself a model call that reads 90,000 tokens — not free, and it happens while the user waits. And keeping the recent portion verbatim is not politeness; the last few turns are where the immediate work is, and a summary of them would break the thread of whatever is in progress.</p>
<h2 id="the-loss-compounds"><a class="heading-anchor" href="#the-loss-compounds">The loss compounds</a></h2>
<p>Here is the part that matters and gets skipped.</p>
<p>A long session compacts repeatedly. The second compaction summarises a region that already contains the first summary. The third summarises the second. A fact from the opening turns has now been through a summariser several times.</p>
<p>If each pass retains 90% of the specifics in what it is given:</p>





























<table><thead><tr><th>compactions</th><th>original detail surviving</th></tr></thead><tbody><tr><td>1</td><td>90.0%</td></tr><tr><td>2</td><td>81.0%</td></tr><tr><td>4</td><td>65.6%</td></tr><tr><td>8</td><td><strong>43.0%</strong></td></tr><tr><td>16</td><td>18.5%</td></tr></tbody></table>
<p>Ninety percent per pass sounds excellent. Eight passes later, most of the detail is gone — and it goes quietly. The summary is fluent and confident; it simply no longer contains the version number that was agreed in turn three.</p>

<h2 id="the-fix-that-follows"><a class="heading-anchor" href="#the-fix-that-follows">The fix that follows</a></h2>
<p>If the problem is repeated summarisation, the answer is to make the things that matter exempt from it.</p>
<p>Keep a small region of <strong>pinned facts</strong> outside the compactable history: the task as originally stated, decisions with their reasons, constraints, file paths and identifiers that have been established. Written once, carried forward verbatim, never passed to a summariser a second time. It survives at 100%, indefinitely, because it never decays.</p>
<p>Everything else — exploration, dead ends, command output, discussion that led somewhere already recorded — can be compacted freely, because losing 90% of it costs nothing.</p>
<p>This makes the summariser's job much easier to specify, too. Rather than "summarise this conversation", the instruction becomes <em>extract anything that a later step would need and that is not already pinned</em> — which is a smaller and far more answerable question than compressing prose in general.</p>
<h2 id="practical-details-that-bite"><a class="heading-anchor" href="#practical-details-that-bite">Practical details that bite</a></h2>
<p><strong>Compact before you have to, not when you are out of room.</strong> A compaction needs its own headroom to run, and triggering at 100% leaves none.</p>
<p><strong>Keep the recent portion untouched.</strong> Whatever is mid-flight must survive verbatim; a half-finished task summarised into a sentence cannot be resumed.</p>
<p><strong>Record that a compaction happened.</strong> A model asked about something it cannot find should be able to tell the difference between "that never happened" and "the detail was compacted away", and can only do so if the boundary is visible in the context.</p>
<p><strong>Never compact quoted source material.</strong> Code, data, an exact error message — these are exactly what summarisation ruins and exactly what later steps need verbatim. Drop them entirely and re-read them when needed; a re-read is cheap, a plausible paraphrase of a stack trace is worse than nothing.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>Compaction is the right answer to a full context window, and it is not free.</p>
<p>Its cost is not the model call. Its cost is that the same material gets summarised again and again, and detail leaves silently.
