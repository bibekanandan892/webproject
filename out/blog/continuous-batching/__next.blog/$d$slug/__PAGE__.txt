4:T2547,<p>A GPU serving one request at a time is mostly idle. The arithmetic for a single token uses a fraction of what the hardware can do, so requests are processed in batches — several at once, at almost the same cost as one.</p>
<p>The question is when a batch begins and ends, and the obvious answer is the expensive one.</p>
<h2 id="the-problem-with-fixed-batches"><a class="heading-anchor" href="#the-problem-with-fixed-batches">The problem with fixed batches</a></h2>
<p>Take a batch of four. Run all four together, one decode step at a time, until every one of them is done. Then start the next four.</p>
<p>The trouble is that requests are not the same length. One reply runs to fifteen tokens and another to two hundred and forty. The short one finishes at step fifteen and its slot then sits empty for two hundred and twenty-five steps, because the batch does not end until the longest request does.</p>
<p>Meanwhile new requests wait in a queue for a slot that is empty and unusable.</p>
<h2 id="refilling-as-you-go"><a class="heading-anchor" href="#refilling-as-you-go">Refilling as you go</a></h2>
<p>Continuous batching changes one thing: when a request finishes, its slot is given to the next queued request immediately, in the middle of the batch.</p>
<p>Nothing about the model changes. It is purely a decision about scheduling — the batch stops being a group of requests that start and end together, and becomes a set of slots that are kept full.</p>
<h2 id="what-that-is-worth"><a class="heading-anchor" href="#what-that-is-worth">What that is worth</a></h2>
<p>Twelve requests, four slots, and reply lengths of 240, 30, 90, 15, 60, 45, 20, 180, 25, 35, 120 and 40 decode steps. That is 900 steps of actual work.</p>

<p>Same requests, same model, same hardware. <strong>2.12× the throughput</strong>, from changing when a slot is refilled.</p>
<p>The utilisation figure is the honest way to see it. Under fixed batching the slots do useful work 42% of the time; the rest is waiting for stragglers. Continuous batching takes that to 88%, and the remaining gap is the tail — near the end there is not enough queued work left to keep four slots busy.</p>
<h2 id="what-it-does-to-individual-requests"><a class="heading-anchor" href="#what-it-does-to-individual-requests">What it does to individual requests</a></h2>
<p>Throughput is the headline, but the effect on waiting is larger and less obvious:</p>



































<table><thead><tr><th>reply length</th><th>finishes at, static</th><th>finishes at, continuous</th></tr></thead><tbody><tr><td>20 steps</td><td>260</td><td><strong>95</strong></td></tr><tr><td>45 steps</td><td>285</td><td><strong>75</strong></td></tr><tr><td>60 steps</td><td>300</td><td><strong>75</strong></td></tr><tr><td>25 steps</td><td>445</td><td><strong>115</strong></td></tr><tr><td>240 steps</td><td>240</td><td>240</td></tr></tbody></table>
<p>The short requests gain most. A twenty-step reply that was queued behind a batch finished at step 260 under fixed batching and at 95 under continuous — and almost all of that wait was queuing, not generating.</p>
<p>The longest request is unchanged. Nothing sped it up; it was never the one waiting.</p>
<h2 id="what-it-does-not-fix"><a class="heading-anchor" href="#what-it-does-not-fix">What it does not fix</a></h2>
<p>It is scheduling only. The model, the attention, the arithmetic per token are all identical — this is a change to when work is admitted, nothing more.</p>
<p>The batch size is still capped by memory. Every request in flight holds a KV cache proportional to its length, so the number of slots is limited by how much cache fits, and keeping slots full means holding more caches at once. Continuous batching increases memory pressure precisely because it succeeds at keeping the machine busy.</p>
<p>Which is why it is normally paired with a scheme that stops the cache being allocated in wasteful contiguous blocks. Better scheduling exposes the memory limit; the memory work is what raises it.</p>
<h2 id="the-short-version"><a class="heading-anchor" href="#the-short-version">The short version</a></h2>
<ul>
<li>Requests are batched because a GPU running one at a time is mostly idle.</li>
<li>With fixed batches, a slot stays empty from when its request finishes until the longest one in the batch does.</li>
<li>Continuous batching refills each slot the moment it empties.</li>
<li>On twelve mixed-length requests across four slots: 540 steps to 255, and 42% slot utilisation to 88%.</li>
<li>Short requests benefit most; the longest request is unaffected.</li>
<li>It changes scheduling only — no change to the model.</li>
<li>Keeping slots full raises memory pressure, which is why it pairs with better KV cache allocation.</li>
