4:T37b8,<p>A large language model does not produce a sentence in one go. It generates <strong>one token at a time</strong>, and each new token is predicted by looking at everything generated so far:</p>
<pre><code>The                ->  The train
The train          ->  The train was
The train was      ->  The train was late
</code></pre>
<p>Every step re-reads the whole sequence. That is where the waste comes from, and the KV cache is what removes it.</p>
<h2 id="q-k-and-v"><a class="heading-anchor" href="#q-k-and-v">Q, K and V</a></h2>
<p>Inside an attention layer, each token is turned into three vectors:</p>





















<table><thead><tr><th></th><th>what it is</th></tr></thead><tbody><tr><td><strong>Query (Q)</strong></td><td>what the current token is looking for</td></tr><tr><td><strong>Key (K)</strong></td><td>what each token has to offer</td></tr><tr><td><strong>Value (V)</strong></td><td>the actual information a token carries</td></tr></tbody></table>
<p>To produce the next token, the model takes the current token's Query, compares it against the Keys of every token in the sequence to get attention scores, and uses those scores to collect the matching Values.</p>
<p>So a single decoding step needs one Query, plus the Keys and Values of <strong>every</strong> token so far.</p>

<p>Step 2 recomputes the K and V for token 1, which it already computed in step 1. Step 3 recomputes tokens 1 and 2. Step 4 recomputes 1, 2 and 3. The work piles up quadratically, and every repeat produces exactly the same numbers as the time before.</p>

<h2 id="the-solution"><a class="heading-anchor" href="#the-solution">The solution</a></h2>
<p>The Keys and Values for a token never change. Once token 1 has been processed, its K and V are fixed — nothing generated later alters them.</p>
<p>So store them. Compute each token's K and V once, keep them in memory, and read them back on every later step. Each step then computes K and V for exactly one new token.</p>
<p>For the same 200-token sequence:</p>
<span class="katex-display"><span class="katex"><span class="katex-mathml"><math xmlns="http://www.w3.org/1998/Math/MathML" display="block"><semantics><mrow><mn>4</mn><mo>+</mo><mn>196</mn><mo>=</mo><mn>200</mn><mtext> K/V computations</mtext></mrow><annotation encoding="application/x-tex">4 + 196 = 200 \text{ K/V computations}</annotation></semantics></math></span><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.7278em;vertical-align:-0.0833em;"></span><span class="mord">4</span><span class="mspace" style="margin-right:0.2222em;"></span><span class="mbin">+</span><span class="mspace" style="margin-right:0.2222em;"></span></span><span class="base"><span class="strut" style="height:0.6444em;"></span><span class="mord">196</span><span class="mspace" style="margin-right:0.2778em;"></span><span class="mrel">=</span><span class="mspace" style="margin-right:0.2778em;"></span></span><span class="base"><span class="strut" style="height:1em;vertical-align:-0.25em;"></span><span class="mord">200</span><span class="mord text"><span class="mord"> K/V computations</span></span></span></span></span></span>
<p>20,094 down to 200 — about <strong>100 times fewer</strong>.</p>
<h2 id="why-only-k-and-v"><a class="heading-anchor" href="#why-only-k-and-v">Why only K and V</a></h2>
<p>The Query belongs only to the token being generated right now. Once that step is done it has served its purpose and is never needed again, so there is nothing to gain by keeping it.</p>
<p>Keys and Values are the opposite. Every token's K and V are needed at every future step, because each new Query has to be compared against all of them. They get reused for the rest of the sequence, which is exactly what makes them worth caching.</p>
<h2 id="the-trade-off"><a class="heading-anchor" href="#the-trade-off">The trade-off</a></h2>
<p>The cache buys speed with memory. Nothing is free: the K and V of every token sit in GPU memory for as long as the sequence is alive, and that grows linearly with sequence length.</p>
<p>For short sequences this is a clear win. For very long ones the cache itself becomes the constraint, which is why serving systems manage it — commonly by keeping only a sliding window of recent tokens plus the first few tokens, the attention sinks, which cannot be dropped without quality falling apart.</p>
<h2 id="summary"><a class="heading-anchor" href="#summary">Summary</a></h2>
<ul>
<li>LLMs generate one token at a time, and each step needs the K and V of every previous token.</li>
<li>Recomputing them every step is quadratic and entirely redundant — the values never change.</li>
<li>Caching K and V turns 20,094 computations into 200 for a 200-token sequence.</li>
<li>Q is not cached, because it is only ever used for the current token.</li>
<li>The cost is memory, which becomes the limiting factor on long sequences.</li>
