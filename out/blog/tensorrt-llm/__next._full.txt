12:T20cc,<p>A GPU runs <strong>kernels</strong> — small programs, each doing one piece of maths across thousands of parallel lanes. A forward pass through a language model is a long sequence of them.</p>
<p>TensorRT-LLM's premise is that a great deal of the time is spent not computing. It compiles a specific model into a fixed <strong>engine</strong> ahead of time, and that compilation is where the recovered time comes from.</p>
<h2 id="the-overhead-nobody-sees"><a class="heading-anchor" href="#the-overhead-nobody-sees">The overhead nobody sees</a></h2>
<p>Every kernel has to be launched by the CPU: parameters marshalled, the call submitted, the GPU notified. Around 5 microseconds each, and that is CPU time the GPU spends idle.</p>
<p>A decode step on a 32-layer model issues roughly a dozen kernels per layer:</p>

























<table><thead><tr><th></th><th></th></tr></thead><tbody><tr><td>kernels launched per token</td><td>384</td></tr><tr><td>CPU launch overhead at 5 µs each</td><td><strong>1.92 ms</strong></td></tr><tr><td>actual GPU work in the step</td><td>7 ms</td></tr><tr><td>overhead as a share of wall clock</td><td><strong>22%</strong></td></tr></tbody></table>
<p>A fifth of the time is spent asking for work rather than doing it.</p>
<p>The fix is to record the whole sequence once and replay it as a single submission. The kernels still run; the CPU stops re-describing them.</p>























<table><thead><tr><th></th><th>launches</th><th>overhead</th><th>tokens/sec</th></tr></thead><tbody><tr><td>launched individually</td><td>384</td><td>1.92 ms</td><td>112</td></tr><tr><td>replayed as one graph</td><td><strong>1</strong></td><td>0.005 ms</td><td><strong>143</strong></td></tr></tbody></table>
<p><strong>1.27× more throughput</strong> with no change whatsoever to the arithmetic.</p>
<p>And notice where it matters. The same 384 launches against a 70 ms prefill is <strong>2.7%</strong> — invisible. Launch overhead is a <em>decode</em> problem specifically, because a decode step is short and made of many tiny kernels. Which is a good illustration of why serving optimizations have to be aimed at one phase or the other.</p>

<h2 id="fusing-and-why-it-is-about-traffic"><a class="heading-anchor" href="#fusing-and-why-it-is-about-traffic">Fusing, and why it is about traffic</a></h2>
<p>Three elementwise operations in a row — scale, add a correction, apply a nonlinearity — as three separate kernels means three reads and three writes of the whole tensor.</p>
<p>For a 4,096 × 4,096 activation at 16 bits:</p>




















<table><thead><tr><th></th><th>memory moved</th><th>at 3 TB/s</th></tr></thead><tbody><tr><td>three separate kernels</td><td>201 MB</td><td>67 µs</td></tr><tr><td>one fused kernel</td><td><strong>67 MB</strong></td><td><strong>22 µs</strong></td></tr></tbody></table>
<p><strong>3× less traffic</strong>, because the intermediate values never leave the chip's fast registers. The arithmetic is identical; only the number of round trips changed.</p>
<p>This is the same principle as everything else in a memory-bound setting. The work was never the problem — the moving was.</p>
<h2 id="what-the-build-step-is-for"><a class="heading-anchor" href="#what-the-build-step-is-for">What the build step is for</a></h2>
<p>All of this requires knowing the shape of the computation in advance, which is what the compilation produces. Given a model, a precision, a maximum batch size and a maximum sequence length, the build chooses which kernels to fuse, selects implementations tuned for the specific GPU architecture, and lays out memory.</p>
<p>That is the trade at the centre of the tool. The engine is <strong>fixed</strong>:</p>
<ul>
<li>built for one model and one precision</li>
<li>built for a maximum batch and sequence length</li>
<li>built for one GPU architecture, not portable to another</li>
<li>a build takes tens of minutes</li>
</ul>
<p>Change any of those and you build again. Which is exactly why a more flexible runtime path exists alongside the compiled one — most teams want to change models more often than they want the last 20%.</p>
<h2 id="the-rest-briefly"><a class="heading-anchor" href="#the-rest-briefly">The rest, briefly</a></h2>
<p>The remaining features are the standard serving set, and they matter for the reasons they always do.</p>
<p><strong>Quantization</strong> cuts the bytes read per token, which is the dominant decode cost, and lets the narrow-precision units do the arithmetic.</p>
<p><strong>Paged attention cache</strong> hands out small fixed blocks instead of reserving for the longest possible answer, so memory that would have been stranded becomes batch slots.</p>
<p><strong>In-flight batching</strong> refills a finished slot at the next step rather than waiting for the slowest request in a group, keeping the batch full.</p>
<p><strong>Custom attention kernels</strong> keep intermediate attention values in fast on-chip memory rather than writing them out and reading them back.</p>
<p><strong>Speculative decoding</strong> verifies several proposed tokens in one pass, so the expensive weight read yields more than one token.</p>
<p><strong>Multi-GPU</strong> splits a model either sideways — every GPU holds part of every layer and they work on the same token together — or lengthways, with each GPU holding a range of layers and requests flowing through as a pipeline. The first reduces latency and needs fast interconnect; the second scales capacity and introduces pipeline bubbles.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>One idea runs through all of it: <strong>keep the GPU from waiting.</strong></p>
<p>Waiting for the CPU to launch the next kernel, waiting for values to come back from memory that never needed to leave, waiting for a batch slot that a finished request is still holding.
