11:T2139,<p>When an ordinary service fails, it usually says so. There is an exception, a stack trace, a non-200.</p>
<p>When an agent fails it typically returns a fluent, confident, wrong answer, and nothing anywhere reports a problem. The failure happened three steps earlier — a tool called with a bad argument, a result misread — and none of that is in the output.</p>
<p>Observability is recording those steps so that the question "why did it do that?" has an answer.</p>
<h2 id="spans-and-traces"><a class="heading-anchor" href="#spans-and-traces">Spans and traces</a></h2>
<p>A <strong>span</strong> is one operation: a model call, a tool call, a retrieval. It records what went in, what came out, how long it took, and what it cost.</p>
<p>A <strong>trace</strong> is one complete run, made of many spans. Spans nest, so a trace is a tree rather than a list — a subagent's spans sit inside the parent span that invoked it.</p>
<p>Above traces sits the <strong>session</strong>: everything one user did across several requests.</p>
<p>That hierarchy is what makes the difference between "the agent gave a bad answer" and "at span 4 the search tool was called with the date in the wrong format, returned nothing, and the model treated an empty result as no availability."</p>
<h2 id="what-has-to-be-in-a-span"><a class="heading-anchor" href="#what-has-to-be-in-a-span">What has to be in a span</a></h2>
<p>The temptation is to log that something happened. That is not enough — you need what it said.</p>
<p>For a <strong>model call</strong>: the full prompt, the full response, which model, the token counts, the cost. The prompt in particular, because when a model behaves oddly the reason is usually visible in what it was actually sent, and reconstructing that later from application code is guesswork.</p>
<p>For a <strong>tool call</strong>: which tool, the exact arguments, the exact result, and whether it errored.</p>
<p>Plus retries, anything read from or written to memory, and the final output.</p>
<h2 id="which-is-why-the-volume-is-a-problem"><a class="heading-anchor" href="#which-is-why-the-volume-is-a-problem">Which is why the volume is a problem</a></h2>
<p>A twelve-step run logging prompts and responses is roughly 6.4 KB a step — about 77 KB for the run.</p>

<p>That is <strong>77 times</strong> the data per request, and it is not padding — it is the prompts and responses, which are the parts you actually need.</p>
<h2 id="keeping-the-useful-eighth"><a class="heading-anchor" href="#keeping-the-useful-eighth">Keeping the useful eighth</a></h2>
<p>The answer is not to log less per span. It is to keep fewer runs, chosen deliberately.</p>
<p>Decide <em>after</em> a run completes whether to store it. Keep every failure, every run that was unusually slow or expensive, every one a user complained about — and a small random sample of the ordinary successes.</p>



































<table><thead><tr><th>failure rate</th><th>5% of successes kept</th><th>volume retained</th><th>failures kept</th></tr></thead><tbody><tr><td>2%</td><td>✓</td><td>6.9%</td><td>100%</td></tr><tr><td>5%</td><td>✓</td><td>9.8%</td><td>100%</td></tr><tr><td><strong>8%</strong></td><td>✓</td><td><strong>12.6%</strong></td><td><strong>100%</strong></td></tr><tr><td>15%</td><td>✓</td><td>19.3%</td><td>100%</td></tr></tbody></table>
<p>At an 8% failure rate that is 3.66 GB a day down to 0.46, with <strong>every failure still on disk</strong>. The sample of successes is what tells you what normal looks like, which you need in order to recognise abnormal.</p>
<p>Sampling before the run — the cheaper thing to implement — throws away failures at the same rate as successes, which defeats the point.</p>
<h2 id="why-this-is-not-ordinary-monitoring"><a class="heading-anchor" href="#why-this-is-not-ordinary-monitoring">Why this is not ordinary monitoring</a></h2>
<p><strong>Nothing crashes.</strong> Conventional monitoring watches for errors. An agent's characteristic failure produces no error at all, so error rate is close to useless as a health signal. Task success rate is the metric, and it cannot be computed from the trace alone — something has to judge whether the answer was right.</p>
<p><strong>The path changes every run.</strong> The same request twice produces different traces. Two runs cannot be diffed the way two identical code paths can, so comparison has to be statistical rather than per-run.</p>
<p><strong>Cost is a first-class signal.</strong> A run that succeeds but takes forty steps and two dollars is a problem that no traditional metric surfaces. Tokens, cost and step count belong on the dashboard beside latency.</p>
<h2 id="the-practical-bits"><a class="heading-anchor" href="#the-practical-bits">The practical bits</a></h2>
<p><strong>Instrument first.</strong> Adding tracing after something has gone wrong means the run you needed to see was not recorded.</p>
<p><strong>Mask before storing.</strong> Prompts contain whatever the user typed, and tool arguments contain whatever was looked up. Both routinely include personal data, and a trace store is a copy of all of it.</p>
<p><strong>Alert on drift, not just errors.</strong> Cost per task rising, step count rising, tool success rate falling — these move before anyone files a complaint.</p>
<p><strong>Keep old traces.</strong> Answering "when did this start?" needs history, and by the time the question is asked it is too late to begin collecting.</p>
<p>And note the boundary: this tells you <em>what the agent did</em>. Whether what it did was any good is a separate judgement, made on top of this data. Traces without that judgement are a very detailed record of unknown quality.</p>
<h2 id="the-short-version"><a class="heading-anchor" href="#the-short-version">The short version</a></h2>
<ul>
<li>Agents fail silently, so the answer alone cannot explain a failure.</li>
<li>A span is one operation; a trace is a full run; spans nest into a tree.</li>
<li>Spans must carry the actual prompts, responses, arguments and results — not just event names.</li>
<li>That makes agent tracing about 77× the volume of conventional request logging.</li>
<li>Sample after the fact: keep all failures plus a few percent of successes, and 12.6% of the data retains every failure.</li>
<li>Error rate is a weak signal because nothing errors; task success rate is the real one.</li>
<li>Traces change every run, so comparison is statistical.</li>
<li>Mask personal data before storing, and instrument before you need it.</li>
