11:T20e7,<p>The Open Knowledge Format is a standard for writing down what an organisation knows about its own data, as a folder of plain markdown files that any tool can read.</p>
<p>That description makes it sound like documentation, which undersells the specific problem it solves.</p>
<h2 id="recoverable-and-unrecoverable"><a class="heading-anchor" href="#recoverable-and-unrecoverable">Recoverable and unrecoverable</a></h2>
<p>Point an agent at a database and it can find out a great deal by looking. Given a <code>shipments</code> table it can read the schema, sample rows, and establish every column's type, which ones are nullable, roughly how many distinct values each holds. All eighteen columns, no help needed.</p>
<p>What it cannot establish, by any amount of querying:</p>
<ul>
<li>A <code>status</code> of <code>'H'</code> means held for manual review, and those rows must be excluded from any revenue figure.</li>
<li><code>delivered_at</code> is populated by a nightly job, so today's rows are legitimately null rather than missing.</li>
<li>There are two weight columns and the older one stopped being maintained in March.</li>
<li><code>region</code> uses internal zone codes, not the ones the reporting team uses.</li>
<li>A carrier correction can arrive weeks later and rewrite a completed row.</li>
</ul>
<p>None of those is visible in the data. A sample of <code>status</code> values yields <code>A</code>, <code>H</code>, <code>C</code>, <code>X</code> with plausible frequencies and no indication of what any of them means or which to exclude. The information exists only in a person.</p>

















<table><thead><tr><th>of 5 rules that change the answer</th><th></th></tr></thead><tbody><tr><td>inferable from the data with effort</td><td>1 (20%)</td></tr><tr><td>not inferable at any cost</td><td><strong>4 (80%)</strong></td></tr></tbody></table>
<p>That ratio is the whole argument. Most of what an agent needs is not discoverable, so "give the agent database access" does not get it there. It will produce a confident, well-formed, wrong number — and the wrongness will be invisible, because the query was valid and the rows were real.</p>

<h2 id="what-a-bundle-looks-like"><a class="heading-anchor" href="#what-a-bundle-looks-like">What a bundle looks like</a></h2>
<p>A folder of markdown files, arranged by what they describe:</p>
<pre><code>logistics/
├── index.md
├── tables/
│   ├── shipments.md
│   └── carriers.md
└── metrics/
    └── on-time-rate.md
</code></pre>
<p>Each file opens with frontmatter. Exactly one field is required — <code>type</code>, saying what kind of thing this file describes — with a handful of conventional optional ones: a title, a description, a pointer to the actual resource, tags, a timestamp.</p>
<p>One required field is a deliberate choice. A format that demanded a rigorous taxonomy would not get filled in; a format that demands almost nothing gets filled in, and partial knowledge written down beats complete knowledge that only exists in conversation.</p>
<p>Files link to each other with ordinary markdown links. A foreign key in <code>shipments</code> becomes a link to <code>carriers.md</code>, which turns the folder into a graph an agent can walk: read the table, notice it references another, follow it.</p>
<h2 id="why-markdown-and-why-in-the-repository"><a class="heading-anchor" href="#why-markdown-and-why-in-the-repository">Why markdown, and why in the repository</a></h2>
<p>Both halves of that matter.</p>
<p><strong>Plain text</strong> means no server to run, no schema migration, no client library. Any agent that can read a file can consume it, which is the entire point of calling it a format rather than a product.</p>
<p><strong>In version control, next to the code</strong> means the knowledge is reviewed in the same pull request as the change that invalidated it. This is the part that determines whether a knowledge base is trustworthy in a year. A wiki page drifts silently because nothing forces anyone to look at it. A file beside the migration that renamed the column shows up in the diff.</p>
<p>It also means the knowledge has a history. Why a rule exists is often more useful than the rule, and <code>git log</code> answers it for free.</p>
<h2 id="the-cost-of-not-having-it"><a class="heading-anchor" href="#the-cost-of-not-having-it">The cost of not having it</a></h2>
<p>For the one rule in five that <em>is</em> recoverable, discovery is slow. Six exploratory queries at roughly a second each, with a model turn between them, is about <strong>12.6 seconds</strong> before the agent can write the query it actually wanted — against 1.5 seconds to read one 900-token file. An 8.4× difference, repeated every session, since nothing learned this way persists.</p>
<p>For the other four, there is no amount of time that helps.</p>
<h2 id="where-it-sits-next-to-other-standards"><a class="heading-anchor" href="#where-it-sits-next-to-other-standards">Where it sits next to other standards</a></h2>
<p>Three different questions, easy to conflate:</p>
<ul>
<li><strong>What can the agent reach?</strong> — a connectivity protocol, which exposes tools and data sources.</li>
<li><strong>How should this be done?</strong> — a procedure or skill, which describes a workflow.</li>
<li><strong>What is this thing and what is true about it?</strong> — this format.</li>
</ul>
<p>An agent with connectivity and no knowledge can query anything and understand none of it. The three are complementary, and the knowledge layer is the one most often assumed to be unnecessary because the data is right there.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>The reason to write this down is not tidiness. It is that four fifths of the context an agent needs cannot be obtained by giving it access to the data.</p>
<p>Which makes the useful test for any candidate fact simple: <strong>could an agent work this out by looking?</strong> If yes, it probably does not need to be written.
