4:T2b10,<p>There are two ways to build something multi-step around a model. Give it tools and let it decide what to do next, over and over. Or lay out the steps yourself and let the model do the work inside each one.</p>
<p>The second is graph engineering: <strong>every step is a node, every possible transition is an edge, and a shared state object carries information between them.</strong> The model still does the thinking. The graph decides where that thinking goes.</p>
<h2 id="the-number-that-justifies-the-constraint"><a class="heading-anchor" href="#the-number-that-justifies-the-constraint">The number that justifies the constraint</a></h2>
<p>Take a document question-answering flow: understand the question, search, write an answer, check it. The check either accepts, sends it back to search because nothing was found, or sends it back to write because the answer was weak — with the cycle capped at three attempts.</p>
<p>How many distinct paths can a run take?</p>

























<table><thead><tr><th>cycle cap</th><th>distinct paths</th></tr></thead><tbody><tr><td>1</td><td>3</td></tr><tr><td>2</td><td>7</td></tr><tr><td>3</td><td><strong>15</strong></td></tr><tr><td>4</td><td>31</td></tr></tbody></table>
<p>Fifteen. Every one of them can be written down, walked through, and tested.</p>
<p>Now the same job as a free loop with six tools and a twelve-step budget:</p>

















<table><thead><tr><th></th><th>possible action sequences</th></tr></thead><tbody><tr><td>the graph</td><td><strong>15</strong></td></tr><tr><td>the loop</td><td><strong>2,610,000,000</strong></td></tr></tbody></table>
<p>Two and a half billion. Not "hard to test" — <strong>coverage is not a meaningful concept</strong> at that size. You can test the cases you thought of and you have no idea what fraction of the space that is.</p>
<p>That is the trade in its entirety. The graph gives up the ability to solve problems whose shape you did not anticipate, in exchange for a system whose behaviour is finite.</p>

<h2 id="the-three-pieces"><a class="heading-anchor" href="#the-three-pieces">The three pieces</a></h2>
<p><strong>A node</strong> is a function. It receives the state, does one thing, and returns the fields it changed. Small and single-purpose: <code>understand</code>, <code>search</code>, <code>write</code>, <code>check</code>.</p>
<p><strong>An edge</strong> says what runs next. A plain edge always goes to the same node; a <strong>conditional</strong> edge is a function that reads the state and returns a name.</p>
<p><strong>State</strong> is a shared object with a declared schema. It is the only channel between nodes — they never call each other — and designing it first is the advice that matters most, because a vague state schema is how nodes end up secretly depending on each other.</p>
<p>The best-practice list is short and all of it follows from these three:</p>
<ul>
<li><strong>Put decisions in code, not in a model call.</strong> A conditional edge reading <code>state["score"] >= 8</code> is deterministic and testable. Asking a model which node to run next reintroduces exactly the unpredictability the graph was for.</li>
<li><strong>Cap every cycle.</strong> A cycle without a counter is a loop with extra steps.</li>
<li><strong>Every path must terminate.</strong> Check this by walking the graph on paper, which is possible precisely because there are fifteen paths.</li>
<li><strong>Turn errors into branches.</strong> Catch the failure, write it into the state, and route on it. A crash ends the run; a state field routes to a recovery node.</li>
</ul>
<h2 id="what-being-testable-actually-buys"><a class="heading-anchor" href="#what-being-testable-actually-buys">What being testable actually buys</a></h2>
<p>Two concrete things.</p>
<p><strong>Faults localise immediately.</strong> When a seven-stage opaque loop produces a wrong answer, you have one transcript and seven candidates — bisecting it by re-running takes about three attempts, each of which may not reproduce. With per-node tests, the failing test names the node and costs nothing extra.</p>
<p><strong>Nodes can be tested without the model.</strong> <code>check</code> is a function from state to a score; feed it a fixed document and a fixed answer and assert the score. No model call, no non-determinism, runs in milliseconds. That is an ordinary unit test, which is not available for any part of a free loop.</p>
<h2 id="two-things-graphs-get-for-free"><a class="heading-anchor" href="#two-things-graphs-get-for-free">Two things graphs get for free</a></h2>
<p><strong>Parallel branches.</strong> If <code>search_docs</code> and <code>search_web</code> do not depend on each other, the graph knows that — they are both edges out of the same node — and can run them together. Two searches at 1.4 s and 2.1 s take 2.1 s instead of 3.5 s, a <strong>1.67×</strong> improvement for no change other than declaring the structure.</p>
<p><strong>Pausing.</strong> Because state and current position are both explicit, they can be written down. That is what makes a run resumable after a crash, and what makes a human-approval step possible: stop before the node that sends, save, return, and continue hours later in a different process.</p>
<h2 id="where-it-is-the-wrong-choice"><a class="heading-anchor" href="#where-it-is-the-wrong-choice">Where it is the wrong choice</a></h2>
<p><strong>Genuinely open-ended work.</strong> If you cannot enumerate the steps, you cannot draw the graph. Debugging an unfamiliar codebase has no fixed shape, and a graph would just be a loop with more ceremony.</p>
<p><strong>Trivial work.</strong> One model call does not need a node.</p>
<p><strong>Graphs that grew.</strong> Past a few dozen nodes the structure stops being something a person can hold, and the property that justified the constraint — that you can see all the paths — is gone. At that point it is a state machine that nobody understands, which is worse than either alternative.</p>
<h2 id="graph-or-loop"><a class="heading-anchor" href="#graph-or-loop">Graph or loop</a></h2>






























<table><thead><tr><th></th><th>loop</th><th>graph</th></tr></thead><tbody><tr><td>the path taken</td><td>varies per run</td><td>the same for the same inputs</td></tr><tr><td>testing</td><td>end to end only</td><td>node by node</td></tr><tr><td>the model's freedom</td><td>chooses every step</td><td>works inside steps you chose</td></tr><tr><td>suits</td><td>open-ended problems</td><td>processes you can name</td></tr></tbody></table>
<p>Neither is better. A refund workflow has a known shape and benefits enormously from being drawn; an investigation does not have one and cannot be.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>The choice is about whether you can name the steps.</p>
<p>If you can, a graph converts billions of possible sequences into fifteen, and that is what makes the system testable, resumable, and explainable to someone who has to sign off on it.
