4:T2258,<p>An embedding model turns a piece of text into a list of numbers positioned so that things meaning similar things land near each other. Search then becomes geometry: find the stored vectors closest to the query's vector.</p>
<p>A vector database is what makes that lookup fast enough to be useful.</p>
<h2 id="what-it-holds"><a class="heading-anchor" href="#what-it-holds">What it holds</a></h2>
<p>Three things per item.</p>
<p>The <strong>vector</strong> — what similarity is computed against. The <strong>original content</strong>, because a list of numbers is not something you can show anyone. And <strong>metadata</strong>: category, date, author, whatever you might want to filter by.</p>
<p>The metadata matters more than it sounds, because most real queries are not pure similarity. "Documents like this one, from this year, that this user may see" is a similarity search with constraints, and whether those constraints are applied before or after the search changes both the cost and the results. Filter first and the search is over a smaller set; search first and you may find that all your nearest neighbours were filtered out.</p>
<h2 id="measuring-closeness"><a class="heading-anchor" href="#measuring-closeness">Measuring closeness</a></h2>
<p>Three measures, and the choice is not arbitrary.</p>
<p><strong>Cosine similarity</strong> compares direction only, ignoring length. This is the usual choice for text, because a long document and a short one about the same subject should count as similar, and length otherwise dominates.</p>
<p><strong>Dot product</strong> combines direction and magnitude. Identical to cosine when the vectors are normalised to unit length — which most embedding models do, making this the cheaper way to compute the same thing.</p>
<p><strong>Euclidean distance</strong> is the straight-line gap. Natural where position genuinely means something rather than just direction.</p>
<p>For normalised vectors these all rank results the same way. The distinction only bites when magnitudes vary.</p>
<h2 id="why-exact-search-is-impossible-at-scale"><a class="heading-anchor" href="#why-exact-search-is-impossible-at-scale">Why exact search is impossible at scale</a></h2>
<p>Suppose 100 million vectors of 768 dimensions.</p>
<p>Comparing a query against all of them means reading all of them. That is a memory bandwidth problem before it is an arithmetic one:</p>

<p>Six seconds a query is not a search product. And note that the two fixes are independent — one reduces how many vectors are examined, the other reduces the bytes per vector — which is why they are almost always used together.</p>
<h2 id="examining-fewer"><a class="heading-anchor" href="#examining-fewer">Examining fewer</a></h2>
<p><strong>Clustering.</strong> Group the vectors and store a centre for each group. At query time, compare against the centres, pick the nearest few groups, and search only those. With 1,024 clusters and 8 probed, that is 0.78% of the data.</p>
<p><strong>Layered graphs.</strong> Build a graph connecting each vector to its near neighbours, with sparse upper layers for long jumps and a dense bottom layer for fine steps. A search enters at the top, travels in large hops toward the query's region, then descends for precision. This is the common default, because it holds high recall without needing the data to cluster cleanly.</p>
<p>Both skip most of the data. Both can therefore miss the true nearest neighbour — if it happened to sit in a cluster that was not probed, it is simply not found.</p>
<h2 id="making-each-vector-smaller"><a class="heading-anchor" href="#making-each-vector-smaller">Making each vector smaller</a></h2>
<p>Storing 768 float32 values is 3,072 bytes per vector, and 307 GB for a hundred million.</p>
<p>The blunt approach is fewer bits per number — int8 instead of float32 divides everything by four, and works better than it sounds because embedding comparisons are robust to that much rounding.</p>
<p>The aggressive approach splits each vector into chunks, builds a small codebook of representative chunks, and stores the index of the nearest codebook entry rather than the values. A 768-dimensional vector becomes 8 bytes.</p>





















<table><thead><tr><th></th><th>index size</th></tr></thead><tbody><tr><td>float32</td><td>307 GB</td></tr><tr><td>int8</td><td>76.8 GB</td></tr><tr><td>8-byte codes</td><td><strong>0.80 GB</strong></td></tr></tbody></table>
<p>384 times smaller. That is the difference between an index that needs a rack and one that fits in memory on a single machine, which is usually the difference that decides an architecture.</p>
<h2 id="what-you-give-up"><a class="heading-anchor" href="#what-you-give-up">What you give up</a></h2>
<p>All of this is approximate. The measure is <strong>recall</strong>: of the true ten nearest neighbours, how many were actually returned.</p>
<p>Brute force gives 100% and takes six seconds. Production settings typically sit around 95%, and each configuration knob — clusters probed, graph connectivity, compression level — trades recall for speed.</p>
<p>That trade is usually correct. Nine of the right ten in a millisecond beats all ten in six seconds for nearly every application, especially since the embedding is itself an approximation of meaning — an exact search over approximate coordinates is not exact in any sense the user cares about.</p>
<p>The exception is anywhere a missed match is expensive rather than merely disappointing. Deduplication, compliance checks, anything where a near-duplicate slipping through is the failure — those want the recall pushed high and the cost paid.</p>
<h2 id="the-short-version"><a class="heading-anchor" href="#the-short-version">The short version</a></h2>
<ul>
<li>Store vectors, the original content, and metadata to filter by.</li>
<li>Cosine for text, dot product when vectors are normalised, Euclidean where position means something.</li>
<li>Brute force over 100M × 768 float32 vectors reads 307 GB per query — about six seconds.</li>
<li>Two independent fixes: examine fewer vectors, and shrink each one.</li>
<li>Clustering or a layered graph cuts what is examined to under 1%.</li>
<li>Compression takes 3,072 bytes per vector down to 8, and the index from 307 GB to 0.80 GB.</li>
<li>Together: 0.13 ms instead of 6.14 s.</li>
<li>The result is approximate. Recall is the dial, ~95% is typical, and that is usually the right call.</li>
