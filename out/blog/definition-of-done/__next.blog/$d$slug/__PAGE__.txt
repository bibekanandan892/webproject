4:T2000,<p>A definition of done is two things: a goal, and a way to check the goal. The second half is the one that gets left out, and it is the one that decides whether a model can work on the task at all.</p>
<h2 id="exact-and-fuzzy"><a class="heading-anchor" href="#exact-and-fuzzy">Exact, and fuzzy</a></h2>
<p>Some definitions of done are mechanical:</p>
<ul>
<li><code>applyBulkDiscount(1000, 20)</code> returns <code>800</code></li>
<li>the project compiles with no errors</li>
<li>this query returns exactly these 14 rows</li>
<li>the reported bug no longer reproduces</li>
</ul>
<p>Each of those is a command with an exit code. No judgement involved, no disagreement possible.</p>
<p>Others are not:</p>
<ul>
<li>"build the sign-in flow"</li>
<li>"write a good summary"</li>
<li>"make this module more readable"</li>
<li>"design a clean structure for this"</li>
</ul>
<p>These are not vague because whoever wrote them was careless. They are genuinely underspecified — "build the sign-in flow" leaves open what happens when the network drops mid-request, how long a session lasts, what the error message says, and what counts as acceptable structure. Those decisions exist whether or not anyone wrote them down.</p>
<h2 id="why-the-checker-sets-a-ceiling"><a class="heading-anchor" href="#why-the-checker-sets-a-ceiling">Why the checker sets a ceiling</a></h2>
<p>Here is the part worth making precise.</p>
<p>A loop attempts the work, runs the checker, and stops when the checker passes. So what the loop produces is not "correct output" — it is <strong>whatever passes the checker</strong>. Those are the same thing only if the checker is perfect.</p>
<p>Say each attempt is genuinely correct 55% of the time, and some fraction of <em>wrong</em> attempts pass the checker anyway:</p>

































<table><thead><tr><th>wrong answers the checker lets through</th><th>output actually correct</th></tr></thead><tbody><tr><td>0%</td><td>100.0%</td></tr><tr><td>5%</td><td>96.1%</td></tr><tr><td>10%</td><td>92.4%</td></tr><tr><td>15%</td><td>89.1%</td></tr><tr><td>25%</td><td><strong>83.0%</strong></td></tr><tr><td>40%</td><td>75.3%</td></tr></tbody></table>
<p>That is a <strong>ceiling</strong>. More attempts do not raise it — they raise the chance of stopping, and the stopping condition is what is flawed. A loop with a 25% false-pass rate produces wrong output 17% of the time no matter how long it runs.</p>
<p>And the leverage sits entirely on the checker:</p>

















<table><thead><tr><th>change</th><th>resulting ceiling</th></tr></thead><tbody><tr><td>tighten the checker from 25% to 5% false passes</td><td>83.0% → <strong>96.1%</strong></td></tr><tr><td>improve the model from 55% to 75% per attempt, checker unchanged at 25%</td><td>83.0% → 92.3%</td></tr></tbody></table>
<p>Tightening the checker beats improving the model, and it is usually the cheaper of the two.</p>

<h2 id="what-the-checker-buys-besides-quality"><a class="heading-anchor" href="#what-the-checker-buys-besides-quality">What the checker buys besides quality</a></h2>
<p>It also decides who has to be present.</p>
<p>With a perfect checker and a 55% per-attempt success rate, four attempts reach 95.9%. The model runs those four attempts on its own, and a person looks at the result once.</p>
<p>Without a checker, every attempt needs a human to say whether it worked. Same four attempts, four reviews — and the person is now the slow part of a loop that was supposed to save their time.</p>
<p>That is the practical reason this matters more for agents than for chat. A single response gets read by a person anyway. A loop that is supposed to run unattended cannot run at all without something to tell it when to stop.</p>
<h2 id="moving-a-fuzzy-goal-toward-a-checkable-one"><a class="heading-anchor" href="#moving-a-fuzzy-goal-toward-a-checkable-one">Moving a fuzzy goal toward a checkable one</a></h2>
<p>The work is not writing the goal more forcefully. It is naming the decisions the goal left open.</p>
<p>"Make this module more readable" becomes:</p>
<ul>
<li>no function longer than 40 lines</li>
<li>no nesting deeper than three levels</li>
<li>every exported function has a doc comment</li>
<li>the existing test suite still passes</li>
<li>the public interface is unchanged</li>
</ul>
<p>None of those is <em>readability</em>. Together they capture enough of it to be checkable, and the residue — whether the naming is good, whether the structure makes sense to someone new — is the part that genuinely needs a person.</p>
<p>That split is the useful output of the exercise. You end up with a mechanical part a loop can grind on, and a small judgement-shaped part for review. Which is a much better division of labour than handing over the whole fuzzy thing and reviewing all of it.</p>
<h2 id="the-honest-limit"><a class="heading-anchor" href="#the-honest-limit">The honest limit</a></h2>
<p>Some work has no exact checker and never will. Is this design right for where the product is going. Is this abstraction one someone will understand in a year. Does this summary emphasise what the reader cares about.</p>
<p>For those, a model is a source of drafts and a person is the definition of done. That is a legitimate way to work and it is worth recognising as different — it does not become an unattended loop by being wrapped in one.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>Before handing work to a model, answer one question: <strong>what command tells me this is finished?</strong></p>
<p>If there is one, the loop can run itself, and the effort belongs in making that command strict — because the loop's ceiling is the checker's precision, and no amount of model improvement or extra attempts moves it.
