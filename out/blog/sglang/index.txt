11:T2426,<p>SGLang is a serving engine for language models. Its distinguishing idea is what it does with the work already done for other requests.</p>
<p>Reading a prompt is expensive — the model builds an internal state for every token before it can generate anything. If two requests begin with the same text, that state is identical for the shared part. SGLang's claim is that this happens constantly, in shapes nobody anticipated, and that finding it should be automatic.</p>
<h2 id="one-tree-for-everybody"><a class="heading-anchor" href="#one-tree-for-everybody">One tree for everybody</a></h2>
<p>Instead of each request owning its cache, SGLang keeps all of them in a single <strong>radix tree</strong> — a tree where each path from the root spells out a token sequence, and shared beginnings share nodes.</p>
<p>A new request walks down from the root as far as its tokens match. Everything matched is reuse: the state already exists and is pointed at, not recomputed. Where the tokens diverge, a new branch is created and only the divergent part is prefilled.</p>
<p>Nobody registers a prefix. The overlap is discovered by walking.</p>
<h2 id="why-nesting-is-the-point"><a class="heading-anchor" href="#why-nesting-is-the-point">Why nesting is the point</a></h2>
<p>Take an agent that reads two documents and asks four questions about each. Eight requests: all sharing a 900-token instruction block, split into two groups of four sharing a 600-token document, each ending in about 120 unique tokens.</p>





















<table><thead><tr><th></th><th>prompt tokens prefilled</th></tr></thead><tbody><tr><td>no sharing at all</td><td>12,960</td></tr><tr><td>sharing the instruction block only</td><td>6,660</td></tr><tr><td>radix tree, all levels</td><td><strong>3,060</strong></td></tr></tbody></table>
<p>The first saving is the obvious one — hoist the system prompt, get 1.95×. The second is the one you cannot get by hand: the <em>document</em> level is shared by four requests each, and that nested reuse is worth another 2.18× on top.</p>
<p>Together, 4.24× less prefill, and the deeper the branching the wider the gap. A conversation tree, a set of samples from one prompt, several tool calls over the same context — all of these are branch structures, and a tree handles them without anyone describing the shape in advance.</p>

<h2 id="eviction-on-a-tree"><a class="heading-anchor" href="#eviction-on-a-tree">Eviction on a tree</a></h2>
<p>The cache is finite, so entries have to go. On a tree the rule is not simply "drop the least recently used".</p>
<p>An internal node's state is a prerequisite for every node beneath it. Dropping it would invalidate the whole subtree, even if those children were used seconds ago. So eviction works from the <strong>leaves</strong> inward: only a node with no children can go, and an internal node becomes eligible only once its descendants have already been removed.</p>
<p>This falls out of recency naturally. A node with active children keeps being touched by their requests, so it stays warm without any special rule — the structure encodes the dependency that a flat cache would have to be told about.</p>
<h2 id="not-calling-the-model-when-the-answer-is-forced"><a class="heading-anchor" href="#not-calling-the-model-when-the-answer-is-forced">Not calling the model when the answer is forced</a></h2>
<p>The second idea has nothing to do with caching.</p>
<p>When output must match a format — a JSON object with known keys, say — most of what comes out is not a prediction at all. After an opening brace the next characters are a quote and a key name, and there is exactly one legal continuation. The model is being asked a question with one possible answer.</p>
<p>Constrained decoding tracks the format with a state machine and masks out every token the format forbids. The useful consequence is that when the machine has only one legal next token, it can be emitted directly — no forward pass.</p>
<p>For an object with four fixed keys, roughly 24 of 36 output tokens are structural:</p>

















<table><thead><tr><th></th><th>tokens</th></tr></thead><tbody><tr><td>forced by the format</td><td>24</td></tr><tr><td>genuinely predicted</td><td>12</td></tr></tbody></table>
<p>That is <strong>3× fewer forward passes</strong> for the same output, and it is free accuracy as well: a token the format forbids can no longer be generated, so malformed output stops being a failure mode rather than becoming a rarer one.</p>
<h2 id="the-front-end"><a class="heading-anchor" href="#the-front-end">The front end</a></h2>
<p>SGLang also ships a Python interface for writing multi-step generations — call the model, keep the result in a variable, branch on it, call again — where the steps are described in one place rather than assembled as separate requests.</p>
<p>This is not only ergonomics. Because the runtime can see the whole program, it knows which calls share a prefix and which branches can run in parallel, and it can schedule accordingly. A sequence of independent HTTP requests gives the server none of that information.</p>
<h2 id="where-it-earns-its-keep"><a class="heading-anchor" href="#where-it-earns-its-keep">Where it earns its keep</a></h2>
<p>The engine's advantage scales with overlap. Long shared system prompts, multi-turn chat, many questions over one document, several samples from one prompt, agent loops that re-send the same context — all high-overlap patterns.</p>
<p>A workload of unrelated one-off prompts has nothing to share, and the tree is then pure bookkeeping. That is the honest limit: the mechanism does not create reuse, it finds reuse that already exists.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>Two separate insights, both about not repeating work.</p>
<p>Keep every request's cache in one tree and shared prefixes are found rather than declared — including the nested ones no configuration would have described.
