4:T1e24,<p>Claude Code is a coding agent that runs in a terminal. It reads files, edits them, runs commands, and repeats until the job is done.</p>
<p>Stripped to its structure it is a loop with three phases: <strong>find out what is true, change something, prove the change worked.</strong> Everything interesting is in how the first and third are made possible.</p>
<h2 id="why-a-chat-window-is-not-enough"><a class="heading-anchor" href="#why-a-chat-window-is-not-enough">Why a chat window is not enough</a></h2>
<p>A model in a chat window can write excellent code and cannot do anything with it. You paste a file in, get a suggestion out, apply it yourself, run the tests yourself, and paste the failure back.</p>
<p>The model never sees the repository, never sees the test output unless you carry it across, and never finds out whether its suggestion worked. Every iteration costs a human round trip, and the human is doing the two things the model cannot: gathering context and verifying results.</p>
<p>Giving the model tools closes that loop. Six are enough for almost everything: read a file, search file contents, match filenames, edit a file, write a file, run a command.</p>
<p>That last one is the load-bearing one, and it is why this works at all.</p>
<h2 id="search-because-reading-is-impossible"><a class="heading-anchor" href="#search-because-reading-is-impossible">Search, because reading is impossible</a></h2>
<p>Take a repository of 4,200 files averaging 180 lines. At roughly 12 tokens a line that is <strong>9.07 million tokens</strong> — about 45 times what a large context window holds. A 200,000-token context fits 92 whole files, which is 2.2% of the project.</p>
<p>So reading the codebase is not an option, and neither is guessing which 2% to read.</p>
<p>Search is the answer, used as a funnel:</p>

















<table><thead><tr><th></th><th>tokens</th></tr></thead><tbody><tr><td>the whole repository</td><td>9,072,000</td></tr><tr><td>the 6 files that match a search</td><td>12,960</td></tr></tbody></table>
<p><strong>700× less</strong>, and the 6 files are the right ones because they were selected by content rather than by hope. The agent then reads only the relevant regions of those.</p>
<p>This is the difference between an agent that works on a real project and one that works on a toy. Not the quality of the edits — the ability to locate the code worth editing without drowning in the rest.</p>

<h2 id="verification-is-the-multiplier"><a class="heading-anchor" href="#verification-is-the-multiplier">Verification is the multiplier</a></h2>
<p>Here is the part that changes the arithmetic completely.</p>
<p>A blind pipeline of steps compounds against you: four steps at 55% each is 9.2%, because every failure passes silently onward. But an agent that can run the tests <em>finds out</em> when it was wrong, and can try again.</p>

























<table><thead><tr><th>attempts</th><th>success, at 55% per attempt</th></tr></thead><tbody><tr><td>1</td><td>55.0%</td></tr><tr><td>2</td><td>79.8%</td></tr><tr><td>3</td><td>90.9%</td></tr><tr><td>4</td><td><strong>95.9%</strong></td></tr></tbody></table>
<p>Same per-attempt accuracy, opposite direction. Four unverified steps at 55% gives 9.2%; four verified attempts at 55% gives 95.9%.</p>
<p>The entire difference is a check that produces a truthful signal. Which is why running the test suite is not a nicety at the end — it is the mechanism that makes a mediocre one-shot success rate into a reliable outcome.</p>
<p>It also explains what makes a task well suited to this kind of agent. The question is not "is it hard?" but <strong>"can the result be checked automatically?"</strong> A failing test, a type error, a script that exits non-zero — all of these close the loop. A change to visual layout, a judgement about naming, a refactor whose only measure is taste: these produce no signal, the loop cannot close, and the agent is back to one-shot accuracy.</p>
<h2 id="standing-instructions-and-permissions"><a class="heading-anchor" href="#standing-instructions-and-permissions">Standing instructions and permissions</a></h2>
<p>Two smaller pieces do a lot of work.</p>
<p>A <strong>project instruction file</strong> holds facts that would otherwise be rediscovered or guessed every session: the build command, the test command, conventions the code follows but does not state. It is context that is always loaded, which is worth spending tokens on precisely because it would take several tool calls to establish.</p>
<p><strong>Permissions</strong> exist because the same tool that runs the test suite can delete files. The gradations — ask before each action, allow edits but confirm commands, plan without acting — are ways of positioning a human at the point where a mistake would be expensive. The agent proposing an action and a person approving it are two separate events, and keeping them separate is the whole safety story.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>The model is the least distinctive part. What makes a coding agent useful is the loop around it.</p>
<p>Search, so that a nine-million-token repository becomes thirteen thousand relevant tokens.
