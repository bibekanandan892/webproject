12:T20d8,<p>Psychology divides thinking into two modes. <strong>System One</strong> is fast and automatic — recognising a face, reading a word, judging whether a sentence sounds angry. <strong>System Two</strong> is slow and deliberate — long division, planning a trip, weighing an argument.</p>
<p>Language models are built like System Two. They answer by writing, one token at a time, and can reason step by step on the page. That makes them extraordinarily general. It also means every answer, however small, is a piece of generated text.</p>
<p>A <strong>System One model</strong> is the other kind: given a situation, it returns a <em>decision</em> — one option from a fixed list, a score, a yes or no — together with a probability that it is right. No text is generated. The output has a type.</p>
<h2 id="the-problem-with-deciding-by-writing"><a class="heading-anchor" href="#the-problem-with-deciding-by-writing">The problem with deciding by writing</a></h2>
<p>A large share of what LLMs are used for in production is not writing at all. It is small decisions:</p>
<ul>
<li>Which of five queues should this ticket go to?</li>
<li>Is this message spam?</li>
<li>Does this transaction need review?</li>
<li>Which tool should the agent call next?</li>
</ul>
<p>Done with an LLM, each decision means building a prompt, generating a short answer, and parsing it. Three problems follow.</p>
<p><strong>Cost.</strong> A routing decision with a 600-token prompt and a 20-token answer on a 70B model is about <code>2 × 70e9 × 620 = 8.7 × 10¹³</code> operations. A 300M-parameter model that reads the same 600 tokens and outputs one probability per queue needs <code>2 × 3e8 × 600 = 3.6 × 10¹¹</code>. That is <strong>241×</strong> less arithmetic for the same decision, and it shows up directly in latency and cost when the decision runs millions of times a day.</p>
<p><strong>The answer might not be an answer.</strong> The LLM returns a string. It might be <code>"billing"</code>, or <code>"Billing"</code>, or <code>"billing_support"</code>, or <code>"I think this is a billing question"</code>, or the name of a queue that does not exist. Constrained decoding and output schemas reduce this; parsing code and retries absorb the rest. A typed model cannot do it at all: its output layer has exactly five positions, one per queue.</p>
<p><strong>The confidence is made up.</strong> Ask an LLM how sure it is and it will write a number — "confidence: 0.9" — but that number is generated text like everything else. It is not, in general, true that the answers it labels 0.9 are right 90% of the time.</p>
<h2 id="what-a-system-one-model-returns"><a class="heading-anchor" href="#what-a-system-one-model-returns">What a System One model returns</a></h2>
<p>Instead of text, the output is a typed structure:</p>

























<table><thead><tr><th>type</th><th>example</th><th>output</th></tr></thead><tbody><tr><td>choice</td><td>route a ticket</td><td>probabilities over a fixed list — billing 0.82, technical 0.11, …</td></tr><tr><td>score</td><td>rate urgency</td><td>a number in a fixed range, with an uncertainty</td></tr><tr><td>yes / no</td><td>needs human review?</td><td>one probability</td></tr></tbody></table>
<p>The list of options is part of the model's definition, not something the prompt asks it to respect. It can still be wrong — pick billing when the answer was technical — but it cannot answer with something outside the list.</p>

<h2 id="calibration-is-the-point"><a class="heading-anchor" href="#calibration-is-the-point">Calibration is the point</a></h2>
<p>A probability is useful only if it means what it says. A model is <em>calibrated</em> if, among all the decisions it makes with probability 0.8, about 80% are correct.</p>
<p>Calibration is what turns a model into a policy. With calibrated probabilities you can say: automate every decision above 0.95, send the rest to a person — and know in advance what error rate the automated share will have. You can tune the threshold to trade cost against mistakes, and the trade is predictable.</p>
<p>Classifiers trained with a proper loss, such as cross-entropy, tend to be reasonably calibrated on data like their training data, and can be corrected with a simple rescaling fitted on held-out examples. They must be re-checked when the incoming data drifts. Text "confidence" from an LLM has no such guarantee and usually needs exactly the same held-out measurement before it can be trusted for anything.</p>
<h2 id="where-it-works-and-where-it-does-not"><a class="heading-anchor" href="#where-it-works-and-where-it-does-not">Where it works and where it does not</a></h2>
<p><strong>Works:</strong> high-volume decisions with a fixed set of outcomes and plenty of labelled history. Routing, triage, moderation, fraud flags, intent detection, choosing the next tool from a fixed set.</p>
<p><strong>Does not:</strong> decisions where the options are not known in advance, where the answer needs explanation, or where the situation requires multi-step reasoning over new information. Those are System Two problems, and an LLM is the right tool.</p>
<p>The productive arrangement uses both. The System One model handles the confident majority instantly and cheaply. Anything it is unsure about — below the threshold — is escalated to an LLM that can reason about it, or to a human. The probability is what makes the hand-off possible.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>A System One model answers with a typed decision and a probability rather than generated text. For a five-way routing decision it uses about 241× less arithmetic than a 70B LLM, cannot answer outside the allowed options, and produces a probability that can be calibrated and used to set automation thresholds.</p>
