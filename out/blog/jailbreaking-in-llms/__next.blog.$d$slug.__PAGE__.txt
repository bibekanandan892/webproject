5:T20d5,<p>Models are trained to refuse certain requests — detailed instructions for serious harm, content that targets individuals, material the deployer has ruled out. A <strong>jailbreak</strong> is an input designed to get the model to comply anyway, by exploiting gaps between the behaviour it was trained on and the situations it can be put in.</p>
<p>It is related to, but different from, <strong>prompt injection</strong>. Prompt injection hides instructions in content the model reads — a web page, an email, a document — so that it acts against its user. Jailbreaking is usually the user themselves trying to get past the model's own limits. Both exploit the same fact: a language model's instructions and its data arrive as the same kind of text.</p>
<p>This post describes the categories at a high level and focuses on defence. It does not include working prompts.</p>
<h2 id="why-jailbreaks-work-at-all"><a class="heading-anchor" href="#why-jailbreaks-work-at-all">Why jailbreaks work at all</a></h2>
<p>Safety behaviour is learned, not hard-coded. During training, a model sees many examples of harmful requests and learns to decline them. Jailbreaks look for inputs that are unlike those examples while still carrying the harmful request:</p>
<ul>
<li><strong>Reframing</strong> the request as fiction, role-play, a hypothetical or a research exercise, so it no longer resembles the refused examples.</li>
<li><strong>Obfuscation</strong> — encodings, other languages, deliberate misspellings, or splitting a request into innocent-looking pieces.</li>
<li><strong>Many-shot pressure</strong> — filling a long context with fabricated examples of the model complying, so the pattern to continue is compliance.</li>
<li><strong>Gradual escalation</strong> across many turns, each step only slightly beyond the last.</li>
<li><strong>Optimised inputs</strong> — strings found by automated search that happen to shift the model's behaviour, often meaningless to a human reader.</li>
</ul>
<p>Each exploits generalisation: the model learned "refuse things that look like this", and the attack makes the request not look like this.</p>
<h2 id="the-attackers-advantage-retries"><a class="heading-anchor" href="#the-attackers-advantage-retries">The attacker's advantage: retries</a></h2>
<p>A jailbreak that works only occasionally is still a jailbreak, because the attacker can keep trying at almost no cost. If a technique succeeds with probability <em>p</em> per attempt, the chance of at least one success in <em>n</em> attempts is <code>1 − (1 − p)ⁿ</code>:</p>




















<table><thead><tr><th>per-attempt success</th><th>within 100 attempts</th><th>within 1,000 attempts</th></tr></thead><tbody><tr><td>2%</td><td><strong>86.7%</strong></td><td>~100%</td></tr><tr><td>0.5%</td><td>39.4%</td><td>99.3%</td></tr></tbody></table>
<p>A defence that blocks 98% of attempts sounds strong and, against a determined attacker, is close to useless. What matters is how hard it is to find <em>any</em> working input — and what happens when one is found.</p>
<h2 id="defence-in-depth"><a class="heading-anchor" href="#defence-in-depth">Defence in depth</a></h2>
<p>No single layer is reliable, so systems stack independent ones. If three layers each miss 10% of attempts and fail independently, the combined miss rate is <code>0.1³ =</code> <strong>0.1%</strong>. Independence is the key word: three filters built the same way fail on the same inputs, and give little more than one.</p>

<p>The layers commonly used:</p>
<p><strong>Model training.</strong> Safety training on diverse adversarial examples, including role-play, multi-turn and encoded variants, so that refusals generalise to unseen phrasings. Training the model to recognise <em>intent</em> rather than surface wording is what makes reframing attacks harder.</p>
<p><strong>Input classifiers.</strong> A separate, smaller model screens requests for harmful intent before they reach the main model. It can be updated quickly when new attack patterns appear.</p>
<p><strong>Output classifiers.</strong> A second check on what the model actually produced, catching harmful content regardless of how the request was phrased. Output checks are robust to obfuscated inputs because they judge the result.</p>
<p><strong>System design.</strong> Limit what the model can do — tools, data access, actions — to what the application needs. A jailbroken model with no dangerous capabilities can do little harm.</p>
<p><strong>Monitoring and rate limits.</strong> Repeated refused or flagged requests from one account are a signal. Since attackers rely on retries, making retries visible and costly removes their main advantage.</p>
<p><strong>Red-teaming.</strong> Deliberately attacking your own system — with people and automated tools — before release and continuously after, feeding what is found back into training and filters.</p>
<h2 id="for-application-builders"><a class="heading-anchor" href="#for-application-builders">For application builders</a></h2>
<ul>
<li>Do not rely on the system prompt alone to enforce policy; it is guidance to the model, not a security boundary.</li>
<li>Treat any content the model reads from outside sources as untrusted.</li>
<li>Add output-side checks for the specific harms your application could cause.</li>
<li>Log and review refusals and flagged outputs; they show what people are trying.</li>
<li>Assume some jailbreaks will succeed, and limit the damage a successful one can do.</li>
</ul>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>A jailbreak is an input that gets a model to do what its safety training was meant to prevent, usually by making a harmful request look unlike anything it learned to refuse. Because attackers can retry freely, a 2% success rate becomes 86.7% within 100 attempts, so per-attempt block rates are a weak measure of safety.</p>
<p>Defence is layered and diverse: robust safety training, input and output classifiers, minimal capabilities, monitoring of repeated attempts, and continuous red-teaming.
