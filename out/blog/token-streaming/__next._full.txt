11:T1d0d,<p>A language model does not compose an answer and then hand it over. It produces one token, appends it to what it has written so far, and produces the next. The answer exists as a growing prefix from the very first step.</p>
<p>Token streaming is the decision to send that prefix as it grows rather than waiting for the last token.</p>
<h2 id="what-the-waiting-actually-is"><a class="heading-anchor" href="#what-the-waiting-actually-is">What the waiting actually is</a></h2>
<p>Suppose the model needs 0.8 seconds before the first token appears — reading the prompt, filling its working state — and then produces about 45 tokens per second. A 600-token answer is finished 14.1 seconds after the request.</p>
<p>Without streaming the reader sees nothing for 14.1 seconds and then everything at once.</p>
<p>With streaming they see the first words at 0.8 seconds. The wait shrinks by 17.7×, and nothing about the model changed. The same tokens were produced at the same speed. Only the moment of sending moved.</p>
<h2 id="why-it-doesnt-feel-like-reading-a-slow-typewriter"><a class="heading-anchor" href="#why-it-doesnt-feel-like-reading-a-slow-typewriter">Why it doesn't feel like reading a slow typewriter</a></h2>
<p>The interesting part is what happens after the first token.</p>
<p>That 600-token answer is roughly 450 words. A person reading at a normal pace takes about 112 seconds to get through it. The model wrote it in 13.3.</p>
<p>So the text is arriving about 8 times faster than anyone can read it. After the opening moment the reader is permanently behind the stream, which means they never wait again — there is always more text on screen than they have got to.</p>
<p>This is the real reason streaming works so well here. It is not that people are patient about partial output. It is that generation comfortably outruns reading, so a partial answer behaves like a complete one.</p>
<p>The margin is not infinite. If generation dropped below about 5 words per second the reader would catch up and start waiting between words, and the effect would invert — a stall you can watch is worse than a wait you cannot.</p>
<h2 id="sending-it"><a class="heading-anchor" href="#sending-it">Sending it</a></h2>
<p>The transport does not need to be clever. The server has a sequence of small pieces to send over time and the client needs to receive them in order. That is what <strong>Server-Sent Events</strong> does.</p>
<p>The server answers with <code>Content-Type: text/event-stream</code> and then simply does not finish the response. It writes a line, flushes it, and keeps the connection open. Each event is a <code>data:</code> line followed by a blank line:</p>
<pre><code>data: {"delta":"Re"}

data: {"delta":"new"}

data: {"delta":" it"}

data: {"delta":" online."}

data: [DONE]
</code></pre>
<p>The blank line is the delimiter — it is how the client knows an event is complete rather than half-received. The final marker exists because the client otherwise cannot distinguish a finished answer from a connection that is merely quiet, and would sit there waiting or retrying.</p>

<h2 id="why-not-a-websocket"><a class="heading-anchor" href="#why-not-a-websocket">Why not a WebSocket</a></h2>
<p>A WebSocket gives you a two-way channel. Streaming an answer needs one direction: the server has tokens, the client displays them. The client has nothing to say until it asks a new question, and that is an ordinary request.</p>
<p>SSE is plain HTTP, so it passes through proxies, load balancers and CDNs without special handling, and the browser reconnects on its own. A WebSocket asks for a protocol upgrade and its own connection lifecycle in exchange for a direction you were not going to use.</p>
<p>If the client genuinely needs to interrupt mid-answer, that is a separate small request to cancel, not a reason to change the transport.</p>
<h2 id="the-failure-everyone-hits"><a class="heading-anchor" href="#the-failure-everyone-hits">The failure everyone hits</a></h2>
<p>Streaming breaks silently when something in the middle buffers.</p>
<p>A proxy, a compression layer or a server framework that collects the response before forwarding it will hold every token until the connection closes and then release them together. The server streams correctly, the client handles events correctly, and the user sees the whole answer appear at once after fourteen seconds.</p>
<p>Nothing errors. There is no failed request to find in a log. The check is to watch when bytes arrive, not whether they arrive — if the first byte and the last byte land at the same moment, something between the two ends is holding them.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>Streaming is not an optimisation of the model. It changes nothing about how the answer is produced.</p>
<p>It is a decision about when to send what already exists, and it is worth making because generation is much faster than reading.
