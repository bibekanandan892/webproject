4:T210d,<p>Nearest neighbour search is the question every vector database answers: given a query vector, which stored vectors are closest to it?</p>
<p>Done exactly, it means comparing the query against every stored vector. With a billion vectors of a thousand dimensions that is a trillion multiplications for one search — arithmetic no amount of hardware makes interactive.</p>
<p>Approximate search drops the guarantee. It usually returns the true nearest neighbours and occasionally misses one. What it buys for that is not a small improvement.</p>
<h2 id="the-measurement-that-matters"><a class="heading-anchor" href="#the-measurement-that-matters">The measurement that matters</a></h2>
<p>Here is the trade, measured rather than asserted. Forty thousand vectors in 32 dimensions, grouped into 256 clusters. A search examines only the clusters whose centres are closest to the query:</p>








































<table><thead><tr><th>clusters examined</th><th>data scanned</th><th>exact answer found</th></tr></thead><tbody><tr><td>1</td><td>0.47%</td><td>42.8%</td></tr><tr><td>2</td><td>0.94%</td><td>67.0%</td></tr><tr><td>4</td><td>1.83%</td><td>91.8%</td></tr><tr><td>8</td><td><strong>3.39%</strong></td><td><strong>99.8%</strong></td></tr><tr><td>16</td><td>6.93%</td><td>100.0%</td></tr><tr><td>32</td><td>13.46%</td><td>100.0%</td></tr></tbody></table>
<p>Scanning 3.4% of the data returns the exact nearest neighbour 99.8% of the time. That is a <strong>29× reduction in work for a 0.2% error rate</strong> — and note the shape of the curve. The first few clusters buy accuracy cheaply; past eight, the extra scanning buys nothing at all.</p>
<p>That knob is the entire interface of approximate search. Everything else is a question of how the candidate neighbourhoods get defined.</p>

<h2 id="why-the-obvious-structure-fails"><a class="heading-anchor" href="#why-the-obvious-structure-fails">Why the obvious structure fails</a></h2>
<p>The natural idea is to build a tree: split the space in half along one dimension, split each half again, and descend to the region containing the query. Logarithmic search, like a binary search.</p>
<p>It works beautifully in two or three dimensions and collapses in a hundred. The reason is worth seeing directly. Take random points and measure how much closer the nearest one is than the farthest:</p>





























<table><thead><tr><th>dimensions</th><th>(farthest − nearest) / nearest</th></tr></thead><tbody><tr><td>2</td><td>239.6</td></tr><tr><td>8</td><td>4.5</td></tr><tr><td>32</td><td>1.43</td></tr><tr><td>128</td><td>0.449</td></tr><tr><td>512</td><td>0.186</td></tr></tbody></table>
<p>In two dimensions the farthest point is 240 times further away than the nearest. In 512 dimensions it is 1.19 times further. Everything is roughly the same distance from everything else.</p>
<p>A tree prunes by proving that an entire region is too far to contain the answer. When the nearest and farthest points differ by 19%, almost no region can be ruled out — so the search visits nearly every branch and performs worse than simply scanning the list, having paid for the tree as well.</p>
<p>This is the single most important fact about high-dimensional search, and it rules out every method that works by carving space into boxes.</p>
<h2 id="what-works-instead"><a class="heading-anchor" href="#what-works-instead">What works instead</a></h2>
<p>Three families survive, and they survive by not trying to prove anything.</p>
<p><strong>Clustering (IVF).</strong> Group the vectors, keep one centre per group, and at query time examine only the nearest few groups. This is the method measured above. It is simple, its memory overhead is one centre per cluster, and its knob — how many groups to examine — maps directly onto the speed/accuracy curve. Its weakness is the boundary: a query sitting between two clusters may have its true neighbour in a cluster that was not examined, which is exactly what the 42.8% at one cluster reflects.</p>
<p><strong>Hashing (LSH).</strong> Use hash functions designed so that nearby vectors collide. Look up the query's bucket and compare only what is in it. Attractive because accuracy is tunable by using more hash tables, and unattractive for the same reason — more tables means more copies of the index.</p>
<p><strong>Graphs (HNSW).</strong> Build a graph where each vector links to some of its near neighbours, with a few long-range links layered on top. Search by starting somewhere and repeatedly walking to whichever neighbour is closer to the query, descending from the sparse long-range layer to the dense local one.</p>
<p>Graphs are what most systems use now, because the greedy walk never needs to rule a region out. It only needs each step to be an improvement, and "is this neighbour closer?" stays a meaningful question in any number of dimensions. The cost is memory for the links and a slow build — and the fact that deleting vectors from a graph is genuinely awkward, since the links that pointed at a removed node have to be repaired.</p>
<h2 id="choosing"><a class="heading-anchor" href="#choosing">Choosing</a></h2>
<p>The honest summary is short.</p>
<p>Graph-based indexes give the best speed at a given accuracy and cost the most memory. Clustering is cheap to build, cheap in memory, and good enough for very large collections where memory is the binding constraint — and it combines naturally with compressing the vectors themselves. Hashing is mostly of historical and theoretical interest now. Trees are for low-dimensional data, which embeddings are not.</p>
<p>And whichever is chosen, the parameter that decides the outcome is the same: how much of the data you are willing to look at. Measure the recall curve on your own vectors and read the flattening point off it. It will not be where the defaults put it.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>The word "approximate" undersells what is happening. This is not a degraded search.</p>
<p>At 3.4% of the work it returned the exact right answer in 998 cases out of 1,000.
