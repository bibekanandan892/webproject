11:T2177,<p>A language model has no memory. Each call is complete on its own: you send text, it returns text, and nothing carries over.</p>
<p>Anything that looks like memory is machinery built around it — something deciding what to write down, and what to place back in front of the model next time.</p>
<h2 id="what-it-buys-you"><a class="heading-anchor" href="#what-it-buys-you">What it buys you</a></h2>
<p>Without it, an agent cannot resolve a reference to anything that happened earlier.</p>
<p>A customer writes: <em>"I'm on the Studio plan and our exports keep failing at 4K."</em> The agent helps, and the session ends.</p>
<p>Three weeks later the same customer writes: <em>"It's happening again."</em></p>
<p>With no memory that sentence is unanswerable. There is no <em>it</em>. The agent has to ask what is happening again, which is exactly the question that makes a support tool feel broken.</p>
<p>With memory, two facts were kept — the plan tier and the recurring fault — and they are retrieved and placed in the prompt before the model ever sees the new message. The pronoun resolves.</p>
<h2 id="four-layers"><a class="heading-anchor" href="#four-layers">Four layers</a></h2>
<p>Memory is not one store. It is four, with different lifespans, and most confusion comes from putting something in the wrong one.</p>

<p>The <strong>context window</strong> is the only thing the model ever sees. Everything else exists to decide what goes into it.</p>
<p><strong>Short-term memory</strong> is the current session: the plan, the steps taken so far, intermediate results. It is thrown away when the session ends, and that is correct — almost none of it matters tomorrow.</p>
<p><strong>Long-term memory</strong> survives across sessions and is tied to a particular user. Stable facts, strong preferences, outcomes worth not repeating.</p>
<p><strong>External knowledge</strong> — documents, databases, APIs — is not memory at all. The agent reads it but does not own it, and it is the same for every user. Worth naming as a separate layer precisely because it is so often confused with the third one.</p>
<h2 id="four-operations"><a class="heading-anchor" href="#four-operations">Four operations</a></h2>
<p><strong>Write</strong> when something happens that will matter later. <strong>Read</strong> the small subset that is relevant to the message in hand, not everything stored. <strong>Update</strong> when a new fact contradicts an old one. <strong>Forget</strong> what has gone stale.</p>
<p>Update and forget are the two that get skipped, and skipping them is what makes a memory system get worse over time rather than better. A store that only ever appends will eventually hold two contradictory facts and retrieve whichever one the search happens to rank higher.</p>
<h2 id="what-one-turn-looks-like"><a class="heading-anchor" href="#what-one-turn-looks-like">What one turn looks like</a></h2>
<ol>
<li>The message arrives.</li>
<li>Search long-term memory for anything relevant to it.</li>
<li>Read the session state from short-term memory.</li>
<li>Build the prompt: instructions, retrieved facts, session state, message.</li>
<li>Run the model, letting it call tools as needed.</li>
<li>Write the session state back. If anything is worth keeping, write that to long-term memory too.</li>
<li>Reply.</li>
</ol>
<p>Steps 2 and 6 are the whole system. Everything else is the ordinary agent loop.</p>
<p>Notice that step 2 is a search. Once there are more stored facts than fit in a prompt, the question stops being "what do we know?" and becomes "what is worth including this time?" — and a memory system's quality is mostly the quality of that judgement.</p>
<h2 id="what-to-keep"><a class="heading-anchor" href="#what-to-keep">What to keep</a></h2>
<p>Keep stable facts: who the user is, what they work in, settled preferences. Keep decisions that constrain future work. Keep outcomes, particularly failures, so the same approach is not tried twice.</p>
<p>Drop the rest. Not every message needs storing — the conversation is already in the context window while it is happening. Acknowledgements and small talk carry nothing. Session scaffolding belongs in short-term memory and should die with the session.</p>
<p>The test is one question: will this be useful in a conversation next week? If not, it is noise, and noise in a memory store is not neutral — it competes with the useful entries at retrieval time.</p>
<h2 id="how-it-fails-quietly"><a class="heading-anchor" href="#how-it-fails-quietly">How it fails quietly</a></h2>
<p>Almost nothing here fails loudly. The agent does not crash; it just answers slightly wrong, and it is easy not to notice.</p>
<p><strong>The prompt overflows.</strong> Retrieved memories, session state and history together exceed the window, and something gets silently truncated — often the part that mattered.</p>
<p><strong>Retrieval misses.</strong> The fact is stored and simply is not found, because the search matched words rather than meaning. From the outside this is indistinguishable from never having stored it.</p>
<p><strong>A memory goes stale.</strong> The user changed roles a year ago and the agent still addresses the old one. Nothing contradicts it because nothing checked.</p>
<p><strong>The store bloats.</strong> Everything was kept, so retrieval returns plausible-looking irrelevant entries, and the useful ones rank below them.</p>
<p><strong>Memories cross users.</strong> The worst one, and the reason every entry should be scoped to a user ID at write time rather than filtered at read time.</p>
<p>Since none of these announce themselves, the only defence is to look: log what was retrieved on each turn, and read that log occasionally against what the agent actually said.</p>
<h2 id="the-short-version"><a class="heading-anchor" href="#the-short-version">The short version</a></h2>
<ul>
<li>Models are stateless; memory is entirely machinery built around them.</li>
<li>Four layers: context window, short-term session state, long-term per-user facts, and external knowledge that is not really memory.</li>
<li>Only the context window is visible to the model — everything else has to be fetched into it.</li>
<li>The operations are write, read, update and forget; skipping the last two makes the system decay.</li>
<li>Each turn retrieves relevant facts before the call and writes new ones after it.</li>
<li>Store what will matter next week, not what matters for the next minute.</li>
<li>The failures are silent, so retrieval has to be logged and checked.</li>
