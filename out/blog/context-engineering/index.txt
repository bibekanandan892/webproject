11:T2434,<p>A model has no memory and no access to anything you have not shown it. Every call, its entire world is the context window.</p>
<p>Context engineering is deciding what goes in there. Not the phrasing of one instruction — the whole thing: which documents, which examples, how much history, which tool definitions, in what order, and what to drop when it will not all fit.</p>
<h2 id="what-is-competing-for-the-space"><a class="heading-anchor" href="#what-is-competing-for-the-space">What is competing for the space</a></h2>
<p>Eight things, typically, and every one of them is optional in the sense that you chose to include it.</p>
<p>The <strong>system prompt</strong> — role, rules, output format. <strong>Examples</strong> of the input-output shape you want. <strong>Retrieved documents</strong>. <strong>Tool definitions</strong>, one per tool, each with its schema. <strong>Long-term memory</strong> about this user. The <strong>conversation history</strong>. The <strong>results of tools called this turn</strong>. And the <strong>current message</strong>.</p>
<p>They all come out of the same budget.</p>
<h2 id="it-really-is-a-budget"><a class="heading-anchor" href="#it-really-is-a-budget">It really is a budget</a></h2>
<p>Take a 32,000-token window and a reasonable allocation:</p>









































<table><thead><tr><th></th><th>tokens</th></tr></thead><tbody><tr><td>system prompt</td><td>800</td></tr><tr><td>tool definitions (eight tools)</td><td>1,600</td></tr><tr><td>examples</td><td>900</td></tr><tr><td>retrieved chunks</td><td>2,400</td></tr><tr><td>memory</td><td>300</td></tr><tr><td>tool results this turn</td><td>2,000</td></tr><tr><td>current message</td><td>200</td></tr><tr><td><strong>fixed subtotal</strong></td><td><strong>8,200</strong></td></tr></tbody></table>
<p>Comfortable. But only one component in that list grows, and it grows every turn.</p>

<p>Nothing here was set up badly. The same allocation that was comfortable at turn one no longer fits at turn forty, and something has to give.</p>
<p>The instinct is to trim retrieval, because it is the easiest thing to make smaller. That is usually the wrong choice — retrieval is the part carrying facts about the current question, while history is mostly exchanges nobody will refer to again. Summarising old turns and keeping the recent ones intact costs less than answering with fewer documents.</p>
<h2 id="order-matters-twice"><a class="heading-anchor" href="#order-matters-twice">Order matters twice</a></h2>
<p><strong>For the model.</strong> Attention does not treat all positions equally: material at the start and end of a long context gets used more reliably than material buried in the middle. So a rule that must be followed does not belong three thousand tokens deep between two retrieved chunks. Put instructions at the edges.</p>
<p><strong>For the cache.</strong> Most providers cache a prompt by its prefix — an identical opening span can be reused instead of reprocessed. That only works if the opening is byte-identical between calls, which means ordering from most stable to least: system prompt, then tools, then examples, then retrieval, then history, then the new message. Put anything that changes per call near the front and the cache never hits.</p>
<p>Those two considerations agree, which is convenient. Stable things are also the instructions you want read reliably.</p>
<h2 id="what-goes-wrong"><a class="heading-anchor" href="#what-goes-wrong">What goes wrong</a></h2>
<p><strong>Too much.</strong> More context is not better context. Padding the window with marginally relevant material makes the relevant material harder to find, and quality falls even though nothing is missing.</p>
<p><strong>Too little.</strong> The model cannot infer a policy it was never shown. It will answer anyway, plausibly.</p>
<p><strong>Buried.</strong> The right information is present, in the middle, and effectively ignored.</p>
<p><strong>Stale.</strong> A tool result from six turns ago that has since been superseded is still sitting there being read as current.</p>
<p><strong>Unstructured.</strong> One undifferentiated wall of text. Section headers cost a handful of tokens and make the boundaries unambiguous.</p>
<p><strong>Contradictory.</strong> The system prompt says one thing, a retrieved document says another, and nothing establishes which wins. The model picks, and not always the same way twice.</p>
<h2 id="how-to-work-on-it"><a class="heading-anchor" href="#how-to-work-on-it">How to work on it</a></h2>
<p>Give each component a token allowance and hold it to that, rather than letting retrieval and history expand until something breaks.</p>
<p>When output is wrong, <strong>log the exact context that produced it</strong> and read it before touching the prompt. Most failures blamed on the model turn out to be a missing document, a stale tool result, or an instruction that was present but buried.</p>
<p>Then treat that context as code: version it, diff it, and compare variants. It is the input that actually determines the output, so it deserves the same handling as anything else that does.</p>
<h2 id="the-short-version"><a class="heading-anchor" href="#the-short-version">The short version</a></h2>
<ul>
<li>The context window is everything the model knows about the task.</li>
<li>Eight or so components compete for one budget: system prompt, examples, retrieval, tools, memory, history, tool results, the message.</li>
<li>History is the only one that grows without bound, and it will eventually crowd out everything else.</li>
<li>When space runs short, compress history before cutting retrieval.</li>
<li>Put instructions at the start or end — the middle gets read least reliably.</li>
<li>Order from stable to fresh so the prefix cache can work.</li>
<li>When output is wrong, read the context that produced it before blaming the model.</li>
