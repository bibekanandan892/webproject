4:T2624,<p>Two ways to find a document, with complementary blind spots.</p>
<p><strong>Keyword search</strong> scores a document by which query words it contains, weighted by how rare those words are in the collection. It is exact. A part number, an error code, a person's name — it finds them because it is matching the literal string.</p>
<p>It also finds nothing when the document says the same thing in different words. Search for "card declined" and a page titled "payment rejected" does not appear at all. Not ranked low — absent.</p>
<p><strong>Vector search</strong> compares meaning, so it handles that case. It also fails in the opposite direction: asked for an exact identifier, it returns things that are <em>about</em> identifiers, because a rare token contributes little to an embedding built to capture overall meaning.</p>
<p>Neither is a superset of the other, so the answer is to run both. That part is easy. Merging the results is not.</p>
<h2 id="why-you-cannot-just-add-the-scores"><a class="heading-anchor" href="#why-you-cannot-just-add-the-scores">Why you cannot just add the scores</a></h2>
<p>Keyword scores are unbounded and query-dependent. The top score for one query might be 18.4, for another 3.2, for another 41.7 — it depends on how rare the words are and how long the documents are.</p>
<p>Cosine similarity is bounded in a narrow band, typically 0.7 to 0.9 for anything worth returning.</p>
<p>So "add them with weights" is not well defined. A weight that balances the two for one query over-weights the keyword side for the next. The usual patch is to normalise each list — map its best to 1 and worst to 0 — but that introduces a distortion of its own: the lowest-scoring document you retrieved gets exactly zero, whatever its actual score was, purely because it came last.</p>
<h2 id="fusing-ranks-instead"><a class="heading-anchor" href="#fusing-ranks-instead">Fusing ranks instead</a></h2>
<p><strong>Reciprocal rank fusion</strong> discards the scores and uses only positions. Each document gets <code>1 / (k + rank)</code> from every list it appears in, summed.</p>
<p>Take a query where the two searches disagree:</p>






























<table><thead><tr><th></th><th>keyword list</th><th>vector list</th></tr></thead><tbody><tr><td>1</td><td>D1 (18.4)</td><td>D3 (0.81)</td></tr><tr><td>2</td><td>D2 (12.1)</td><td>D7 (0.79)</td></tr><tr><td>3</td><td>D3 (9.6)</td><td>D2 (0.76)</td></tr><tr><td>4</td><td>D7 (4.2)</td><td>D9 (0.71)</td></tr></tbody></table>
<p>D1 is the keyword search's clear favourite — a score of 18.4 against the runner-up's 12.1 — and the vector search does not return it at all.</p>
<p>Fused with the standard constant:</p>





























<table><thead><tr><th></th><th>fused score</th></tr></thead><tbody><tr><td>D3</td><td>0.03227</td></tr><tr><td>D2</td><td>0.03200</td></tr><tr><td>D7</td><td>0.03175</td></tr><tr><td><strong>D1</strong></td><td><strong>0.01639</strong></td></tr><tr><td>D9</td><td>0.01563</td></tr></tbody></table>
<p>D1 drops to fourth. Its enormous keyword score bought it nothing, because <strong>appearing respectably in both lists beats topping one of them.</strong> That is the rule RRF encodes, and it is usually the behaviour you want: agreement between two independent methods is stronger evidence than enthusiasm from one.</p>
<h2 id="the-constant-is-not-a-detail"><a class="heading-anchor" href="#the-constant-is-not-a-detail">The constant is not a detail</a></h2>
<p>That <code>k</code> is doing more work than it looks. It sets how much the top of a list dominates the rest of it:</p>



































<table><thead><tr><th>k</th><th>rank 1</th><th>rank 2</th><th>gap</th></tr></thead><tbody><tr><td>0</td><td>1.00000</td><td>0.50000</td><td>100%</td></tr><tr><td>1</td><td>0.50000</td><td>0.33333</td><td>50%</td></tr><tr><td>10</td><td>0.09091</td><td>0.08333</td><td>9.1%</td></tr><tr><td>60</td><td>0.01639</td><td>0.01613</td><td><strong>1.6%</strong></td></tr></tbody></table>
<p>At k = 60, being first rather than second in a list is worth 1.6% — so ranks are nearly interchangeable and what matters is <em>how many lists you appear in</em>. At k = 0, being first is worth twice being second, and a single list's favourite can win outright.</p>
<p>Re-fuse the same two lists with k = 0 and the order changes: <strong>D3, D1, D2, D7</strong>. D1 climbs from fourth to second. Same data, same formula, different answer.</p>

<h2 id="choosing-between-the-two-methods"><a class="heading-anchor" href="#choosing-between-the-two-methods">Choosing between the two methods</a></h2>
<p><strong>Rank fusion</strong> needs no calibration, is immune to scale differences, and behaves sensibly on any query. Its cost is that it throws away magnitude — a document that matched overwhelmingly and one that matched adequately are treated as "first" either way.</p>
<p><strong>Weighted score fusion</strong> keeps that magnitude and lets you deliberately favour one retriever. It requires normalisation, and normalisation has to be chosen carefully: min-max over the retrieved list makes the last result zero regardless of its real score, which is an artefact, not a judgement.</p>
<p>For most systems, rank fusion first. Move to weighted scores only when you have an evaluation set showing a specific query type where magnitude carries information the ranks lose.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>Running both searches is the obvious half. The combination is where the behaviour actually lives.</p>
<p>And the standard combination has a knob in it that is easy to copy without reading: <code>k</code> is not a smoothing detail, it is the answer to "can one retriever's favourite win on its own?"
