12:T223e,<p>A RAG system is only as good as its first step: turning the user's question into a search. And user questions are bad searches. They are short, conversational, full of pronouns, and phrased in the user's vocabulary rather than the documents'.</p>
<p><em>"and what about for contractors?"</em> is a perfectly clear follow-up in a conversation about holiday policy. As a search query, it is almost useless.</p>
<p>Query rewriting puts a language model in front of the retriever to fix the query before it is used. Multi-query retrieval goes a step further: it writes several versions and searches with all of them.</p>
<h2 id="rewriting-a-single-query"><a class="heading-anchor" href="#rewriting-a-single-query">Rewriting a single query</a></h2>
<p>The simplest form takes the conversation and the latest message and produces a standalone search query:</p>





















<table><thead><tr><th>user wrote</th><th>rewritten</th></tr></thead><tbody><tr><td><em>and what about for contractors?</em></td><td><em>annual leave entitlement for contractors</em></td></tr><tr><td><em>why is it so slow lol</em></td><td><em>causes of slow page load times in the checkout service</em></td></tr><tr><td><em>the thing from the Q3 call about pricing</em></td><td><em>pricing changes announced in the Q3 earnings call</em></td></tr></tbody></table>
<p>Three fixes happen at once: references are resolved from the conversation, filler is removed, and the wording moves toward how documents describe the topic. This is cheap — one short model call — and nearly always worth it in a conversational system.</p>
<h2 id="multi-query-search-several-ways"><a class="heading-anchor" href="#multi-query-search-several-ways">Multi-query: search several ways</a></h2>
<p>A single rewrite still bets on one phrasing. Documents describe the same thing many ways: "annual leave", "paid time off", "holiday entitlement", "vacation days". A query that matches one phrasing may miss the others entirely.</p>
<p>Multi-query retrieval asks the model for several different rewrites — different vocabulary, different angles, sometimes a broader and a narrower version — runs a search for each, and merges the results.</p>
<p>If one query finds the relevant document with probability 0.6, and three rewrites each have that chance <em>independently</em>, the chance at least one finds it is:</p>
<p><code>1 − 0.4³ = 93.6%</code></p>





















<table><thead><tr><th>single-query recall</th><th>three independent rewrites</th></tr></thead><tbody><tr><td>50%</td><td>87.5%</td></tr><tr><td>60%</td><td><strong>93.6%</strong></td></tr><tr><td>70%</td><td>97.3%</td></tr></tbody></table>
<p>But rewrites of the same question are not independent. If a document is missed because it uses vocabulary none of the rewrites thought of, all three miss it together. Suppose that half the time the three queries succeed or fail as one:</p>
<p><code>0.5 × 0.6 + 0.5 × 0.936 =</code> <strong>76.8%</strong></p>
<p>Still a large gain over 60%, and much less than the independent estimate. The lesson is that rewrites should be <em>diverse</em>: different words and different angles, not three paraphrases of one sentence. Prompting explicitly for synonyms, for the more technical phrasing, and for a broader version of the question is what reduces that correlation.</p>

<h2 id="merging-the-results-reciprocal-rank-fusion"><a class="heading-anchor" href="#merging-the-results-reciprocal-rank-fusion">Merging the results: reciprocal rank fusion</a></h2>
<p>Each search returns a ranked list, and the scores from different queries are not comparable. Reciprocal rank fusion ignores the scores and uses only the ranks:</p>
<p><code>score(document) = Σ over lists of 1 / (60 + rank)</code></p>
<p>The constant 60 damps the difference between rank 1 and rank 2 so that no single list dominates. Compare three documents:</p>

























<table><thead><tr><th>document</th><th>ranks in the three lists</th><th>fused score</th></tr></thead><tbody><tr><td>A</td><td>1, missing, 3</td><td>0.0323</td></tr><tr><td>B</td><td>2, 2, 2</td><td><strong>0.0484</strong></td></tr><tr><td>C</td><td>1, missing, missing</td><td>0.0164</td></tr></tbody></table>
<p>B was never first, but every query found it near the top; it wins. A was first once and found twice; it comes second. C topped one list and nothing else; it comes last. That is usually the right judgement: a document that every phrasing finds is more likely relevant than one that a single phrasing happens to rank first.</p>
<h2 id="related-techniques"><a class="heading-anchor" href="#related-techniques">Related techniques</a></h2>
<p><strong>Step-back queries.</strong> Ask a more general question first — "what are the rules for leave entitlement?" — to retrieve background, then the specific one.</p>
<p><strong>Decomposition.</strong> Split a compound question — "compare the leave policies of the UK and US offices" — into sub-questions, retrieve for each, and combine.</p>
<p><strong>HyDE.</strong> Instead of rewriting the question, have the model write a hypothetical answer and search with that, since answers look more like documents than questions do.</p>
<p>These combine freely with multi-query; they are all ways of producing better queries than the one the user typed.</p>
<h2 id="what-it-costs"><a class="heading-anchor" href="#what-it-costs">What it costs</a></h2>
<p>One extra model call to produce the rewrites — a few hundred milliseconds — and <em>n</em> searches instead of one, which run in parallel and are cheap. More retrieved chunks means more for a reranker or the generation model to read; deduplicate before passing them on.</p>
<p>For simple, keyword-like queries the gain is small. For conversational follow-ups, vague questions and corpora with inconsistent vocabulary, it is usually one of the highest-value changes to a RAG pipeline.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>Rewrite every conversational query into a standalone search; it is cheap and fixes pronouns, filler and vocabulary. For harder cases, generate several diverse rewrites and search with all of them: recall rises from 60% toward 93.6%, reaching it only as far as the rewrites fail independently.</p>
