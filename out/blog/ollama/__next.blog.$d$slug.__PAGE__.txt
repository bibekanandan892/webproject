5:T2408,<p>Running a language model on your own machine used to mean choosing a model format, compiling an inference engine, picking a quantization, and writing a server around it. Ollama turns all of that into:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="bash" data-theme="github-light github-dark-default"><code data-language="bash" data-theme="github-light github-dark-default" style="display: grid;"><span data-line=""><span style="--shiki-light:#6F42C1;--shiki-dark:#FFA657">ollama</span><span style="--shiki-light:#032F62;--shiki-dark:#A5D6FF"> run</span><span style="--shiki-light:#032F62;--shiki-dark:#A5D6FF"> llama3.1</span></span></code></pre></figure>
<p>The first time, it downloads the model. Then you are talking to it. Under that single command there are four separate pieces, and knowing what they are explains what Ollama can and cannot do for you.</p>
<h2 id="the-four-pieces"><a class="heading-anchor" href="#the-four-pieces">The four pieces</a></h2>
<p><strong>1. A model registry.</strong> <code>llama3.1</code> is a name in Ollama's library, like an image name in Docker. Pulling it fetches a set of layers — the weights, a prompt template, default parameters, a licence — and stores them locally by content hash, so models that share layers share disk.</p>
<p><strong>2. Quantized weights in GGUF.</strong> The weights are not the original 16-bit release. They are quantized, typically to about 4–5 bits per weight, and stored as GGUF: a single file holding the tensors, the tokenizer and the metadata needed to run them. This is what makes models fit on ordinary hardware.</p>
<p><strong>3. An inference engine.</strong> Ollama's runtime is built on the llama.cpp lineage of engines: optimised CPU code, plus GPU back-ends for Apple Metal, NVIDIA CUDA and AMD ROCm. It detects the hardware, puts as many layers on the GPU as will fit, and runs the rest on the CPU.</p>
<p><strong>4. A local server.</strong> Ollama runs a background service on port 11434 with a REST API, including an OpenAI-compatible endpoint. Anything that can call an LLM API can be pointed at <code>http://localhost:11434</code> instead.</p>
<h2 id="the-modelfile"><a class="heading-anchor" href="#the-modelfile">The Modelfile</a></h2>
<p>Customising a model is done with a Modelfile, deliberately modelled on a Dockerfile:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="text" data-theme="github-light github-dark-default"><code data-language="text" data-theme="github-light github-dark-default" style="display: grid;"><span data-line=""><span>FROM llama3.1</span></span>
<span data-line=""><span>PARAMETER temperature 0.2</span></span>
<span data-line=""><span>PARAMETER num_ctx 8192</span></span>
<span data-line=""><span>SYSTEM You are a terse assistant that answers in one sentence.</span></span></code></pre></figure>
<p><code>ollama create terse -f Modelfile</code> produces a new named model that shares the base weights and adds the new layers on top. Nothing is retrained; it is the same weights with a different default prompt and settings.</p>
<h2 id="what-decides-the-speed"><a class="heading-anchor" href="#what-decides-the-speed">What decides the speed</a></h2>
<p>Generating each token means reading every weight once. On a laptop or desktop that is limited not by arithmetic but by how fast weights can be streamed from memory. So the ceiling is easy to estimate:</p>
<p><code>tokens per second ≈ memory bandwidth ÷ model size in bytes</code></p>

<p>100 GB/s is a typical laptop with ordinary RAM. 400 GB/s is a high-end unified-memory laptop. 1,000 GB/s is a desktop GPU. Real speeds land somewhat below these ceilings.</p>
<p>Two consequences follow. First, quantization is not only about fitting: a 4-bit model is about <strong>3.3×</strong> faster than the same model at 16 bits, because there are fewer bytes to read. Second, a 70B model on a laptop is possible but slow — a couple of tokens a second, slower than reading speed.</p>

<h2 id="memory-what-must-fit"><a class="heading-anchor" href="#memory-what-must-fit">Memory: what must fit</a></h2>
<p>The weights must fit, plus the KV cache for the context, plus some working space. An 8B model at 4-bit needs roughly 5 GB for weights and a few hundred megabytes to a few gigabytes of cache depending on context length. Ollama's context default is modest for exactly this reason; raising <code>num_ctx</code> raises memory use.</p>
<p>When a model does not fit entirely on the GPU, Ollama splits it: some layers on the GPU, the rest on the CPU. That works, but the CPU layers run at system-RAM bandwidth, and the whole token waits for the slowest part. A model that is 80% on the GPU is often much closer to CPU speed than GPU speed.</p>
<h2 id="loading-and-unloading"><a class="heading-anchor" href="#loading-and-unloading">Loading and unloading</a></h2>
<p>Loading a model means reading it from disk into memory: an 8B 4-bit model is about 1.6 seconds from a 3 GB/s SSD, a 70B model tens of seconds. To avoid paying that on every request, Ollama keeps a model loaded after use — five minutes by default, adjustable with <code>keep_alive</code> — and unloads it afterwards to free memory. The first request after a pause is slow; the rest are not.</p>
<p>Several models can be loaded at once if memory allows, and requests to the same model can be processed in parallel, which is what lets a local server back a small team or a set of agents.</p>
<h2 id="when-to-use-it-and-when-not"><a class="heading-anchor" href="#when-to-use-it-and-when-not">When to use it, and when not</a></h2>
<p><strong>Use it</strong> for private data that should not leave the machine, offline work, development against a local API, experimenting with many open models, and running small models for cheap, frequent tasks.</p>
<p><strong>Do not expect</strong> server-grade throughput. Ollama is optimised for a single machine and a modest number of users. Serving many concurrent users at high throughput is the job of engines built for batching on data-centre GPUs, like vLLM or SGLang.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>Ollama is a registry, a set of quantized GGUF models, a llama.cpp-style inference engine and a local HTTP server, wrapped in one command. The Modelfile customises a model without retraining it.</p>
<p>Locally, speed is bandwidth divided by model size: an 8B model at about 4.85 bits runs near 20 tokens a second on a 100 GB/s laptop, a 70B model near 2.
