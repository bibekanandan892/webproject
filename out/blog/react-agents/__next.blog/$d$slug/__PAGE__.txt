4:T2c9f,<p>ReAct is short for reasoning and acting. It is a pattern for building an agent where every step follows the same three beats: a <strong>thought</strong> about what to do, an <strong>action</strong> taken, and an <strong>observation</strong> of what came back.</p>
<p>The loop repeats those beats until the model decides it has enough to answer.</p>
<h2 id="why-write-the-thought-down"><a class="heading-anchor" href="#why-write-the-thought-down">Why write the thought down</a></h2>
<p>The actions and observations are obviously necessary. The thought is the part that looks optional, and it is not.</p>
<p>It goes into the transcript. On the next step the model reads its own reasoning back, along with what the tool returned, and that is what keeps a sequence of calls coherent rather than each one being decided from scratch.</p>
<p>It is also the only record of <em>why</em>. When an agent takes a strange action, the observation tells you what it got and the action tells you what it did — the thought is the only thing that tells you what it believed at the time. Debugging without it means guessing.</p>
<h2 id="the-parts"><a class="heading-anchor" href="#the-parts">The parts</a></h2>
<p>A model that decides what happens next. A <strong>system prompt</strong> that sets out the pattern, the tools, and the rules. <strong>Tools</strong>, each with a name, a description, and a schema. <strong>Memory</strong>, which here just means the running transcript. And a <strong>loop controller</strong> — ordinary code that calls the model, runs whatever tool it asked for, appends the result, and calls again.</p>
<p>The tool descriptions deserve more care than they usually get. They are the entire basis on which the model chooses, so two tools described similarly will be picked between at random.</p>
<h2 id="a-trace"><a class="heading-anchor" href="#a-trace">A trace</a></h2>
<p>Three tools — <code>query_sales</code>, <code>calculate</code> — and the question: <em>did we ship more in Q3 than Q2, and by how much?</em></p>

















































<table><thead><tr><th></th><th></th></tr></thead><tbody><tr><td><strong>Thought</strong></td><td>I need both quarters' totals, and I do not know either.</td></tr><tr><td><strong>Action</strong></td><td><code>query_sales(quarter="Q2")</code></td></tr><tr><td><strong>Observation</strong></td><td>18,400 units</td></tr><tr><td><strong>Thought</strong></td><td>Now the other quarter.</td></tr><tr><td><strong>Action</strong></td><td><code>query_sales(quarter="Q3")</code></td></tr><tr><td><strong>Observation</strong></td><td>21,850 units</td></tr><tr><td><strong>Thought</strong></td><td>Higher. <p>Two habits worth noticing.</p>
<p>It fetched both numbers before doing anything with them, because the second query did not depend on the first result. And it used a calculator rather than doing the arithmetic itself, which is what a well-written system prompt asks for — a model producing a percentage from inside its own weights is guessing at a digit level.</p>

<p>That is also the pattern's main cost. The transcript only grows, and every step re-sends all of it, so a twenty-step run pays for its early steps twenty times over.</p>

<p>The <code>except</code> is the part people leave out. A tool that raises kills the run; a tool whose failure is handed back as an observation gives the model something to react to — and reacting to what came back is the entire pattern.</p>
<h2 id="what-goes-wrong"><a class="heading-anchor" href="#what-goes-wrong">What goes wrong</a></h2>
<p><strong>It loops.</strong> The same action with the same arguments, over and over. <code>MAX_STEPS</code> is the guaranteed exit; detecting a repeated action and injecting a nudge to try something else is the graceful one.</p>
<p><strong>It picks the wrong tool.</strong> Almost always a description problem rather than a reasoning problem.</p>
<p><strong>It invents a tool or malformed arguments.</strong> Validate before executing, and return the validation error as an observation.</p>
<p><strong>It runs out of context.</strong> Inevitable on long runs, since the transcript only grows. Old observations get summarised or dropped, while the question and the recent steps stay intact.</p>
<p><strong>It stops too early.</strong> It answers from two observations when it needed four. The fix is in the prompt: state what has to be true before answering, as something checkable.</p>
<h2 id="the-short-version"><a class="heading-anchor" href="#the-short-version">The short version</a></h2>
<ul>
<li>ReAct runs thought, action, observation, repeatedly, until a final answer.</li>
<li>The thought is written into the transcript, so the model reads its own reasoning back each step.</li>
<li>It is also the only record of why an action was taken, which is what makes the run debuggable.</li>
<li>Tool choice comes down to tool descriptions.</li>
<li>The transcript is the memory, and it is re-sent whole on every step — which is the pattern's main cost.</li>
<li>Tool failures should come back as observations, not exceptions.</li>
<li>A step limit is the only guaranteed way out.</li>
