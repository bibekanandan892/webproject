12:T1ded,<p>Fugu, from Sakana AI, is a model whose output is not an answer. Given a task, it decides which of several frontier models should handle it — and in its larger variant, how several of them should split the work between them.</p>
<p>The claim behind it is that coordination is its own axis of capability: that a well-directed team of existing models beats any one of them, without training anything bigger.</p>
<p>That claim is testable, and the arithmetic is more interesting than the architecture.</p>
<h2 id="how-much-is-there-to-win"><a class="heading-anchor" href="#how-much-is-there-to-win">How much is there to win</a></h2>
<p>Different models fail on different problems. If they failed on exactly the same ones, routing would be pointless — you would always pick the strongest and be done.</p>
<p>So the ceiling for routing is the <strong>union</strong>: the share of problems that at least one model in the pool can solve. A perfect router with foreknowledge would hit exactly that.</p>
<p>On one software-engineering benchmark, three frontier models score 69.2%, 58.6% and 54.2%. If their failures were statistically independent, the union would be 94.2% — a 25-point gap above the best single model, sitting there waiting for a router good enough to claim it.</p>
<p>They are not independent. Hard problems tend to be hard for everyone, so the real union is far below 94.2%.</p>
<p>But this cuts both ways, and here is what makes it worth computing. The orchestrated system reaches <strong>73.7%</strong>. For that to be possible, the fraction of the best model's failures that are hard for <em>every</em> model must be at most 85.4% — because if more than that were commonly hard, no router could have got past 72.3%.</p>
<p>So the reported number tells you something about the pool that no individual score does: at least 15% of what the strongest model gets wrong, some other model gets right.</p>

<h2 id="two-shapes-of-the-same-idea"><a class="heading-anchor" href="#two-shapes-of-the-same-idea">Two shapes of the same idea</a></h2>
<p><strong>The fast variant picks one model per input.</strong> It does not write out its reasoning — it reads its own hidden state after taking in the task and produces a score per candidate model directly. One forward pass, then hand the whole job over.</p>
<p>That design decision is the point of the variant. If choosing which model to use cost as much as running one, routing would be a tax rather than a saving.</p>
<p><strong>The larger variant plans a small workflow.</strong> Rather than one choice it emits a structure: a set of subtasks, which model handles each, and which earlier results each one is allowed to see.</p>
<p>This second form is not bound by the union ceiling above, and that is exactly why it exists. Two models can each produce a partial answer that neither could complete alone, and a third can assemble them. Composition can exceed the best member in a way selection cannot.</p>
<h2 id="training-something-whose-output-is-a-plan"><a class="heading-anchor" href="#training-something-whose-output-is-a-plan">Training something whose output is a plan</a></h2>
<p>Both variants face the same difficulty: the thing being learned is a decision, and decisions have no gradient of their own. You only find out whether a choice was good by running it.</p>
<p>The first stage is ordinary supervised learning. Run every candidate model over a set of tasks, record how well each did, turn those scores into a target distribution, and train the selector to match it. This teaches broad competence — which models are generally good at which kinds of work.</p>
<p>The second stage handles what supervision cannot. For workflows there is no labelled correct plan, so training compares <em>sampled</em> plans against each other: generate several for the same task, score each on whether the final answer was right, and push toward the ones that scored above the group's average. A plan is not judged against an ideal; it is judged against its own siblings.</p>
<p>The selection head is also adjusted with a search method that needs no gradients at all — perturb the parameters, keep what scores well, move that way. Slow per step, but it works on objectives that are not differentiable, which a "did this workflow succeed" reward is not.</p>
<h2 id="the-parts-that-are-easy-to-overlook"><a class="heading-anchor" href="#the-parts-that-are-easy-to-overlook">The parts that are easy to overlook</a></h2>
<p><strong>Workers do not see each other's context.</strong> Each subtask gets only what the plan explicitly grants it. This is a correctness measure, not tidiness: if every worker inherited every previous result, one confused step would contaminate the rest, and the orchestrator would lose the independence that makes combining answers worth anything.</p>
<p><strong>The pool is swappable.</strong> Because the orchestrator scores candidates rather than embedding knowledge of specific ones, a better model can be added without retraining from scratch. That is a real practical property — the alternative is a system that decays as the field moves.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>The honest reading of Fugu is not "orchestration beats big models". It is that a pool of models with genuinely different failures contains more capability than any member exposes, and that this surplus can be partly recovered by something small and cheap deciding who does what.</p>
<p>How much surplus there is depends entirely on how different the models are.
