12:T2ab7,<p>A trained model is a file of weights. Model serving is everything needed to turn that file into something that answers requests: reliably, quickly enough, for many users at once, at a cost that makes sense.</p>
<p>It is mostly not about the model. It is about queues, batches, memory and hardware.</p>
<h2 id="the-request-path"><a class="heading-anchor" href="#the-request-path">The request path</a></h2>
<p>A typical request to a served model goes through:</p>
<ol>
<li><strong>A gateway</strong> — authentication, rate limits, routing to the right model and version.</li>
<li><strong>A queue</strong> — requests wait here when every worker is busy.</li>
<li><strong>A scheduler</strong> — groups waiting requests into batches and assigns them to workers.</li>
<li><strong>A model worker</strong> — a process holding the weights on one or more accelerators, running the forward passes.</li>
<li><strong>Pre- and post-processing</strong> — tokenising input, applying safety filters, formatting and streaming output.</li>
</ol>
<p>Each step adds latency, and any of them can be the bottleneck.</p>
<h2 id="batching-is-the-economics"><a class="heading-anchor" href="#batching-is-the-economics">Batching is the economics</a></h2>
<p>A GPU running a model for one request at a time spends most of its time waiting for weights to arrive from memory, not computing. Serving many requests together lets each weight that is loaded be used for all of them. Throughput rises almost proportionally with batch size, until compute becomes the limit.</p>
<p>For a language model on a GPU rented at $2 an hour:</p>





















<table><thead><tr><th>tokens per second (whole GPU)</th><th>cost per million tokens</th></tr></thead><tbody><tr><td>50 — one request at a time</td><td><strong>$11.11</strong></td></tr><tr><td>500 — modest batching</td><td>$1.11</td></tr><tr><td>2,000 — well-batched</td><td><strong>$0.28</strong></td></tr></tbody></table>
<p>A forty-fold difference in cost on the same hardware, from how requests are grouped. <strong>Continuous batching</strong> — adding new requests to a running batch the moment others finish, rather than waiting for a whole batch to complete — is what makes high utilisation possible for generation, where every request has a different length.</p>
<h2 id="utilisation-is-the-latency-trap"><a class="heading-anchor" href="#utilisation-is-the-latency-trap">Utilisation is the latency trap</a></h2>
<p>There is a catch. A busy server makes requests wait. With random arrivals and service times, queueing theory gives the average wait as <code>ρ / (1 − ρ)</code> times the service time, where ρ is utilisation. For a 100 ms service time:</p>






























<table><thead><tr><th>utilisation</th><th>average queue wait</th><th>total response time</th></tr></thead><tbody><tr><td>50%</td><td>100 ms</td><td>200 ms</td></tr><tr><td>80%</td><td>400 ms</td><td>500 ms</td></tr><tr><td>90%</td><td>900 ms</td><td>1,000 ms</td></tr><tr><td>95%</td><td><strong>1,900 ms</strong></td><td><strong>2,000 ms</strong></td></tr></tbody></table>
<p>From 50% to 95% busy, the wait grows nineteen-fold. The last few points of utilisation are where latency explodes. Cost pushes toward running hot; latency targets push back. Real serving systems run well below 100% and <strong>autoscale</strong> — adding workers as load rises — to stay on the flat part of the curve.</p>

<h2 id="fitting-the-model-in-memory"><a class="heading-anchor" href="#fitting-the-model-in-memory">Fitting the model in memory</a></h2>
<p>The weights must fit on the accelerators, with room left for working memory — for language models, mostly the KV cache that grows with every active conversation.</p>
<ul>
<li><strong>Quantization</strong> stores weights in 8 or 4 bits instead of 16, halving or quartering their memory and speeding up memory-bound inference.</li>
<li><strong>Tensor parallelism</strong> splits each layer across several GPUs that work on it together; <strong>pipeline parallelism</strong> gives different layers to different GPUs.</li>
<li><strong>Paged KV caches</strong> allocate cache memory in small blocks, like virtual memory, so variable-length conversations do not waste space — which directly raises how many requests fit in a batch.</li>
</ul>
<h2 id="latency-targets-for-language-models"><a class="heading-anchor" href="#latency-targets-for-language-models">Latency targets for language models</a></h2>
<p>Generation has two latencies that matter separately:</p>
<ul>
<li><strong>Time to first token (TTFT)</strong> — dominated by processing the prompt. Affected by prompt length, prompt caching and queueing.</li>
<li><strong>Time per output token (TPOT)</strong> — the streaming speed once generation starts. Affected by batch size and model size.</li>
</ul>
<p>Larger batches improve cost and throughput but slow each request's tokens. Serving systems set targets for both, often at the 95th or 99th percentile, and tune batch sizes to meet them.</p>
<h2 id="operating-it"><a class="heading-anchor" href="#operating-it">Operating it</a></h2>
<p><strong>Versioning and rollout.</strong> Serve several model versions side by side; shift traffic gradually; roll back quickly.</p>
<p><strong>Cold starts.</strong> Loading tens of gigabytes of weights takes time. Keep warm capacity and scale up before demand peaks rather than after.</p>
<p><strong>Observability.</strong> Track queue depth, utilisation, TTFT and TPOT percentiles, error rates, and tokens per second per GPU. Cost per million tokens follows directly from the last.</p>
<p><strong>Graceful overload.</strong> When demand exceeds capacity, reject or queue with a clear signal rather than letting every request slow down.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>Model serving is gateways, queues, schedulers and workers wrapped around a model.
