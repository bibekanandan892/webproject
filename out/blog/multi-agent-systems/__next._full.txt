11:T2b9e,<p>One agent with twelve tools and a two-page system prompt starts making worse choices than one with three tools and a paragraph. Splitting the job across several agents is a response to that.</p>
<p>A multi-agent system is two or more agents working on a shared task, each with its own instructions and its own tools, plus something deciding who runs when.</p>
<h2 id="three-things-it-needs"><a class="heading-anchor" href="#three-things-it-needs">Three things it needs</a></h2>
<p><strong>Specialisation.</strong> Each agent has a narrow role, a short prompt, and only the tools that role needs. This is the entire point — if every agent has every tool, nothing has been gained.</p>
<p><strong>Communication.</strong> Agents pass work to each other. What passes between them should be structured — named fields with known meanings — rather than prose. Free text between agents is where misreadings creep in, and they are hard to spot because the output still looks reasonable.</p>
<p><strong>Coordination.</strong> Something decides the order and decides when the whole thing is finished. Without it there are several agents, but not a system.</p>
<h2 id="the-roles-that-keep-appearing"><a class="heading-anchor" href="#the-roles-that-keep-appearing">The roles that keep appearing</a></h2>
<p>An <strong>orchestrator</strong> takes the request, hands out subtasks, and assembles the result. A <strong>worker</strong> does one kind of job well. A <strong>router</strong> looks at the request and picks who should handle it. A <strong>planner</strong> turns a goal into steps. A <strong>critic</strong> checks work against something independent.</p>
<p>Most real systems are a small combination of these, not all of them.</p>

<p>A system that keeps API documentation in step with the code. A release has just changed some endpoints.</p>

<p>Two things are doing real work here.</p>
<p>The writers run <strong>in parallel</strong> because the endpoints are independent. Three sequential calls became one round, and that is the clearest win a multi-agent system offers.</p>
<p>The reviewer is <strong>grounded in something other than the writer's opinion</strong> — it reads the actual code, not just the draft. A critic that only re-reads the draft it is checking will approve confident nonsense, because confident nonsense reads well.</p>
<h2 id="how-they-talk"><a class="heading-anchor" href="#how-they-talk">How they talk</a></h2>
<p><strong>Message passing</strong> sends a task and its context directly to one agent. <strong>Shared state</strong> gives every agent a common scratchpad to read and write. <strong>Handoffs</strong> pass the work <em>and</em> the control — the sender stops, the receiver continues.</p>
<p>Whichever you use, define the shape. <code>{"endpoint": "...", "verb": "...", "changed": [...]}</code> survives being read by a different model with a different prompt. A paragraph describing the same thing does not, reliably.</p>
<p>How much memory to share is a real dial. Sharing everything gives each agent full context and costs tokens on every call. Sharing summaries is cheaper and loses detail. Sharing nothing is cheapest and means agents repeat each other's work.</p>

<table><thead><tr><th></th><th>one agent</th><th>several</th></tr></thead><tbody><tr><td>prompt</td><td>one, long</td><td>several, each short</td></tr><tr><td>tools</td><td>all on one</td><td>split by role</td></tr><tr><td>parallel work</td><td>tool calls only</td><td>natural</td></tr><tr><td>debugging</td><td>one transcript</td><td>many, plus the handoffs</td></tr><tr><td>latency</td><td>lower</td><td>higher, unless parallelism wins it back</td></tr><tr><td>tokens</td><td>lower</td><td>higher — every handoff re-sends context</td></tr></tbody></table>
<p>The debugging line is the one that gets underestimated. When a single agent goes wrong there is one transcript to read. When a system of five goes wrong, the visible failure is often three handoffs downstream of the actual mistake, and each agent along the way made a locally sensible decision.</p>
<h2 id="what-goes-wrong"><a class="heading-anchor" href="#what-goes-wrong">What goes wrong</a></h2>
<p><strong>They talk instead of working.</strong> Agents exchange messages, each adding little, and the token count climbs while nothing progresses. Cap total turns.</p>
<p><strong>Nobody owns a step.</strong> Two agents both write the summary, or neither does. Scope each role explicitly, and keep the orchestrator to routing rather than letting it also do the work.</p>
<p><strong>One mistake gets amplified.</strong> The researcher retrieves the wrong figure, the writer builds a confident paragraph on it, and the reviewer checks whether the paragraph is well written. Errors need catching where they are made, which means a critic with independent grounding.</p>
<p><strong>The critic never accepts.</strong> Each round it finds something new, and the loop does not end. Cap the revisions, and accept when two consecutive rounds raise substantially the same point — that is a critic with no more to say, not a draft with more to fix.</p>
<p><strong>Coordination costs more than the work.</strong> For a task with three short steps, the messages describing the steps can outweigh doing them.</p>
<h2 id="when-not-to"><a class="heading-anchor" href="#when-not-to">When not to</a></h2>
<p>Start with one agent. Move only when it is clearly failing.</p>
<p>The good reasons to split are real ones: the prompt has grown unmanageable, the parts genuinely need different tools or different models, several subtasks are independent and can run at once, or a review step measurably improves the result.</p>
<p>The bad reason is that more agents feel more capable. Each one you add is another prompt to tune, another failure mode, and another hop where context gets dropped. If the work is tightly coupled — every step needing everything the previous step saw — splitting it just means paying to re-send that context at each boundary.</p>
<h2 id="the-short-version"><a class="heading-anchor" href="#the-short-version">The short version</a></h2>
<ul>
<li>A multi-agent system is specialised agents, structured communication, and something coordinating them.</li>
<li>The recurring roles are orchestrator, worker, router, planner and critic.</li>
<li>Parallelism on independent subtasks is the clearest benefit.</li>
<li>A critic only helps if it checks against something other than the draft.</li>
<li>Messages between agents should be structured, not prose.</li>
<li>The costs are tokens, latency and debugging — and debugging is the one people underestimate.</li>
<li>Start with one agent; add a second only when the first is visibly failing.</li>
