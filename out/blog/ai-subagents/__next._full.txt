11:T219f,<p>A subagent is an agent invoked by another agent. The parent hands it a narrow task, it runs its own loop with its own tools, and it returns a result.</p>
<p>The useful way to think about it is as a <strong>function call</strong>. It has a signature — what goes in, what comes out — it has its own local state, and when it returns, that local state is gone.</p>
<p>That last part is not a detail. It is what subagents are for.</p>
<h2 id="what-the-parent-does-not-have-to-see"><a class="heading-anchor" href="#what-the-parent-does-not-have-to-see">What the parent does not have to see</a></h2>
<p>An agent's context accumulates everything it did: every tool call, every result, every intermediate step. A subagent's context accumulates all of that too — and then throws it away, returning only its answer.</p>
<p>Say a subagent takes twelve turns to do its job, building up around 9,600 tokens of transcript, and reports back in 200.</p>

<p>Around 98% of what happened never reaches the parent. It stays inside the subagent, is used there, and is discarded when it returns.</p>
<p>Compare that to one agent doing everything: by the time it has finished the third subtask, the first subtask's tool output is still sitting in its context, competing for attention with the work in front of it.</p>
<h2 id="the-other-thing-narrowness-buys"><a class="heading-anchor" href="#the-other-thing-narrowness-buys">The other thing narrowness buys</a></h2>
<p>A subagent gets a short prompt and a few tools, because it does one thing.</p>
<p>That matters more than it sounds. An agent choosing between four well-described tools makes better choices than the same model choosing between twenty — the description of each tool is all it has to go on, and twenty descriptions contain more near-collisions than four.</p>
<p>So delegation improves decisions twice over: the subagent has less to read, and less to choose between.</p>
<h2 id="depth-is-where-the-cost-is"><a class="heading-anchor" href="#depth-is-where-the-cost-is">Depth is where the cost is</a></h2>
<p>Subagents can call subagents. That composes nicely and multiplies quickly.</p>








































<table><thead><tr><th>depth</th><th>branching 2</th><th>branching 3</th><th>branching 5</th><th>cost at branching 5</th></tr></thead><tbody><tr><td>1</td><td>2</td><td>3</td><td>5</td><td>$0.15</td></tr><tr><td>2</td><td>4</td><td>9</td><td>25</td><td>$0.75</td></tr><tr><td>3</td><td>8</td><td>27</td><td><strong>125</strong></td><td><strong>$3.75</strong></td></tr><tr><td>4</td><td>16</td><td>81</td><td>625</td><td>$18.75</td></tr></tbody></table>
<p>Depth three with five-way branching is 125 agent runs for a single user request. Nobody designs that on purpose; it happens when each level looks locally reasonable.</p>
<p>Latency behaves similarly. Siblings run in parallel, but levels do not — a three-deep hierarchy has three sequential rounds of waiting whatever the branching.</p>
<p>So depth needs an explicit limit, the same way a loop needs a step limit.</p>
<h2 id="what-it-costs-elsewhere"><a class="heading-anchor" href="#what-it-costs-elsewhere">What it costs elsewhere</a></h2>
<p><strong>Coordination tokens.</strong> Splitting the task and combining the results are extra model calls that exist only because the work was split.</p>
<p><strong>Lossy handoffs.</strong> The subagent sees only what the parent passed it. A missing constraint produces a technically correct answer to the wrong question, and the parent has no way to notice because it never saw the working.</p>
<p><strong>Harder debugging.</strong> A wrong final answer might come from a bad split, a bad subagent, or a bad synthesis. The parent's transcript shows three tidy summaries and none of the evidence.</p>
<p>Which suggests logging what goes into and out of every subagent, even though the parent does not see it. The discarded transcript is exactly what you need when something is wrong.</p>
<h2 id="when-not-to"><a class="heading-anchor" href="#when-not-to">When not to</a></h2>
<p>If the task does not decompose cleanly, splitting it just adds handoffs. If each part needs everything the other parts saw, you will spend the saving re-sending context across the boundaries.</p>
<p>And for anything a single agent handles adequately, subagents add coordination cost, latency, and failure modes in exchange for nothing.</p>
<h2 id="the-short-version"><a class="heading-anchor" href="#the-short-version">The short version</a></h2>
<ul>
<li>A subagent is an agent called like a function: narrow task in, result out, working discarded.</li>
<li>Discarding the working is the point — a parent sees ~2% of what its subagents did.</li>
<li>Narrow tool sets also improve tool choice, because there is less to confuse.</li>
<li>Nesting multiplies: depth 3 with 5-way branching is 125 runs for one request.</li>
<li>Levels are sequential even though siblings are parallel, so depth costs latency too.</li>
<li>Cap the depth explicitly, as you would cap loop steps.</li>
<li>Log subagent inputs and outputs, since the parent's view has the evidence removed.</li>
<li>Do not split work that does not decompose — the handoffs cost more than the split saves.</li>
