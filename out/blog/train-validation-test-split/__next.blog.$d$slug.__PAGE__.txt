5:T2224,<p>A model is only useful if it works on data it has not seen. Every evaluation practice in machine learning is built around measuring that honestly, and the most basic one is splitting the data into three parts before anything else happens.</p>

























<table><thead><tr><th>set</th><th>typical share</th><th>used to</th></tr></thead><tbody><tr><td><strong>training</strong></td><td>70–80%</td><td>fit the model's weights</td></tr><tr><td><strong>validation</strong></td><td>10–15%</td><td>choose between models, settings and when to stop</td></tr><tr><td><strong>test</strong></td><td>10–15%</td><td>report the final result — once</td></tr></tbody></table>
<p>The reason there are three, not two, is the interesting part.</p>
<h2 id="training-where-the-model-learns"><a class="heading-anchor" href="#training-where-the-model-learns">Training: where the model learns</a></h2>
<p>The training set is what gradient descent sees. The model's weights are adjusted to reduce error on exactly these examples, so performance on them is always optimistic. A large enough model can memorise its training set completely and still be useless on anything else. Training accuracy tells you the model <em>can</em> fit the data, nothing more.</p>
<h2 id="validation-where-you-make-decisions"><a class="heading-anchor" href="#validation-where-you-make-decisions">Validation: where you make decisions</a></h2>
<p>Building a model involves many choices the training process does not make for you: the architecture, the learning rate, how much regularisation, which features to include, when to stop training. Each is decided by trying options and comparing them on data the model did not train on — the validation set.</p>
<p>Validation data is therefore <em>used</em>, indirectly. Every choice made by looking at validation scores fits the final model a little to those particular examples.</p>
<h2 id="test-where-you-find-out"><a class="heading-anchor" href="#test-where-you-find-out">Test: where you find out</a></h2>
<p>The test set answers one question: how well will the finished model do on new data? To answer it honestly, it must play no part in any decision. Ideally it is looked at once, at the end.</p>
<h2 id="what-goes-wrong-without-the-middle-set"><a class="heading-anchor" href="#what-goes-wrong-without-the-middle-set">What goes wrong without the middle set</a></h2>
<p>Suppose you skip validation and choose between models by their test score. It feels harmless — you are only picking the best one.</p>
<p>Simulate it. Twenty model configurations, all with the same <strong>true</strong> accuracy of 90%. Each is scored on the same 1,000-example test set; random variation means each gets a slightly different score. Pick the best:</p>

























<table><thead><tr><th>configurations compared on the test set</th><th>average score of the "best" one</th></tr></thead><tbody><tr><td>1</td><td>90.00%</td></tr><tr><td>5</td><td>91.11%</td></tr><tr><td>20</td><td><strong>91.71%</strong></td></tr><tr><td>100</td><td>92.39%</td></tr></tbody></table>
<p>None of them is better than 90%. But pick the winner from 20 and you will report 91.71% — an improvement that exists only because you chose the configuration that happened to get lucky on those particular 1,000 examples. Try 100 and you will report 92.39%.</p>
<p>This is overfitting to the test set, and it happens with no change to any model weights at all. It is why test sets must be reserved, and why public benchmarks that the whole field tunes against gradually stop measuring what they claim to.</p>

<h2 id="how-big-each-set-needs-to-be"><a class="heading-anchor" href="#how-big-each-set-needs-to-be">How big each set needs to be</a></h2>
<p>The test set's size decides how precisely you know the result. For a model around 90% accurate:</p>

























<table><thead><tr><th>test examples</th><th>standard error</th><th>95% interval</th></tr></thead><tbody><tr><td>100</td><td>3.00%</td><td>±5.88%</td></tr><tr><td>1,000</td><td>0.95%</td><td>±1.86%</td></tr><tr><td>10,000</td><td>0.30%</td><td>±0.59%</td></tr></tbody></table>
<p>With 100 test examples, "91%" means anywhere from about 85% to 97%. Differences between models smaller than the interval are not evidence of anything. When data is plentiful, test and validation sets can be a small percentage of the total and still contain tens of thousands of examples; when it is scarce, <strong>cross-validation</strong> — rotating which slice is held out and averaging — gets more out of it.</p>
<h2 id="splitting-correctly"><a class="heading-anchor" href="#splitting-correctly">Splitting correctly</a></h2>
<p>The split must mimic how the model will meet new data. Random splitting is right only when examples are independent. Common traps:</p>
<ul>
<li><strong>Time.</strong> Forecasting models must be validated on data <em>later</em> than their training data. A random split lets the model peek at the future.</li>
<li><strong>Groups.</strong> If one patient contributes many scans, or one user many messages, all of that person's data must fall in one set. Otherwise the model can recognise the person rather than learn the task.</li>
<li><strong>Duplicates.</strong> Near-identical examples on both sides of the split — the same image resized, the same document reposted — inflate test scores.</li>
<li><strong>Preprocessing.</strong> Statistics used to normalise data, fill missing values or select features must be computed on the training set only, then applied to the others.</li>
</ul>
<p>Each of these is a form of <strong>leakage</strong>: information about the test examples reaching the model or the modeller before the final evaluation.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>Training data fits the weights, validation data makes the choices, test data reports the result. Merging the last two looks harmless but is not: choosing the best of 20 equally good models on a 1,000-example test set reports 91.71% for models that are all really 90%.</p>
