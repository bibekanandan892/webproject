11:T2133,<p>The Model Context Protocol is a standard for how an AI application talks to external systems — files, databases, issue trackers, whatever the work requires.</p>
<p>Two things about it are worth understanding properly: the arithmetic that makes a protocol worth having, and the trust boundary it creates.</p>
<h2 id="the-arithmetic"><a class="heading-anchor" href="#the-arithmetic">The arithmetic</a></h2>
<p>Without a shared protocol, every application that wants to reach a system writes its own integration. Five applications and ten systems means fifty separate pieces of work, and any two applications reaching the same system have written the same thing twice.</p>
<p>With a protocol, each application implements the protocol once and each system exposes itself once. Fifteen pieces of work.</p>



































<table><thead><tr><th>applications × systems</th><th>pairwise</th><th>with a protocol</th><th>reduction</th></tr></thead><tbody><tr><td>5 × 10</td><td>50</td><td>15</td><td>3.3×</td></tr><tr><td>8 × 20</td><td>160</td><td>28</td><td>5.7×</td></tr><tr><td>12 × 30</td><td>360</td><td>42</td><td>8.6×</td></tr><tr><td>20 × 60</td><td>1,200</td><td>80</td><td>15.0×</td></tr></tbody></table>
<p>The reduction grows because the pairwise cost is a <strong>product</strong> and the protocol cost is a <strong>sum</strong>. There is no ecosystem size at which the gap stops widening.</p>
<p>The marginal case is more persuasive than the total. Adding one new system to a world of twelve applications costs twelve integrations pairwise, or one with a protocol. That is the number that decides whether a small team's tool ever gets used.</p>

<h2 id="the-part-that-is-not-just-an-api"><a class="heading-anchor" href="#the-part-that-is-not-just-an-api">The part that is not just an API</a></h2>
<p>An ordinary HTTP API requires a person to read documentation and write a binding. The knowledge of what the API can do lives in a human's head and then in code.</p>
<p>An MCP server is <strong>self-describing</strong>. On connecting it announces what it offers: each tool's name, a plain-language description of when to use it, and a schema for its arguments. Data sources and prompt templates are announced the same way.</p>
<p>That changes who reads the documentation. The descriptions go into the model's context, and the model decides which tool fits the request — so adding a capability to a server makes it available to every connected application without anyone writing integration code for it.</p>
<p>This is the actual content of the standard. Without the self-description it would be a message format; with it, the set of available actions is discovered at run time rather than compiled in.</p>
<h2 id="three-parts-and-one-rule"><a class="heading-anchor" href="#three-parts-and-one-rule">Three parts and one rule</a></h2>
<ul>
<li>The <strong>host</strong> is the application the person is using.</li>
<li>A <strong>client</strong> lives inside the host, one per connected server, handling that connection.</li>
<li>A <strong>server</strong> exposes some system's capabilities.</li>
</ul>
<p>Transport is either a local process communicating over standard input and output — nothing leaves the machine — or HTTP for a remote server shared by many users. Messages are JSON-RPC in both cases.</p>
<p>And the rule that matters: <strong>the model requests, the host decides.</strong> A model emitting a tool call has produced text, not an action. The host validates it, checks whether it is permitted, and runs it or refuses. That separation is the whole safety architecture, and it is the same separation whether the tool reads a file or transfers money.</p>
<h2 id="the-trust-boundary"><a class="heading-anchor" href="#the-trust-boundary">The trust boundary</a></h2>
<p>This deserves more weight than it usually gets.</p>
<p>Everything an MCP server sends — tool descriptions at connect time, and content returned from calls — lands in the model's context as text. The model cannot tell that text apart from the user's own instructions by any structural means.</p>
<p>Two consequences follow.</p>
<p><strong>Returned content is untrusted input.</strong> A document fetched through a server, an issue description, a web page — any of these can contain text addressed to the model, instructing it to do something the user never asked for. It will read exactly like a legitimate instruction. The defence is not to hope the model notices, but to keep destructive and outward-facing actions behind an approval the user gives, so a redirected agent cannot complete the loop on its own.</p>
<p><strong>A server is code you are trusting.</strong> A local server runs on the machine with the user's permissions. Installing one is closer to installing a program than to adding a URL, and the same caution applies — which is easy to forget when it is one line in a configuration file.</p>
<p>Neither of these is an argument against the protocol. They are the cost of the capability, and they are worth naming precisely because the convenience makes them easy to skip past.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>The protocol is worth having for a plain arithmetic reason: it converts a product into a sum, and the advantage compounds as the ecosystem grows.</p>
<p>Its real innovation is self-description, which moves the integration knowledge from a developer's code into the model's context.
