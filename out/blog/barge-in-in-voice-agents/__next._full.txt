12:T1de2,<p>The agent is halfway through reading out three appointment slots when the user says <em>"the second one"</em>. A person would stop at once. An agent without barge-in carries on reading the third slot, then answers a question nobody is asking any more.</p>
<p>Barge-in is the ability to be interrupted: detect that the user has started speaking while the agent is talking, stop the agent's speech, and hand the turn back. It sounds like a single feature. In practice it is four separate problems, each of which can fail on its own.</p>
<h2 id="1-hearing-the-user-over-yourself"><a class="heading-anchor" href="#1-hearing-the-user-over-yourself">1. Hearing the user over yourself</a></h2>
<p>While the agent talks, its own voice comes out of the user's speaker — and, on a phone or a laptop, goes straight back into the user's microphone. To a voice activity detector, that echo looks exactly like the user speaking. Without handling it, the agent interrupts itself.</p>
<p><strong>Acoustic echo cancellation</strong> subtracts the known outgoing audio from the incoming audio, leaving only what the user said. Browsers and phones provide it, with varying quality; speakerphones and cheap headsets are the hard cases. Some systems also raise the detection threshold while the agent is speaking, accepting slower barge-in for fewer false ones.</p>
<h2 id="2-deciding-it-is-a-real-interruption"><a class="heading-anchor" href="#2-deciding-it-is-a-real-interruption">2. Deciding it is a real interruption</a></h2>
<p>Not every sound from the user is a request to take the turn:</p>
<ul>
<li><strong>Backchannels</strong> — "mm-hmm", "yeah", "okay" — mean <em>keep going</em>.</li>
<li><strong>Noise</strong> — a cough, a laugh, someone else in the room, traffic.</li>
<li><strong>Real interruptions</strong> — "wait", "no, the other one", "stop", or simply a new question.</li>
</ul>
<p>Stopping on everything makes the agent fragile: it halts every time the user agrees with it. Stopping on nothing makes it rude. The usual approach waits for a short stretch of confirmed speech — a few hundred milliseconds, or the first recognised words — and classifies it before yielding. That classification is where most of the detection delay comes from.</p>
<h2 id="3-actually-stopping"><a class="heading-anchor" href="#3-actually-stopping">3. Actually stopping</a></h2>
<p>Once the decision is made, the audio has to stop. That is harder than it sounds, because audio is buffered at several points: the TTS engine has generated ahead, the server has queued frames, the network is carrying them, and the client keeps a jitter buffer to play smoothly.</p>
<p>Everything already in those buffers keeps playing unless it is explicitly flushed. With detection taking about 200 ms, the user hears the agent talking over them for:</p>





















<table><thead><tr><th>audio already buffered</th><th>overlap the user hears</th></tr></thead><tbody><tr><td>100 ms</td><td>300 ms</td></tr><tr><td>250 ms</td><td>450 ms</td></tr><tr><td>500 ms</td><td><strong>700 ms</strong></td></tr></tbody></table>
<p>700 milliseconds of both talking at once feels like the agent did not hear. Good barge-in sends a "clear" signal all the way to the client so it discards what it has queued, and keeps server-side buffers short while the agent is speaking.</p>

<h2 id="4-remembering-what-was-really-said"><a class="heading-anchor" href="#4-remembering-what-was-really-said">4. Remembering what was really said</a></h2>
<p>This is the part most often missed. The language model generated a complete reply — say 120 words — and the conversation history records it. But the user interrupted 14 seconds in. At a speaking rate of 150 words per minute, they heard <strong>35 words</strong>. The other 85 were never spoken.</p>
<p>If the history keeps all 120, the model believes the user heard the third appointment slot, the cancellation policy and the closing question. Its next reply will refer to things the user never heard: <em>"As I mentioned, there's a £10 fee…"</em></p>
<p>The fix is to truncate the agent's turn in the history to what was actually played, using timestamps from the audio output, and often to mark it as interrupted. The model then knows it was cut off and can respond to the interruption naturally: <em>"The second one — Tuesday at 3pm. Shall I book it?"</em></p>
<h2 id="tuning-the-trade-off"><a class="heading-anchor" href="#tuning-the-trade-off">Tuning the trade-off</a></h2>
<p>Barge-in has the same two-sided error as every turn-taking decision:</p>
<ul>
<li><strong>Too sensitive:</strong> stops on coughs, echoes and "mm-hmm". The agent never finishes a sentence in a noisy room.</li>
<li><strong>Too sluggish:</strong> the user has to shout "STOP" twice. People hang up.</li>
</ul>
<p>The right setting depends on context. When the agent reads a long list or legal text, users should be able to cut in easily. When it is collecting a card number, a cough should not abandon the flow. Some agents also allow certain utterances — confirmations, required disclosures — to be marked as non-interruptible.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>Barge-in is four problems: cancelling the agent's own echo, classifying whether the user's sound is a real interruption, stopping every buffered byte of audio, and rewriting the history to contain only what was heard.</p>
<p>Detection takes around 200 ms; buffered audio adds the rest — with 500 ms buffered, 700 ms of talking over the user.
