11:T1fbe,<p>An agent skill is a folder containing instructions — and optionally scripts and reference files — that an agent loads by itself when it recognises the situation.</p>
<p>It exists because the alternative does not fit.</p>
<h2 id="why-not-just-put-it-in-the-prompt"><a class="heading-anchor" href="#why-not-just-put-it-in-the-prompt">Why not just put it in the prompt</a></h2>
<p>A team accumulates procedures: how a release note is formatted, which checks run before a deploy, what a data export has to include, the conventions a migration follows. Written down, each is a page or two — call it 4,200 tokens.</p>
<p>Fifty of those, loaded on every request:</p>

















<table><thead><tr><th></th><th>tokens</th></tr></thead><tbody><tr><td>50 procedures, fully loaded</td><td>210,000</td></tr><tr><td>a 200,000-token context window</td><td>200,000</td></tr></tbody></table>
<p>It is over budget before the agent has read a single file of yours. And even if it fitted, 49 of the 50 are irrelevant to whatever was asked — diluting attention and paying for context that will not be used.</p>
<h2 id="loading-in-stages"><a class="heading-anchor" href="#loading-in-stages">Loading in stages</a></h2>
<p>The answer is to load almost nothing and expand on demand.</p>
<p><strong>Level one</strong> is a name and a one-line description, about 95 tokens per skill. Always present.</p>
<p><strong>Level two</strong> is the full instructions, loaded only for the skill that matched — 4,200 tokens.</p>
<p><strong>Level three</strong> is whatever the instructions themselves point at: a longer reference, a schema, an example file. Read only if the work needs it.</p>





















<table><thead><tr><th></th><th>tokens</th></tr></thead><tbody><tr><td>50 descriptions</td><td>4,750</td></tr><tr><td>one skill expanded</td><td>4,200</td></tr><tr><td><strong>total</strong></td><td><strong>8,950</strong></td></tr></tbody></table>
<p><strong>23× less</strong> than loading everything, and the descriptions cost 2.4% of the window — an amount you would not notice.</p>

<h2 id="the-description-is-the-whole-interface"><a class="heading-anchor" href="#the-description-is-the-whole-interface">The description is the whole interface</a></h2>
<p>Here is the consequence that matters, and it follows directly from the staging.</p>
<p>At level one the agent sees nothing but the descriptions. Whether a skill is ever used is decided entirely by whether its one line matches the situation — so the description is not a label, it is the trigger.</p>
<p>Which means the work of writing a good skill is mostly the work of writing that line. Two failures:</p>
<p><strong>Too vague.</strong> "Helps with reports" matches nothing in particular and will be skipped in favour of doing the work from scratch. The instructions inside may be excellent and will never be read.</p>
<p><strong>Too broad.</strong> "For any data-related task" matches constantly, including when something else was the right choice, and now a specific procedure is being applied to a situation it was not written for.</p>
<p>The useful shape is to say <em>when</em>, not <em>what</em>: "Use when producing the weekly operations summary — covers the required sections, the metric definitions, and the sign-off order." Someone reading that knows whether it applies. So does a model.</p>
<h2 id="what-unused-skills-actually-cost"><a class="heading-anchor" href="#what-unused-skills-actually-cost">What unused skills actually cost</a></h2>
<p>Worth doing this arithmetic because the intuition is wrong.</p>
<p>Of 50 skills, suppose 6 are relevant in a typical session. The other 44 cost 44 × 95 = <strong>4,180 tokens</strong> — 2.1% of the window. Negligible.</p>
<p>So the reason to prune a skill collection is not token cost. It is that every added skill makes the selection problem harder: fifty descriptions that overlap are harder to choose between than twenty that do not. Keep them because they are distinguishable, delete them because they are confusable, and do not think about the tokens at all.</p>
<h2 id="carrying-code"><a class="heading-anchor" href="#carrying-code">Carrying code</a></h2>
<p>A skill can include scripts, and this is more than a convenience.</p>
<p>Asking the model to write the code costs around 700 tokens and produces something slightly different every time. Invoking a script costs about 40 tokens and produces exactly the same behaviour on every run — 17.5× cheaper and, more importantly, deterministic.</p>
<p>Which suggests the division: put the <em>judgement</em> in the instructions and the <em>mechanics</em> in a script. Anything with a single correct implementation should not be regenerated on each use.</p>
<h2 id="where-it-sits-next-to-a-connectivity-protocol"><a class="heading-anchor" href="#where-it-sits-next-to-a-connectivity-protocol">Where it sits next to a connectivity protocol</a></h2>
<p>Two different questions, often confused because both extend an agent.</p>
<p>A connectivity protocol answers <strong>what can the agent reach</strong> — it exposes tools and data sources that were previously unreachable.</p>
<p>A skill answers <strong>how should this be done here</strong> — it supplies procedure for something already reachable.</p>
<p>An agent with tools and no procedure will do the work in a way that is reasonable and not yours. An agent with procedure and no tools cannot do the work at all. They are additive.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>Progressive disclosure is the mechanism, and it is not complicated: keep an index in context, expand one entry when it matches.</p>
<p>The interesting part is what that shifts.
