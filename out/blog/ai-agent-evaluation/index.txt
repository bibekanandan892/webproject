11:T2253,<p>An agent does not produce one answer. It produces a sequence of decisions — which tool, which arguments, what to do with the result — and then an answer at the end.</p>
<p>Scoring only the answer therefore discards most of what happened, including whether it was earned or lucky.</p>
<h2 id="why-the-steps-have-to-be-measured"><a class="heading-anchor" href="#why-the-steps-have-to-be-measured">Why the steps have to be measured</a></h2>
<p>Because per-step reliability compounds, and the compounding is brutal.</p>

<p>A 95% success rate per step sounds respectable. Over twenty steps it finishes <strong>35.8%</strong> of the time. To complete twenty steps nine times out of ten you need to be right on <strong>99.5%</strong> of individual steps.</p>
<p>This is why a final-outcome number is not enough on its own. Two agents can both complete 60% of tasks while having quite different per-step reliabilities, and the one with the better steps will pull ahead as tasks get longer — which is exactly what happens as you deploy it on real work.</p>
<h2 id="what-to-measure"><a class="heading-anchor" href="#what-to-measure">What to measure</a></h2>
<p><strong>The outcome.</strong> Did it finish the task correctly? Simple to define, matches what a user cares about, and says nothing about why a failure happened.</p>
<p><strong>The trajectory.</strong> Did it take sensible steps in a sensible order? This is where debugging lives, and where luck gets separated from skill. An agent that reached the right answer without calling the tool that would have told it the answer has guessed, and it will not guess right next time.</p>
<p>The trouble with trajectories is that there is rarely one correct path. Rather than demanding an exact sequence, it is usually more useful to check whether the required steps all happened (in order or not), what fraction of the steps taken were useful, and what fraction of the necessary ones were missed.</p>
<p><strong>The tool calls specifically.</strong> Was the right tool picked, were the arguments valid, did the call succeed, was the result used correctly, and was a non-existent tool ever invented. These are structured and machine-checkable, and they are where a large share of failures actually are.</p>
<h2 id="one-run-tells-you-nothing"><a class="heading-anchor" href="#one-run-tells-you-nothing">One run tells you nothing</a></h2>
<p>Agents are not deterministic. The same task twice produces different trajectories, and sometimes different outcomes.</p>

































<table><thead><tr><th>runs</th><th>interval on the success rate</th></tr></thead><tbody><tr><td>1</td><td>±78.4 pts</td></tr><tr><td>3</td><td>±45.3 pts</td></tr><tr><td>10</td><td>±24.8 pts</td></tr><tr><td>30</td><td>±14.3 pts</td></tr><tr><td>100</td><td>±7.8 pts</td></tr><tr><td>250</td><td>±5.0 pts</td></tr></tbody></table>
<p>Three runs pins the success rate to about ±45 points, which is to say not at all. Telling an 80% agent from a 70% one needs roughly 145 runs of each.</p>
<p>Which puts a hard floor under the cost of evaluating a change. If a prompt tweak is reported to have improved success from 70% to 80% on five runs, that is noise.</p>
<p>The practical compromise is a fixed test set run several times, reporting the average <em>and the worst case</em>. For anything that takes real actions, the worst case is the number that matters.</p>
<h2 id="what-else-has-to-be-tracked"><a class="heading-anchor" href="#what-else-has-to-be-tracked">What else has to be tracked</a></h2>
<p>Success rate alone will happily approve an agent that is unusable.</p>
<p><strong>Steps per task.</strong> Fewer is better, and a rising step count is often the first sign of a prompt change gone wrong.</p>
<p><strong>Cost and latency per task.</strong> An agent that succeeds 95% of the time at four dollars and ninety seconds a task may be worse than one at 88%, twenty cents and twelve seconds. Nothing in a quality metric surfaces that.</p>
<p><strong>Recovery.</strong> When a tool errors, does the agent adapt or collapse? Real tools fail, so this is a property worth measuring on purpose by injecting failures.</p>
<p><strong>Loops.</strong> The same call repeated forever. Cap steps and count how often the cap is hit — that number should be near zero and is easy to forget to look at.</p>
<h2 id="testing-safely"><a class="heading-anchor" href="#testing-safely">Testing safely</a></h2>
<p>An agent under evaluation is taking real actions. Send an email during a test run and the email is sent.</p>
<p>So evaluation runs against a sandbox: fake tools with the same interfaces, seeded data, a database that gets reset. This also fixes reproducibility — an agent evaluated against the live web is being scored partly on what the web did that day.</p>
<p>And build the test set from <strong>real tasks</strong>, including the ones that go wrong: ambiguous requests, tools that fail, inputs designed to push it somewhere it should not go. Easy tasks confirm the agent works on easy tasks.</p>
<h2 id="the-short-version"><a class="heading-anchor" href="#the-short-version">The short version</a></h2>
<ul>
<li>An agent produces a sequence of decisions, so scoring only the final answer discards most of the evidence.</li>
<li>Per-step reliability compounds: 95% per step is 35.8% over twenty steps.</li>
<li>Finishing twenty steps nine times in ten needs 99.5% per step.</li>
<li>Outcome says whether it worked; trajectory says why, and separates skill from luck.</li>
<li>Tool selection, arguments and result handling are structured and cheap to check automatically.</li>
<li>Agents are non-deterministic — three runs measures nothing; distinguishing 80% from 70% takes about 145.</li>
<li>Track steps, cost, latency, recovery from tool failures, and how often the step cap is hit.</li>
<li>Evaluate in a sandbox, because a test run takes real actions and the live world is not reproducible.</li>
