4:T22a2,<p>A reranker takes a list of candidate documents and reorders them by how well they actually answer the question. It never searches, never adds anything, never invents. It only sorts what it was handed.</p>
<p>That sounds like a small job. It exists because the thing that produced the list was working under a constraint the reranker is not.</p>
<h2 id="the-constraint"><a class="heading-anchor" href="#the-constraint">The constraint</a></h2>
<p>Search over a large corpus has to be fast, and fast means the documents were processed <strong>before the question existed</strong>.</p>
<p>An embedding-based retriever encodes each document into a vector in advance. When a question arrives it encodes that too and finds the nearest vectors. This works because the document's vector does not depend on the question — which is exactly what makes it possible to precompute, and exactly what limits it.</p>
<p>A document's embedding is a summary of the whole document, fixed in advance, made without knowing what would be asked. It captures roughly what the document is about. It cannot emphasise the one sentence that answers <em>this</em> question, because when it was made there was no question.</p>
<p>A keyword retriever has the analogous problem in a different form: it matches words, so it misses a document that says the right thing in different words, and matches one that uses the right words about something else.</p>
<h2 id="reading-both-together"><a class="heading-anchor" href="#reading-both-together">Reading both together</a></h2>
<p>A reranker drops the constraint. It takes the question and one document as a <strong>single input</strong> and produces a relevance score.</p>
<p>Because it sees both at once, attention can run between them — this phrase in the question against that clause in the document. It can tell a document that mentions the topic from one that answers the question, which is precisely the distinction a precomputed summary cannot make.</p>
<p>The price is that nothing can be prepared in advance. The score depends on the pair, so it exists only once both halves are present.</p>

<p>So the pipeline is: a fast retriever narrows a million documents to a hundred, and a slow model reads all hundred properly and keeps the best five.</p>
<p>The retriever does not have to be right about the order. It only has to get the right documents <em>somewhere</em> in its hundred. That is a much easier requirement, and it is why a crude first stage paired with a good reranker beats a better first stage alone.</p>
<h2 id="the-knob"><a class="heading-anchor" href="#the-knob">The knob</a></h2>
<p>How many candidates to rerank is the one parameter that matters.</p>
<p>Too few and the reranker cannot fix what the retriever missed — if the right document was at rank 150 and you rerank 100, no amount of careful reading recovers it. Too many and the latency grows linearly with no benefit, because the extra candidates were not relevant anyway.</p>
<p>A hundred to two hundred in, five to ten out is the usual range. The output number matters as well as the input: passing a model twenty documents when three were relevant buries the useful ones among distractors, and long contexts are read least reliably in the middle.</p>
<h2 id="in-between"><a class="heading-anchor" href="#in-between">In between</a></h2>
<p>There is a middle design worth knowing about. Instead of one vector per document, keep one per token, precomputed. At query time, compare the question's tokens against the document's tokens directly.</p>
<p>The comparison is fine-grained, like a cross-encoder. The document side is still precomputed, like a bi-encoder. The cost is storage — hundreds of vectors per document rather than one — which is a real constraint at corpus scale, but it can be fast enough to serve as the retriever itself rather than only reordering someone else's shortlist.</p>
<h2 id="why-it-matters-more-than-it-sounds"><a class="heading-anchor" href="#why-it-matters-more-than-it-sounds">Why it matters more than it sounds</a></h2>
<p>In a retrieval-augmented system the model can only answer from what it was given. A wrong document does not produce a hedged answer; it produces a confident answer about the wrong thing.</p>
<p>Reranking is where that gets caught, and it is often the cheapest available improvement — no retraining, no re-embedding the corpus, one component added between two existing ones.</p>
<h2 id="the-short-version"><a class="heading-anchor" href="#the-short-version">The short version</a></h2>
<ul>
<li>A reranker reorders candidates; it never searches or adds.</li>
<li>Retrieval is fast because documents are encoded before the question exists — which is also its limitation.</li>
<li>A reranker reads the question and document together, so it can tell mentioning a topic from answering a question.</li>
<li>That makes it impossible to precompute: 1,000 queries over 1M documents is a billion runs.</li>
<li>At ~10 ms a pair, scoring a whole corpus per query is 2.8 hours; scoring a hundred is about a second.</li>
<li>So the retriever only needs the right document somewhere in its shortlist, not at the top.</li>
<li>Rerank 100–200, keep 5–10; anything the retriever missed entirely is unrecoverable.</li>
<li>Late-interaction models keep per-token vectors precomputed, trading storage for precision.</li>
