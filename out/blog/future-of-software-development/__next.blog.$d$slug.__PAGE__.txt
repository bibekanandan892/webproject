5:T1f41,<p>Coding agents can now read a repository, write a feature across a dozen files, run the tests and fix what fails. It is natural to ask what happens to software development when the writing of code costs almost nothing.</p>
<p>The answer is easier to reason about with a little arithmetic than with predictions, because the arithmetic is not new. It is Amdahl's law.</p>
<h2 id="coding-was-never-most-of-the-job"><a class="heading-anchor" href="#coding-was-never-most-of-the-job">Coding was never most of the job</a></h2>
<p>Studies of how developers spend their time vary, but they agree on the shape: writing new code is a minority of the work. The rest is understanding the existing system, working out what should be built, reviewing, testing, debugging, coordinating with other people, and dealing with production.</p>
<p>Call writing code 30% of the job. If AI makes that part faster and nothing else changes:</p>

























<table><thead><tr><th>coding speed-up</th><th>whole job speed-up</th></tr></thead><tbody><tr><td>2×</td><td>1.18×</td></tr><tr><td>5×</td><td>1.32×</td></tr><tr><td>10×</td><td><strong>1.37×</strong></td></tr><tr><td>infinitely fast</td><td><strong>1.43×</strong></td></tr></tbody></table>
<p>Making the 30% free removes 30% of the time. Everything else still takes as long as it did. That is the ceiling on "AI writes the code" alone, and it is lower than the experience of using the tools suggests — because the tools feel fastest on exactly the part that was never the bottleneck.</p>
<h2 id="the-bottleneck-moves"><a class="heading-anchor" href="#the-bottleneck-moves">The bottleneck moves</a></h2>
<p>When one stage of a pipeline gets much faster, the work piles up at the next one. With code generation nearly free, three stages become the constraint.</p>
<p><strong>Specification.</strong> An agent builds what it is asked for. "Add export to CSV" leaves open which fields, what encoding, how to handle commas in values, who can use it, what happens with a million rows. A person used to resolve those questions while writing the code, often without noticing. Now they have to be resolved before — or the agent resolves them by guessing.</p>
<p><strong>Verification.</strong> Generated code arrives faster than anyone can read it. Review becomes the slowest step, and reviewing code you did not write, in volume, is a different skill from writing it. Tests, types, and automated checks stop being good practice and become the only way to keep up.</p>
<p><strong>Integration and judgement.</strong> Deciding which of three working approaches fits the system, what not to build, when to accept a trade-off. None of that is made faster by generating code faster.</p>
<p>If AI also speeds up testing and review — say 60% of the job made three times faster — the gain becomes <strong>1.67×</strong>. If everything except deciding, specifying and integrating — 40% of the job — were instantaneous, the ceiling is <strong>2.5×</strong>. The size of the remaining human share sets the limit, not the speed of the model.</p>

<h2 id="what-the-work-becomes"><a class="heading-anchor" href="#what-the-work-becomes">What the work becomes</a></h2>
<p>Follow the bottlenecks and the shape of the job comes out of them.</p>
<p><strong>Writing intent precisely.</strong> The highest-leverage artefact becomes the description of what the software must do: requirements, constraints, edge cases, acceptance criteria. A clear definition of done is what lets an agent finish a task correctly without supervision — and its absence is what makes agents produce plausible code that solves the wrong problem.</p>
<p><strong>Building the checks.</strong> Test suites, type systems, linters, property tests, staging environments, observability. These are what make it safe to accept code faster than it can be read. Teams that already had good automated verification get the largest gains from AI; teams that relied on careful reading get the smallest.</p>
<p><strong>Architecture and taste.</strong> Agents are good at local changes and weaker at keeping a large system coherent over time. Someone has to decide boundaries, choose what to standardise, and say no to complexity that each individual change would happily add.</p>
<p><strong>Managing agents.</strong> Splitting work into tasks an agent can finish, running several in parallel, reviewing their output, and knowing which kinds of task to trust them with. It resembles leading a team more than typing.</p>
<h2 id="what-stays-hard"><a class="heading-anchor" href="#what-stays-hard">What stays hard</a></h2>
<p>Understanding the problem. Most failed software was not failed by bad code; it built the wrong thing, or the right thing for the wrong users, or something that could not be operated. Cheaper code makes it cheaper to build the wrong thing quickly.</p>
<p>Owning the result. When a system fails in production at 3 a.m., someone has to understand it well enough to fix it. Code nobody on the team has read is code nobody can debug quickly. Keeping understanding in the team — through review, documentation and deliberate ownership — becomes a real cost to plan for, not a side effect of writing it yourself.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>AI is making code nearly free to write, and Amdahl's law limits what that alone can do: if coding is 30% of the job, even infinitely fast coding makes the job 1.43× faster.</p>
<p>The rest of the gain has to come from the stages that remain — specifying what to build, verifying that it works, and keeping the system coherent. Those become the core of the profession.
