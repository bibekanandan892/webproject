11:T2e40,<p>There is a limit to how much text can usefully go into one model call. Not just the hard context limit — well before that, quality falls off. Material in the middle of a very long input gets used less reliably than material at the ends.</p>
<p>A recursive language model works around that by never putting the input in front of the main model at all.</p>
<h2 id="the-input-becomes-a-variable"><a class="heading-anchor" href="#the-input-becomes-a-variable">The input becomes a variable</a></h2>
<p>The full text sits in a code environment as a variable. The main model gets a short prompt saying that the variable exists, roughly what it contains, and that it has two things available: the ability to run code, and a function that calls another language model.</p>
<p>Then it writes code.</p>

<p>Each <code>call_llm</code> sends one ticket to a separate model instance and gets back a single line. The main model never sees a ticket. It sees four hundred one-line answers, decides whether that is enough, and either answers or writes more code.</p>
<p>That last part is what makes it recursive rather than a fixed pipeline: the model chooses how to split the input, and it chooses differently depending on what is being asked. A question about one specific customer would produce a filter before the fan-out. A question about overall themes would produce grouping.</p>

<p>Four hundred support tickets, about 600 tokens each — 240,000 tokens of source.</p>

<p>The number that changed is the first row. No call has to handle more than 660 tokens — <strong>364 times smaller</strong> than the original problem — and every one of them is operating in the range where models are reliable.</p>
<p>The number that did <em>not</em> improve is the third row. Total tokens went <strong>up</strong>, by about 23%, because each sub-call repeats a prompt and produces output. This is not a technique for processing fewer tokens. It is a technique for never processing many at once.</p>
<h2 id="when-it-is-cheaper-and-when-it-is-not"><a class="heading-anchor" href="#when-it-is-cheaper-and-when-it-is-not">When it is cheaper, and when it is not</a></h2>
<p>That distinction decides the economics, and the answer depends entirely on which model runs the leaves.</p>





















<table><thead><tr><th></th><th>cost</th></tr></thead><tbody><tr><td>one frontier call over the whole input</td><td>$0.606</td></tr><tr><td>leaves on a small model, root on the frontier</td><td><strong>$0.067</strong></td></tr><tr><td>every call on the frontier model</td><td>$0.898</td></tr></tbody></table>
<p>Nine times cheaper, or half again more expensive, from the same structure.</p>
<p>The saving does not come from recursion. It comes from the fan-out moving almost all the token volume onto a cheap model, and leaving only the small synthesis step on the expensive one. Run the whole tree on your best model and you pay a premium for the privilege of splitting the work up.</p>
<p>Which is the right way to think about it: recursion is what makes it <em>possible</em> to use a small model on a large problem, and that is where the money is.</p>
<h2 id="against-retrieving-instead"><a class="heading-anchor" href="#against-retrieving-instead">Against retrieving instead</a></h2>
<p>Search picks the relevant pieces before the model sees anything. Its weakness is that it has to decide relevance from the question alone, which fails when what matters cannot be recognised by resemblance — counting, comparing across everything, or finding what is absent.</p>
<p>A recursive model visits everything and decides as it goes, and can change strategy after seeing partial results. That costs far more, since it touches the whole input rather than a retrieved slice.</p>
<p>Roughly: search when the answer is <em>in</em> a few places, recurse when the answer is <em>about</em> all of it.</p>
<h2 id="what-it-costs-you"><a class="heading-anchor" href="#what-it-costs-you">What it costs you</a></h2>
<p><strong>Latency.</strong> Four hundred calls fan out in parallel, but the levels are sequential, and the slowest leaf holds up its group.</p>
<p><strong>Errors compound.</strong> A leaf that misreads its ticket returns a confident wrong line, and the root cannot tell — it never saw the source. Nothing downstream can catch it.</p>
<p><strong>It is hard to debug.</strong> The model wrote the code that split the input. When an answer is wrong, the fault may be in a leaf, in the synthesis, or in a split that put related material in different groups. The transcript shows what happened without showing why.</p>
<p><strong>It needs real infrastructure.</strong> A sandboxed environment that runs model-written code, with limits on time, calls and spend.</p>
<h2 id="the-short-version"><a class="heading-anchor" href="#the-short-version">The short version</a></h2>
<ul>
<li>The input stays in a code environment; the main model gets the variable name, not the contents.</li>
<li>It writes code that slices the input and calls other models on the pieces.</li>
<li>Only short summaries come back, so the root's context stays small.</li>
<li>On 400 tickets: largest single context 240,000 → 660 tokens, a 364× reduction.</li>
<li>Total tokens go <em>up</em> about 23% — this does not reduce work, it redistributes it.</li>
<li>It is 9× cheaper only if the leaves run on a small model; all-frontier is more expensive than one big call.</li>
<li>Search when the answer sits in a few places; recurse when it is about the whole input.</li>
<li>The costs are latency, uncatchable leaf errors, and debugging model-written code.</li>
