12:T2207,<p>A language model has no memory between requests. Everything it can use to produce an answer — the system prompt, the conversation so far, retrieved documents, tool results, and the answer it is writing — has to be present, as tokens, in a single input. That input has a maximum size: the <strong>context window</strong>.</p>
<h2 id="what-fits"><a class="heading-anchor" href="#what-fits">What fits</a></h2>
<p>Context windows are measured in tokens. At roughly 1.3 tokens per English word and about 330 words to a printed page:</p>

























<table><thead><tr><th>context window</th><th>words</th><th>pages</th></tr></thead><tbody><tr><td>8,192 tokens</td><td>6,302</td><td>19</td></tr><tr><td>131,072 tokens</td><td><strong>100,825</strong></td><td><strong>306</strong></td></tr><tr><td>1,000,000 tokens</td><td>769,231</td><td>2,331</td></tr></tbody></table>
<p>A 128k window holds a long novel or a substantial codebase module. A million-token window holds several books. The output counts against the same budget: if the window is 128k and the prompt is 120k, at most 8k tokens remain for the reply.</p>
<h2 id="why-it-is-limited"><a class="heading-anchor" href="#why-it-is-limited">Why it is limited</a></h2>
<p>Two costs grow with context length.</p>
<p><strong>Attention arithmetic.</strong> Each token attends to every earlier token, so the number of pairs grows with the square of the length. Going from 8k to 128k tokens multiplies the pairs by <strong>256</strong> — from 67 million to 17 billion per layer and head. Kernels like Flash Attention make this fast in practice, but the growth is still quadratic.</p>
<p><strong>Memory for the KV cache.</strong> Every token in context leaves keys and values at every layer, held for the rest of the generation. For a 70B-class model with grouped-query attention, about 320 KB per token: <strong>42.9 GB</strong> for a single 131k-token conversation. That memory decides how many conversations a GPU can serve at once, and therefore the cost.</p>
<p>Training matters too. A model trained mostly on short sequences does not automatically handle long ones well; long-context ability has to be trained, often in a late stage with position-encoding adjustments.</p>
<h2 id="bigger-is-not-the-same-as-better"><a class="heading-anchor" href="#bigger-is-not-the-same-as-better">Bigger is not the same as better</a></h2>
<p>A model that <em>accepts</em> 128k tokens does not necessarily <em>use</em> all of them equally well.</p>
<ul>
<li><strong>Lost in the middle.</strong> Many models recall information near the start and end of a long context better than information buried in the middle.</li>
<li><strong>Distraction.</strong> Irrelevant material competes for attention. Adding loosely related documents can lower accuracy compared with adding only the relevant one.</li>
<li><strong>Latency.</strong> Processing a long prompt takes time before the first output token appears, even with fast hardware.</li>
<li><strong>Cost.</strong> Input tokens are billed. A full window on every request is expensive.</li>
</ul>
<p>The practical lesson is to treat context as a scarce resource to be spent deliberately, not a container to be filled.</p>

<h2 id="conversations-re-send-everything"><a class="heading-anchor" href="#conversations-re-send-everything">Conversations re-send everything</a></h2>
<p>Because the model is stateless, a chat application sends the entire conversation with every new message. If each turn adds 500 tokens, turn 20 sends 10,000 tokens — and the total sent over the whole conversation is <code>500 × (1 + 2 + … + 20) =</code> <strong>105,000 tokens</strong>, more than ten times what is finally in context.</p>
<p>Prompt caching softens this: a provider can reuse the computation for a prefix it has already processed, charging a fraction of the price and skipping most of the prefill time. Keeping the stable part of the prompt — system instructions, tool definitions, early history — unchanged and at the front is what makes caching effective.</p>
<h2 id="managing-context"><a class="heading-anchor" href="#managing-context">Managing context</a></h2>
<p>When conversations or documents outgrow the window, or simply grow expensive, systems choose what to keep:</p>
<ul>
<li><strong>Retrieval</strong> — store documents outside the context and bring in only the passages relevant to the current question.</li>
<li><strong>Summarisation and compaction</strong> — replace old turns with a summary that preserves decisions, facts and open tasks.</li>
<li><strong>Truncation</strong> — drop the oldest turns, keeping the system prompt and recent exchanges.</li>
<li><strong>Structured memory</strong> — save key facts to an external store and reinsert only those that matter.</li>
<li><strong>Ordering</strong> — place the most important material at the start or end, where it is most reliably used.</li>
</ul>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>The context window is the single input that holds everything a model can see: instructions, history, documents, tool results and its own answer. At 128k tokens it is about 306 pages, but filling it costs 256 times the attention arithmetic of an 8k context and about 42.9 GB of cache on a 70B-class model.</p>
<p>Models do not use long contexts uniformly, and chats re-send their whole history each turn — 105,000 tokens over 20 turns for 10,000 in context.
