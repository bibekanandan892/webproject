4:T2528,<p>A language model does one thing: text in, text out. It cannot look anything up, cannot remember yesterday, cannot check whether it was right, and cannot do anything at all in the outside world.</p>
<p>Harness engineering is everything you build around the model to close that gap. The model is one component. The harness is the system that makes it useful.</p>
<h2 id="why-the-model-is-not-the-product"><a class="heading-anchor" href="#why-the-model-is-not-the-product">Why the model is not the product</a></h2>
<p>Picture hiring someone genuinely brilliant, then giving them no logins, no access to your systems, no notebook, and no colleague to check their work. On day two they remember nothing about day one. They would still be brilliant, and still unable to do the job.</p>
<p>That is a raw model. Everything that turns it into something a user can rely on lives outside it:</p>
<ul>
<li>reaching real data and real systems</li>
<li>remembering what was said earlier</li>
<li>coping when something fails</li>
<li>following instructions the same way every time</li>
<li>knowing whether the output was any good</li>
<li>seeing what is happening once real users arrive</li>
</ul>
<p>A better model raises the ceiling. The harness decides how much of that ceiling you actually reach.</p>
<h2 id="the-parts-of-a-harness"><a class="heading-anchor" href="#the-parts-of-a-harness">The parts of a harness</a></h2>
<p>Most harnesses end up with the same seven pieces.</p>





































<table><thead><tr><th>part</th><th>what it does</th></tr></thead><tbody><tr><td><strong>Prompts</strong></td><td>Assembles the system instructions, templates and context sent on each call</td></tr><tr><td><strong>Tools</strong></td><td>Declares what the model may call, and actually runs it when it asks</td></tr><tr><td><strong>Memory</strong></td><td>Keeps conversation history, and compresses it before it overruns the context</td></tr><tr><td><strong>Errors</strong></td><td>Handles a failed tool, a malformed response, a timeout, a rate limit</td></tr><tr><td><strong>Input and output</strong></td><td>Validates what goes in, and parses and checks what comes back</td></tr><tr><td><strong>Guardrails</strong></td><td>Blocks unsafe or out-of-scope requests and responses</td></tr><tr><td><strong>Observability</strong></td><td>Logs, traces and metrics, so a production problem is diagnosable</td></tr></tbody></table>
<p>None of this is model work. All of it is engineering.</p>
<h2 id="the-loop-that-makes-an-agent"><a class="heading-anchor" href="#the-loop-that-makes-an-agent">The loop that makes an agent</a></h2>
<p>An agent is a harness running a loop.</p>
<p>The model never executes anything itself. It reads what it has been given and says what it would like to happen next. Everything else is the harness's job:</p>

<p>Take a support agent asked: <em>has order 4172 shipped, and if not, tell the customer when it will?</em></p>
<p>The harness assembles the prompt — the instructions, the available tools, the question — and sends it. The model replies asking for a tool:</p>
<pre><code>lookup_order(id=4172)
</code></pre>
<p>The harness runs that against the real system, gets back <code>status: packing, ships: 9 September</code>, appends it to the conversation, and calls the model again. Now the model asks for the second tool:</p>
<pre><code>send_message(to="customer", text="Your order is packed and ships on 9 September.")
</code></pre>
<p>The harness runs that too, appends the result, and calls the model once more. This time the model asks for nothing, so the loop ends and its final text is returned.</p>
<p>Three model calls, two tool executions, one answer. The model decided <em>what</em> to do. The harness did all of it.</p>
<h2 id="knowing-whether-it-works"><a class="heading-anchor" href="#knowing-whether-it-works">Knowing whether it works</a></h2>
<p>You cannot improve what you cannot measure, and "it seemed fine when I tried it" does not survive contact with real users.</p>
<p>An evaluation harness is a second harness whose job is grading the first. It holds a fixed set of test inputs, runs them through the system, and scores the results.</p>
<p>How you score depends on the task. When there is a right answer — a lookup, a classification, an extraction — compare against it directly and count. When there isn't — a summary, an explanation, a reply to a customer — the usual approach is to have another model grade the output against written criteria.</p>
<p>The point of fixing the test set is that you can change a prompt, swap a model, or rewrite a tool, and see whether things got better or worse instead of guessing.</p>
<h2 id="what-keeps-it-manageable"><a class="heading-anchor" href="#what-keeps-it-manageable">What keeps it manageable</a></h2>
<ul>
<li><strong>Keep the parts separate.</strong> Prompt assembly, tool execution, and memory should be independently replaceable. They change at different rates.</li>
<li><strong>Log everything.</strong> Every prompt, every tool call, every response. When something goes wrong in production, the log is all you have.</li>
<li><strong>Add guardrails early.</strong> Retrofitting safety onto a system that already has users is far harder than building it in.</li>
<li><strong>Assume tools fail.</strong> Timeouts, bad input, rate limits. Decide what happens on each, rather than letting an exception escape.</li>
<li><strong>Test the harness itself.</strong> It is ordinary code with ordinary bugs, and most production incidents come from it rather than from the model.</li>
<li><strong>Watch it after launch.</strong> Real traffic finds inputs your test set never had.</li>
</ul>
<h2 id="the-short-version"><a class="heading-anchor" href="#the-short-version">The short version</a></h2>
<ul>
<li>A model only maps text to text. Everything else is the harness.</li>
<li>The harness handles prompts, tools, memory, errors, I/O, guardrails and observability.</li>
<li>An agent is the harness looping: call the model, run whatever tool it asks for, feed the result back, repeat until it stops asking.</li>
<li>An evaluation harness with a fixed test set is how you tell whether a change helped.</li>
<li>The harness is ordinary software, and it is usually most of the code.</li>
