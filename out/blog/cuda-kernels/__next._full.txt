12:T2388,<p>Every operation a neural network runs on a GPU — each matrix multiply, each activation, each normalisation — is a <strong>kernel</strong>: a function the CPU launches, which the GPU then runs across thousands of threads in parallel. A forward pass through a large model is a sequence of hundreds of kernel launches.</p>
<p>Most people never write one. But the reasons some operations are fast and others are slow, why "fused" kernels exist, and why Flash Attention was such a large improvement all come from how kernels work.</p>
<h2 id="the-shape-of-a-kernel"><a class="heading-anchor" href="#the-shape-of-a-kernel">The shape of a kernel</a></h2>
<p>A kernel is written from the point of view of a single thread. The programmer says what one thread does, and launches a grid of them:</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="cuda" data-theme="github-light github-dark-default"><code data-language="cuda" data-theme="github-light github-dark-default" style="display: grid;"><span data-line=""><span>__global__ void add(const half* x, const half* y, half* out, int n) {</span></span>
<span data-line=""><span>    int i = blockIdx.x * blockDim.x + threadIdx.x;   // which element am I?</span></span>
<span data-line=""><span>    if (i &#x3C; n) out[i] = x[i] + y[i];</span></span>
<span data-line=""><span>}</span></span>
<span data-line=""> </span>
<span data-line=""><span>// launch: enough blocks of 256 threads to cover n elements</span></span>
<span data-line=""><span>add&#x3C;&#x3C;&#x3C;(n + 255) / 256, 256>>>(x, y, out, n);</span></span></code></pre></figure>
<p>The hierarchy has three levels:</p>
<ul>
<li><strong>Threads</strong> each handle a small piece of the work — here, one element.</li>
<li><strong>Blocks</strong> group threads (here 256) that run on the same streaming multiprocessor and can share a small, very fast on-chip memory.</li>
<li>The <strong>grid</strong> is all the blocks needed to cover the problem.</li>
</ul>
<p>The hardware runs threads in groups of 32 called <strong>warps</strong>, which execute the same instruction in lockstep. Threads in a warp that take different branches run one branch after the other, so divergent code is slower.</p>
<h2 id="the-one-ratio-that-decides-speed"><a class="heading-anchor" href="#the-one-ratio-that-decides-speed">The one ratio that decides speed</a></h2>
<p>A GPU has two limits: how fast it can compute and how fast it can move data from its main memory. For an H100, roughly 989 trillion 16-bit operations per second against 3.35 TB per second of memory bandwidth.</p>
<p>Divide one by the other: <strong>295 operations per byte.</strong> A kernel that does fewer than 295 operations for every byte it reads or writes cannot keep the arithmetic units busy — it is waiting on memory. This ratio is a kernel's <strong>arithmetic intensity</strong>, and it predicts performance better than anything else.</p>























<table><thead><tr><th>kernel</th><th>operations per byte</th><th>bound by</th><th>share of peak compute</th></tr></thead><tbody><tr><td>element-wise add (fp16)</td><td>0.17</td><td>memory</td><td><strong>0.056%</strong></td></tr><tr><td>matrix multiply, 4,096 × 4,096</td><td>1,365</td><td>compute</td><td>up to ~100%</td></tr></tbody></table>
<p>The add reads two 2-byte numbers, writes one, and does one addition: 1 operation per 6 bytes. It uses about one two-thousandth of the chip's arithmetic. Nothing about the code can fix that; the kernel is waiting on memory by construction.</p>
<p>The matrix multiply does <code>2n³</code> operations on <code>3n²</code> numbers. At n = 4,096 that is 1,365 operations per byte, well past the 295 needed. The arithmetic takes about 139 µs and the memory traffic only 30 µs. This is why GPUs are built around matrix multiplication — it is the operation that can actually feed them.</p>

<h2 id="fusion-stop-moving-the-same-data"><a class="heading-anchor" href="#fusion-stop-moving-the-same-data">Fusion: stop moving the same data</a></h2>
<p>A transformer layer contains many memory-bound operations in a row: add a bias, apply an activation, multiply by a scale, add the residual. Done as separate kernels, each one reads the whole tensor from memory and writes it back:</p>
<p><code>x → [kernel 1] → memory → [kernel 2] → memory → [kernel 3] → out</code></p>
<p>A fused kernel does all three on each element while it is in registers, reading <code>x</code> once and writing <code>out</code> once. For three element-wise operations on a 64-million-element tensor:</p>




















<table><thead><tr><th></th><th>memory traffic</th><th>time</th></tr></thead><tbody><tr><td>three kernels</td><td>3 reads + 3 writes</td><td>240 µs</td></tr><tr><td>one fused kernel</td><td>1 read + 1 write</td><td><strong>80 µs</strong></td></tr></tbody></table>
<p>Exactly 3× faster, with the same arithmetic. Compilers like <code>torch.compile</code> and XLA find these fusions automatically; hand-written fused kernels exist for the combinations that matter most.</p>
<h2 id="tiling-reuse-what-you-loaded"><a class="heading-anchor" href="#tiling-reuse-what-you-loaded">Tiling: reuse what you loaded</a></h2>
<p>Fusion avoids writing intermediate results. Tiling avoids reading the same input repeatedly. A matrix multiply loads a tile of each input into the block's shared memory once, and every thread in the block reuses it many times. That reuse is what pushes the intensity to 1,365.</p>
<p>Flash Attention is this idea applied to attention. The naive version writes the full sequence-by-sequence score matrix to main memory and reads it back for the softmax and again for the weighted sum. Flash Attention computes attention in tiles that stay in on-chip memory, never materialising the full matrix. The arithmetic is unchanged; the memory traffic collapses.</p>
<h2 id="launch-overhead"><a class="heading-anchor" href="#launch-overhead">Launch overhead</a></h2>
<p>Each kernel launch costs a few microseconds on the CPU side. For large tensors this is negligible. For small ones it dominates: adding two million-element vectors moves 6 MB, which takes about 1.8 µs — less than the ~5 µs it takes to launch the kernel. During decoding, where each step touches small tensors through hundreds of kernels, launch overhead can be a fifth of the step. CUDA graphs fix this by recording the whole sequence of launches once and replaying it as a single unit.</p>
<h2 id="what-to-take-away"><a class="heading-anchor" href="#what-to-take-away">What to take away</a></h2>
<p>A CUDA kernel is a function written for one thread and run across thousands. Its speed is governed by arithmetic intensity: below about 295 operations per byte on an H100 it waits on memory, above it it uses the compute. An element-wise add reaches 0.056% of peak; a large matrix multiply can reach nearly all of it.</p>
